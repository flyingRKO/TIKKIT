# 백엔드 테스트 작성 (TIKKIT)

서비스 레이어 → 레포지토리 레이어 → (둘 다 갖춰졌다면) 통합 테스트 순서로 3계층만 작성한다. **컨트롤러 전용 테스트(`@WebMvcTest` + 목업 서비스)는 만들지 않는다** — 통합 테스트가 실제 컨트롤러까지 태우므로 같은 것을 두 번 확인하는 셈이다.

## 참고 파일

- `service.md`: 서비스 레이어 유닛 테스트(Mockito).
- `repository.md`: 레포지토리 레이어 테스트(Testcontainers, 실제 DB).
- `integration.md`: 통합 테스트(전체 스프링 컨텍스트, 컨트롤러 포함). 동시성 재현 테스트도 여기 속한다.

## 절차

1. 방금 구현한(또는 보강할) 계층이 무엇인지 확인한다.
2. 서비스 코드라면 `service.md`, 레포지토리/QueryDSL 코드라면 `repository.md`를 확인해 그 계층의 테스트를 작성한다.
3. 같은 기능의 서비스+레포지토리가 모두 작성·테스트됐다면, `integration.md`를 확인해 해당 API 엔드포인트에 통합 테스트 1세트를 추가한다.
4. 동시성이 관련된 기능(재고 차감, 좌석 선점)이면 `integration.md`의 동시성 재현 테스트 패턴도 함께 검토한다.

## 안티패턴

- ❌ `@WebMvcTest`로 컨트롤러만 따로 목업 서비스로 테스트 → ✅ 통합 테스트가 컨트롤러까지 실제로 태우므로 별도로 만들지 않는다
- ❌ 레포지토리 테스트를 H2로 작성 → ✅ Testcontainers PostgreSQL(조건부 UPDATE, `CHECK` 제약은 H2로 재현 불가)
- ❌ 성공 케이스만 테스트 → ✅ 예외/실패 케이스(재고 부족, 상태 전이 위반 등)를 반드시 포함
- ❌ 서비스 테스트에서 실제 DB에 접근 → ✅ Repository는 Mockito로 목업
