# DB 설계 (TIKKIT 백엔드)

`docs/ERD.md`가 TIKKIT의 살아있는 스키마 소스다. 새 테이블/컬럼을 설계하거나 기존 스키마를 바꿀 때는 항상 이 문서를 함께 갱신한다 — 코드만 바꾸고 문서를 놔두면 다음 설계 때 잘못된 상태를 기준으로 작업하게 된다.

## 참고 파일

- `conventions.md`: 타입·명명·제약·동시성 패턴. 컬럼 하나를 정할 때마다 확인한다.
- `migration.md`: Flyway 버전 규칙과 무중단 스키마 변경(expand/backfill/contract) 절차. 기존 테이블을 바꿀 때 확인한다.

## 절차

1. **요구사항 확인** — 비즈니스 규칙이 PRD/ERD에 없으면 임의로 정하지 말고 사용자에게 확인한다(루트 `CLAUDE.md`의 "추측하지 말고 질문할 것" 원칙). 예: 금액 컬럼 타입, 테이블 단/복수 규칙처럼 프로젝트 전체에 영향을 주는 결정은 특히 그렇다.
2. **`conventions.md` 기준으로 컬럼 설계** — 타입, 제약, 인덱스를 정한다.
3. **`docs/ERD.md` 갱신** — 새/변경 테이블을 표와 Mermaid `erDiagram`에 반영한다. 기존 테이블 변경이면 "마이그레이션 이력" 표에도 한 줄 추가한다. 테이블·컬럼 한국어 `COMMENT` 문도 함께 작성한다.
4. **Flyway 스크립트 작성** — `migration.md`의 버전 규칙을 따른다. 기존 테이블을 무중단으로 바꿔야 하면 expand → backfill → contract 3단계로 나눈다.
5. **JPA 엔티티 매핑** — `@Table(name = "...")`(복수형), 필드 타입은 `conventions.md`를 따른다.
6. **검증 테스트 작성** — 제약 조건(UNIQUE/CHECK)과, 마이그레이션이면 데이터 정합성(예: 백필 후 건수 일치)을 테스트로 확인한다.

## 안티패턴

- ❌ 컬럼 타입을 정할 때 `float`/`double`로 금액을 저장 → ✅ `numeric(12,0)` + `BigDecimal`
- ❌ `ddl-auto: update`로 스키마를 암묵적으로 바꿈 → ✅ Flyway 마이그레이션 파일로 명시
- ❌ 테이블 하나를 한 번에 뜯어고쳐 배포 중단 위험을 만듦 → ✅ expand → backfill → contract로 나눈다
- ❌ ERD.md는 그대로 두고 엔티티 코드만 수정 → ✅ 둘을 항상 같이 갱신
