# DB 설계 컨벤션

`docs/ERD.md`의 공통 규칙을 재사용 가능한 형태로 정리한 것이다. 실제 스키마 내용(테이블·컬럼 목록)은 항상 `docs/ERD.md`를 확인한다 — 이 파일은 규칙만 담는다.

## 명명 규칙

| 대상 | 규칙 | 예시 |
|---|---|---|
| 테이블명 | 복수형 snake_case | `members`, `ticket_grades`, `schedule_seats` |
| JPA 엔티티 클래스명 | 단수형 PascalCase | `Member`, `TicketGrade`, `ScheduleSeat` |
| FK 컬럼명 | 참조 대상을 단수로 | `member_id`, `ticket_grade_id` |
| 시간 컬럼 | `_at` 접미사 | `created_at`, `expires_at` |
| 비즈니스 식별자 | `_no` 접미사 | `reservation_no` |

```java
// ✅ 테이블은 복수, 클래스는 단수
@Entity
@Table(name = "ticket_grades")
public class TicketGrade { ... }
```

## 컬럼 타입

| 데이터 | 타입 | 이유 |
|---|---|---|
| 금액 | `numeric(12,0)` + `BigDecimal`(`precision=12, scale=0`) | `float`/`double`은 이진 부동소수점 오차 발생. PostgreSQL `money`는 `lc_monetary` 로케일에 좌우돼 비권장. 원화는 소수 단위가 없지만 할인율 계산·외화 확장 대비 |
| Enum | `varchar` + `CHECK` 제약, `@Enumerated(EnumType.STRING)` | ordinal 저장은 순서 변경 시 데이터 깨짐 |
| 시간 | `timestamptz` + `Instant` | DB가 UTC로 저장·자동 변환해 서버/DB 타임존 설정에 의존하지 않는다. `timestamp`(타임존 없음)는 운영(Docker, 보통 UTC)과 개발 환경이 달라지면 최대 9시간 오차가 난다 |
| PK | `bigint GENERATED BY DEFAULT AS IDENTITY` | 레거시 `bigserial` 대신 PostgreSQL 10+ 권장 방식 |
| 대소문자 무시 유니크 (이메일 등) | `UNIQUE(lower(column))` | 저장 전 애플리케이션에서도 소문자로 정규화 |
| 생성/수정 시각 | 전 테이블에 `created_at`/`updated_at` | `BaseTimeEntity` + JPA Auditing으로 공통화 |

```sql
-- ❌
amount float

-- ✅
amount numeric(12,0) NOT NULL CHECK (amount >= 0)
```

## 제약·인덱스 패턴

- **복합 UNIQUE**: 두 컬럼 조합이 유일해야 할 때 (`UNIQUE(schedule_id, grade)`)
- **범위/순서 CHECK**: `CHECK(0 <= remaining_quantity AND remaining_quantity <= total_quantity)`
- **부분 인덱스**: 특정 상태만 자주 조회할 때 (`CREATE INDEX ... WHERE status = 'PENDING'`)
- **내림차순 인덱스**: 최신순 목록 조회에 사용 (`idx(member_id, created_at DESC)`)
- **의도적 비정규화는 반드시 문서화**: 조회 편의를 위해 FK를 중복시켰다면 그 이유를 ERD.md와 코드 주석에 남긴다
- **복합 FK 가드**: 중복된 두 참조 경로(예: A가 B를 거쳐 C를 참조하면서 동시에 C를 직접도 참조)가 서로 어긋나지 않게 하려면, 부모 쪽에 `UNIQUE(id, 참조컬럼)`을 걸고 자식 쪽에서 그 두 컬럼을 묶어 복합 FK로 참조한다. 애플리케이션 로직으로만 일치를 보장하지 않는다
- **한국어 COMMENT**: 모든 테이블·컬럼에 `COMMENT ON TABLE`/`COMMENT ON COLUMN`으로 한국어 설명을 단다. 문구는 `docs/ERD.md`의 COMMENT 블록을 그대로 쓴다(새로 설계할 때도 ERD.md에 먼저 작성).

## 동시성 패턴

재고·잔여 수량처럼 여러 요청이 동시에 갱신하는 컬럼에는 아래 패턴을 순서대로 검토한다(자세한 도입 시점은 `docs/ROADMAP.md` Phase 5 참조).

1. **조건부 UPDATE** (기본으로 채택): 현재 상태를 WHERE 절에 포함해 원자적으로 갱신하고, 영향받은 행 수로 성공 여부를 판단한다.
   ```sql
   UPDATE ticket_grades SET remaining_quantity = remaining_quantity - :qty
   WHERE id = :id AND remaining_quantity >= :qty;
   -- affected rows == 0 이면 재고 부족으로 처리
   ```
2. **낙관적 락**: `version` 컬럼을 추가하고 충돌 시 재시도. 충돌이 드물 때 적합.
3. **비관적 락**: `SELECT ... FOR UPDATE`. 충돌이 잦고 확실한 직렬화가 필요할 때만.
4. **분산 락(Redis)**: DB 락으로 부족한 경우(다중 DB 인스턴스 등)에만 마지막 수단으로 검토한다.

여러 행을 한 번에 잠글 때는 **ID를 정렬해서 `IN` 절에 넣어** 데드락을 방지한다.

```sql
UPDATE schedule_seats SET status = 'HELD', reservation_id = :reservationId
WHERE id IN (:sortedSeatIds) AND status = 'AVAILABLE';
```
