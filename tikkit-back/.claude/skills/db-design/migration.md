# 마이그레이션 규칙 (Flyway)

## 버전 규칙

- 스키마 변경: `V{n}__description.sql` (예: `V4__create_seat_tables.sql`)
- 시드 데이터: `V{n}_{m}__seed_description.sql` (예: `V1_1__seed_dev_data.sql`) — 메인 버전 시퀀스(`V1`, `V2`, ...)와 분리해, 버전 이력만 보면 스키마 변화가 바로 보이게 한다.
- 시드는 `spring.flyway.locations`로 dev 프로필에서만 로드한다. 테스트·운영 DB에는 절대 섞이지 않아야 한다.
- 마이그레이션 파일명은 실제 테이블명(복수형)을 기준으로 짓는다: `V3__add_version_to_ticket_grades.sql` (❌ `..._ticket_grade.sql`).
- `ddl-auto`는 `validate`로 고정한다. Hibernate가 스키마를 암묵적으로 바꾸게 두지 않는다.

## 무중단 스키마 변경: expand → backfill → contract

기존 테이블 구조를 바꿔야 할 때(컬럼 제거, 모델 전환 등) 한 마이그레이션에 몰아넣지 않는다. 배포 도중 애플리케이션이 예전 스키마를 기대하는 순간이 있으면 요청이 실패하기 때문이다.

1. **Expand**: 새 테이블/컬럼을 추가만 한다. 기존 구조는 그대로 둬서 이전 버전의 애플리케이션도 계속 동작한다.
2. **Backfill**: 기존 데이터를 새 구조로 옮긴다. 반드시 검증 쿼리로 정합성을 확인한다(예: 옮긴 후 합계·건수가 이전과 일치하는지).
3. **Contract**: 애플리케이션이 새 구조만 사용하도록 배포된 뒤에, 이전 컬럼/테이블을 제거한다.

TIKKIT의 지정석 전환(V4~V6, `docs/ERD.md` 2절)이 이 패턴의 실제 예시다(`venues`는 처음부터 V1에 있으므로 여기 포함되지 않는다):
- V4: `seats`/`schedule_seats`/`reservation_seats` 테이블 생성 (expand)
- V5: 기존 예약 데이터를 좌석에 배정, 검증 (backfill)
- V6: `ticket_grades`의 수량 컬럼 제거 (contract)

## COMMENT 예시

`CREATE TABLE` 바로 뒤에 한국어 `COMMENT`를 붙인다. 문구는 `docs/ERD.md`의 COMMENT 블록을 그대로 쓴다.

```sql
CREATE TABLE members (
    id      bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email   varchar(255) NOT NULL,
    ...
);
COMMENT ON TABLE members IS '회원 정보';
COMMENT ON COLUMN members.email IS '로그인에 사용하는 이메일(로그인 ID), 대소문자 구분 없이 유일';
```

## 체크리스트

- [ ] 마이그레이션이 하나의 논리적 변경만 담고 있는가 (여러 목적을 한 파일에 섞지 않는다)
- [ ] 기존 데이터가 있는 컬럼 추가 시 `NOT NULL`이면 `DEFAULT`를 함께 지정했는가
- [ ] 대용량 테이블에 인덱스를 추가할 때 락 영향을 고려했는가
- [ ] `docs/ERD.md`의 "마이그레이션 이력" 표에 새 버전을 추가했는가
- [ ] backfill 단계라면 검증 테스트(건수/합계 일치)를 작성했는가
- [ ] 새/변경 테이블·컬럼에 한국어 `COMMENT ON`을 추가했는가
