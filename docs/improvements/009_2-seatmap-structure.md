## 1. 왜 만들었나

009_1이 `@import` 한 줄로 전송량 76.8%를 줄이면서 **전송량의 주인이 바뀌었다.** 폰트 비중이
88% → 53.8%로 내려가고 Script가 8.3% → 35.7%로 올라왔다. 그 번들 분석이 남긴 1순위가
`@base-ui/react` 34,562B였다.

그리고 009_1은 자기가 안 다룬 것을 분명히 적어뒀다 — 좌석맵 Suspense 분리, 좌석맵 응답 축소,
`cookies()` 분리는 **근거가 다르다**는 이유로 Task 030_2로 떼어냈다. 좌석맵 문서 전송이
32.9KB뿐이라 반으로 줄여도 16KB이고, 그 작업들의 근거는 전송량이 아니라 확장성이다.

ROADMAP도 Task 030_2 제목 옆에 그 말을 박아뒀다 — **"근거가 전송량이 아니라 확장성이다"**.

그래서 이 Task의 첫 결정은 "무엇을 재야 확장성을 말할 수 있는가"였다. 답은 **기울기**이고,
기울기는 한 점에서 말할 수 없다. 2,000석짜리 시드 하나로는 "지금 몇 KB 줄었다"밖에 못 쓴다.
그래서 **10,000석 시드를 새로 만드는 것부터 시작했다.**

## 2. 측정 환경

009_1 2절과 같다 — `docker-compose.prod.yml` 전체 스택(nginx + BE 2대 + postgres + redis),
`--profile monitoring` 없이, 측정 대상은 `http://localhost`(nginx 80번) 하나,
Lighthouse 호스트 CLI `--preset=desktop --only-categories=performance`, `CACHE_TYPE=none`.

### 2.1 군을 넷으로 나눴다

| 군 | 내용 |
|---|---|
| **before** | main 기준 (rect 좌석 / dynamic subset 폰트 / base-ui 버튼 / 분리 없음) |
| **all5** | 항목 1·2·3·4·5 전부 (단일 폰트 포함) |
| **items123** | 폰트만 되돌린 군. 귀속을 가르려고 따로 쟀다 |
| **final** | items123 + 자리표시자 CLS 수정 = 출하 상태 |

`items123`을 따로 잰 것이 이 문서의 수치를 전부 바꿨다. 5개를 한 번에 적용하고 총합만 보면
"path 합치기가 Layout을 79% 줄였다"로 적게 되는데, **그건 폰트 몫이었다**(6.4절).

### 2.2 "총합만 측정"이 이 경우에 성립한 이유

항목마다 전용 지표의 축이 거의 겹치지 않아서, 한 번에 적용해도 각자 귀속된다.

| 항목 | 전용 지표 |
|---|---|
| 1 base-ui 제거 | 스크립트 청크 바이트 (결정론적) |
| 2 Suspense 분리 | 스트림 마커 — 본문 텍스트 도착 시각 |
| 3 path 합치기 | DOM 노드 · JS heap · 무스로틀 TBT |
| 4 `getMe()` 격리 | TTFB · 빌드 라우트 표 |
| 5 단일 폰트 | 폰트 요청 수 · 폰트 바이트 |

귀속이 안 되는 건 FCP·LCP·CLS·점수 같은 **종합 지표**뿐이다. 그래서 그 넷의 귀속이 필요해질
때마다 군을 하나씩 더 쟀다(`items123`, `final`).

### 2.3 before를 다시 쟀다 — 세션을 건너서도 맞았다

009_1 표를 before로 쓰지 않고 같은 세션에서 다시 쟀다. 교차 확인이 됐다 —
다시 잰 홈 before가 FCP **615ms** / 전송 **536,341B**인데 009_1의 after는
616ms / 536,216B였다. 상세도 535ms vs 536ms. **다른 세션인데 0.2% 안에서 맞았다.**
층② 응답도 247,885B로 009_1의 gzip 실험 때와 바이트까지 같다.

### 2.4 대형 시드 `01c-large-venue.sql` (신규)

좌석 10,000석. 등급 비율(VIP:R:S:A = 1:2:3:4)을 `01b`와 같게 둬서 선택 가능 좌석 수도
같은 비율로 늘어나게 했다 — 안 그러면 "좌석당" 환산값을 두 군 사이에서 비교할 수 없다.

100석/열로 둔 것은 V5의 "1,000석 초과면 40석/열" 규칙에서 **의도적으로 벗어난 것**이다.
40석/열이면 250열이 되어 배치도가 폭 40 × 높이 250의 극단적 세로 비율이 되고, 좌석 대부분이
화면 밖으로 밀려 페인트 비용이 과소 측정된다. 100 × 100이면 2,000석군(40 × 50)과 종횡비가
0.8 → 1.0으로 가깝게 남는다.

`schedule_seats.id`는 양 군 모두 8자리를 유지했다(최대 12,052,894). 009_1 3.8절이 "바이트는
같은 자릿수 구간에서만 비교할 수 있다"를 남겼기 때문에 매 교체마다 확인했다.

### 2.5 회차와 수렴 판정

009_1과 같다 — 워밍업 `curl` 20회, 홈 4회 / 상세 3회 / 좌석맵 6회, 산포 `(max-min)/중앙값`이
20%를 넘으면 **판단 불가** 표시, 회차마다 문서 `resourceSize`로 무결성 검사.

여기에 **무스로틀 군 6회**를 추가했다(`LH_EXTRA_FLAGS=--throttling-method=provided`).
원래 목적은 009_1이 "판단 불가"로 남긴 좌석맵 FCP 이중분포가 Lantern 시뮬레이션 산물인지
보는 것이었는데, 결과는 가설과 반대였고(3.6절) 대신 다른 것을 건졌다(3.3절).

## 3. 핵심 발견

### 3.1 같은 변경이 2,000석에서는 회귀, 10,000석에서는 개선이다

정적 좌석을 등급별 `<path>`로 합치는 변경의 효과가 좌석 수에 따라 **부호가 바뀐다.**

| 지표 (하이드레이션 직후) | 2,000석 before → final | 10,000석 before → final |
|---|---|---|
| DOM 노드 | 2,245 → 1,053 (**-53.1%**) | 10,245 → 4,253 (**-58.5%**) |
| JS heap | 4,753.62 → 4,476.99KB (-5.8%) | 8,233.64 → 7,254.11KB (**-11.9%**) |
| **RecalcStyle** | 18.71 → **31.59ms (+68.8%)** | 71.84 → **29.20ms (-59.4%)** |
| Layout | 35.27 → 41.42ms (+17.4%) | 42.22 → 34.24ms (-18.9%) |
| 무스로틀 TBT | 0 → 0 | **53 → 0ms** |

2,000석만 보면 **RecalcStyle +68.8%, Layout +17.4%짜리 회귀**다. 거기서 멈췄으면 기각했다.
10,000석에서 방향이 뒤집힌다 — 정적 좌석 6,000개를 노드 6,000개가 아니라 `<path>` 3개로
만들면 스타일 재계산 대상이 그만큼 줄어든다.

교차점이 어디인지는 재지 않았다. 두 점만 있어서 "2,000과 10,000 사이"까지만 말할 수 있다.

### 3.2 이 변경은 전송량 레버가 아니다 — 그게 정상이다

| | 2,000석 | 10,000석 |
|---|---|---|
| 문서 바이트 | 677,153 → 667,342 (**-1.4%**) | 3,245,812 → 3,196,065 (**-1.5%**) |

좌석당으로 보면 path 명령이 84자, 기존 rect 마크업이 86자다. 클래스가 좌석마다 붙어 있던 걸
그룹으로 올린 몫까지 합쳐 좌석당 8바이트쯤 벌고, 10,000석에서 총 49.7KB다. 전체의 1.5%다.

**바이트로 정당화하려 했다면 "요소 6,000개를 3개로 줄였는데 50KB 벌었다"는 문장이 됐을 것이다.**
ROADMAP이 근거를 미리 "전송량이 아니라 확장성"으로 못박아 둔 게 여기서 값을 했다.

### 3.3 Lantern 스로틀이 하이드레이션 비용을 가리고 있었다

10,000석 좌석맵 TBT:

| | 스로틀 (desktop preset) | 무스로틀 |
|---|---|---|
| before | 1ms (산포 300%) | **53ms** (45~62) |
| final | 0ms | **0ms** (6/6) |

스로틀 켠 쪽만 봤으면 "TBT는 원래 0이었고 안 변했다"로 끝났다. 선택 불가 좌석 6,000개를
DOM 노드 6,000개로 만드는 하이드레이션이 메인 스레드를 53ms 잡고 있었고, 그게 사라진 것이
이 Task에서 **체감에 가장 가까운 개선**이다.

무스로틀 군은 원래 다른 목적(FCP 이중분포 확인)으로 넣은 보조 실험이었다. 목적은 실패했고
(3.6절) 대신 이걸 건졌다.

### 3.4 Suspense로 쪼개면 본문이 좌석을 안 기다린다 — 그 이득이 좌석 수에 안 묶인다

좌석 조회를 `Suspense`로 분리한 뒤 HTML 스트림을 직접 읽어 마커별 도착 시각을 쟀다.

| 간격 | 2,000석 before → final | 10,000석 before → final |
|---|---|---|
| 첫 바이트 | 6.55 → 6.6ms | 6.93 → 6.8ms |
| **본문 h1 - 첫 바이트** | 17.41 → **4.44ms** | 58.2 → **6.92ms** |
| 첫 좌석 - 본문 h1 | 10.63 → 19.82ms | 56.21 → 106.43ms |

before에서 그 간격은 **좌석 수에 비례해 커졌다**(17.41 → 58.2ms). final은 좌석 수와 무관하게
5~7ms에서 평탄하다. **좌석 수에 비례하던 비용을 상수로 만든 것**이고, 이 Task에서 "확장성"을
가장 곧게 보여주는 수치다.

#### ROADMAP의 전제 하나가 틀렸다

ROADMAP은 "`loading.tsx`만 있어 셋이 다 끝날 때까지 백지"라고 적었다. **틀렸다.**
`loading.tsx`가 그 자체로 Suspense 경계라서 셸은 원래도 먼저 나간다 — 측정하면 헤더 로고와
자리표시자가 **첫 바이트와 같은 청크(6.55ms)** 에 도착한다.

이 프로젝트는 이미 그걸 알고 있었다. `performances/[id]/page.tsx:15-20` 주석이
"같은 세그먼트에 loading.tsx가 있어 스트리밍이 이미 시작된 뒤라 notFound()를 불러도 상태
코드는 200으로 남는다(soft 404)"라고 적어뒀다. 같은 사실의 다른 면이다.

따라서 ROADMAP이 경고한 "`redirect`/`notFound` 위치를 같이 봐야 한다"도 **절반은 이미
해소돼 있었다.** 404는 이번 변경 전에도 soft였고, 더 쪼개도 상태 코드가 나빠지지 않는다.

#### 셋으로는 못 쪼갠다

`seats/page.tsx`의 검증 순서가 분할선을 정한다 — `notFound()`는 공연이, `redirect()`는 등급이
필요하고 **좌석은 둘 중 어디에도 안 쓰인다.** 그래서 2+1이 유일한 분할이다. 셋으로 쪼개면
잘못된 `gradeId`로 들어온 사용자가 좌석맵 셸을 본 뒤 상세로 튕기는 UX 변경이 된다.

#### 함정: 아무도 await하지 않는 promise

좌석 조회를 검증보다 먼저 띄우면 `redirect()`가 throw될 때 그 promise를 아무도 await하지 않아
**unhandled rejection**이 된다. 거부를 흡수하는 noop 핸들러를 먼저 붙이고 원본을 자식에게 넘겼다.
검증 뒤로 fetch를 미루는 대안은 좌석 조회가 왕복 두 번만큼 늦게 출발한다.

### 3.5 Suspense 분리는 공짜가 아니었다 — CLS가 0.0278에서 0.1996으로 뛰었다

분리한 뒤 좌석맵 Lighthouse 점수가 **100 → 90**으로 떨어졌다. CLS가 6회 중 5회에서
**0.1996**이었다(구글 기준 0.1을 넘는다).

폰트 탓이 아니라는 것을 `items123` 군으로 확인했다 — 폰트를 되돌려도 5/6이 0.1996이다.
(오히려 단일 폰트가 발생 빈도를 5/6 → 2/6으로 **줄였다.** 한 번에 도착해 레이아웃이 한 번만
정착하기 때문으로 보인다.)

원인은 **푸터**다. 실측하면 좌석 영역은 300px 지점에서 시작해 1,114px 높이로 그려지고 푸터는
1,176px에 온다(2,000석, 1350×940 뷰포트). 자리표시자가 28rem(448px)이면 푸터가 약 800px —
**화면 안에 보인다.** 좌석이 도착하면 푸터가 +376px 밀리고, 376/940 = 거리 비율 0.4에 영향
영역을 곱하면 CLS 0.2가 된다. 측정값 0.1996과 맞는다.

고치는 방향을 "실제 좌석맵 높이를 맞춘다"로 잡지 않았다. 공연장마다 다르고 서버는 좌석을 받기
전에 그 높이를 모른다. 대신 **두 상태 모두에서 푸터가 접힘선 아래에 있게** 만들었다 —
화면 밖에서 일어나는 시프트는 CLS에 잡히지 않는다. `min-h-[calc(100vh-12rem)]`이면
940px 뷰포트에서 748px(바닥 1,048px), 768px에서 576px(바닥 876px), 1200px에서 1,008px이라
어느 쪽에서도 푸터가 화면 밖에 머문다.

| | before | 분리 후 | 자리표시자 수정 후 |
|---|---|---|---|
| CLS (2,000석) | 0.0278 | 0.1996 (5/6) | **0.0005** |
| 점수 | 100 | 90 (5/6) | **100 (6/6)** |
| CLS (10,000석) | 0.0278 | 0.199 (6/6) | **0.0011** |

before보다도 98% 낮다. **스트리밍을 쪼개는 변경은 자리표시자 높이를 같이 보지 않으면
지표를 망가뜨린다** — 이 Task에서 가장 비싸게 배운 것이다.

### 3.6 좌석맵 FCP 이중분포는 Lantern 산물이 아니었다 — 그리고 이번엔 아예 안 나왔다

009_1이 "판단 불가"로 남긴 좌석맵 FCP 산포 25.2%가 **이번 세션에서는 0.6%로 수렴했다.**
before 6회가 490~493ms 한 덩어리였고 370ms 모드가 안 나왔다. 그 산포는 009_1 세션 한정이었다.

계획에 적은 가설은 "무스로틀에서 빠른 모드가 사라지면 Lantern 시뮬레이션 산물로 확정"이었는데
**결과는 반대**였다. 무스로틀 쪽이 산포 45.9%로 두 모드가 더 선명하고, **CLS가 모드를 가른다** —
FCP 92~102ms 회차는 CLS 0.0277(대체 글꼴로 먼저 그리고 폰트 도착 후 시프트), FCP 133~137ms
회차는 CLS 0.0005(폰트가 먼저 와서 시프트 없음).

즉 두 모드는 시뮬레이션 산물이 아니라 **실제 폰트 경쟁 레이스**이고, Lantern은 결정론적
모델이라 그걸 평균화해 가린다. 009_1 3.3절의 해석("좌석 rect가 폰트 경쟁을 피한 회차")을
뒷받침하는 직접 증거다.

> [!warning] 확인 필요
> 단일 폰트로 바꾸면 그 레이스가 사라져야 하는데, 10,000석에서는 산포가 55.2% → 17.2%로
> 풀렸고 **2,000석에서는 45.9% → 43.4%로 안 풀렸다.** 폰트 경쟁만으로 설명되지 않는다.
> 미규명으로 남긴다.

### 3.7 009_1의 번들 귀속을 정정한다 — 4.2배 과대평가였다

009_1은 홈 스크립트 191,785B 중 `@base-ui/react`를 **34,562B(18%)** 로 귀속하고 "다음 Task
1순위"로 지목했다. 실제로 제거해 보니:

| | before | final |
|---|---|---|
| 홈 Script 전송 | 13개 191,777B | 12개 **183,557B** |
| 홈 Script 디코드 | 612,074B | **590,916B** |

전송 **-8,220B**, 디코드 -21,158B, 청크 -1개다. 귀속값의 **4.2분의 1**이다.

009_1 자신이 "번들 귀속이 청크 문자열 grep이라 비중은 근사다 — 한 청크에 여러 라이브러리가
섞이면 첫 마커로 전부 귀속"이라고 경고했었다. 그 오차의 배수가 이번에 나왔다.

치환 자체는 깨끗했다. `@base-ui/react`를 쓰는 곳이 `button.tsx`와 `alert-dialog.tsx` 둘뿐이고,
alert-dialog는 `cancel-reservation-button.tsx` 하나만 소비한다 — 즉 의존성이 사라지는 게 아니라
**예매 취소 화면에만 남는다.** 홈·상세·좌석맵 청크에서는 `base-ui` 문자열이 0이다.

한 가지만 조심하면 됐다. base-ui의 `useButton`이 네이티브 버튼일 때 `type: 'button'`을
넣어준다(`useButton.js:183`). HTML 기본값은 `submit`이라, 안 옮기면 폼 안에서 `type`을 안 적은
버튼의 클릭이 폼 제출로 바뀐다.

### 3.8 단일 폰트 서브셋은 기각했다 — FCP를 66% 줄였는데도

미리 적어둔 수용 기준이 "폰트 요청 11 → 1 + 폰트 바이트가 205~289KB보다 작고 FCP 회귀 없음"
이었다. 만든 파일이 374,336B로 그 기준을 넘는다. 사후 합리화를 막으려고 측정 전에 적어둔 자리다.

| 지표 | before | items123 | all5 | 폰트 몫 |
|---|---|---|---|---|
| 홈 FCP | 615ms (0.6%) | 617ms (0.4%) | **207ms (40.4%)** | **-410ms** |
| 홈 LCP | 743ms | 744ms | 807ms | +63ms |
| 홈 전송 | 536,341B | 528,458B | 599,501B | **+71,043B** |
| 상세 FCP | 535ms (0.4%) | 535ms (0.5%) | **207ms (39.5%)** | -328ms |
| 상세 전송 | 447,551B | 440,679B | 588,812B | **+148,133B** |

> [!warning] 정정 (Task 039_1)
> **이 표가 처음에는 산포를 떼고 207ms만 적고 있었다.** 괄호는 6.3절에서 되돌린 것이다.
> `all5`의 FCP 산포는 **40.4% / 39.5%** 로 이 하네스의 "판단 불가" 기준(20%)을 넘는다.
> before·items123이 0.4~0.6%인 것과 신뢰도가 다르다.
>
> 그래서 아래 "FCP가 66% 내려간 것은 진짜다"는 **과하다.** 내려간 **방향**은 맞지만
> 크기는 판정 구간 밖이라 특정할 수 없다. 이 207ms를 다음 Task의 재판정 목표로 쓰면
> 산포 40.4% 안의 점을 과녁으로 삼는 것이 되므로, 039_1은 **A군 대비 상대 변화**로
> 기준을 잡고 207ms는 방향 참조로만 쓴다. 교훈 8의 반대 실수 — 산포를 모르고
> **기준선을** 채택하는 것 — 를 막는 자리다.
>
> **홈 LCP가 743 → 807ms로 +63ms 악화된 것도 이 절이 설명하지 않았다.** "요청 수 줄서기가
> CSS·JS·문서를 뒤로 밀고 있었다"가 전부라면 LCP도 같이 내려가야 한다. 039_1은 FCP만
> 보지 않고 LCP를 같이 보고, 이 불일치가 풀리는지로 아래 추론을 검증한다.

FCP가 내려간 **방향**은 진짜다(크기는 위 정정 참조). 기각의 이유는 **그 이득이 어디서 왔는가**다 —
바이트가 아니라 **요청 수**에서 왔다. nginx가 `listen 80`만 선언해(`nginx.conf:111` — 이 절이
처음 적은 `:87`은 Task 039가 `max_fails` 주석을 넣으며 밀렸다) HTTP/1.1이고, 커넥션 6개 제한
때문에 폰트 조각 11개가 2라운드로 줄을 선다. 그 줄서기가 CSS·JS·문서를 뒤로 밀고 있었다.

**다만 이 추론은 교락돼 있다.** 요청 수(11 → 1)와 바이트(홈 +71,043B)가 **동시에** 움직였고,
요청 수를 단독 변수로 분리한 실험이 이 Task에는 없다. "바이트가 아니다"의 직접 근거는
**바이트가 늘었는데 FCP가 내려갔다**는 것 하나뿐이고, 커넥션 6개 줄서기는 측정이 아니라
`listen 80` 선언과 브라우저 동작에서 연역한 것이다. 요청 수를 단독으로 재는 것은 HTTP/2를
켜는 쪽이고, 그게 039_1이다.

그렇다면 올바른 레버는 374KB 폰트가 아니라 **HTTP/2**다. HTTP/2면 작은 파일 11개를 그대로
두고도 경쟁이 사라지고 바이트는 205~289KB로 유지된다. 지금 못 켜는 이유는 TLS가 없어서이고
그건 Task 034에 달려 있다. **재판단 조건: Task 034에서 HTTP/2를 켠 뒤 같은 비교를 다시 한다.**

> [!note] 정정 (Task 039_1)
> **"Task 034에 달려 있다"가 틀렸다.** 필요한 것은 클라우드 배포가 아니라 TLS 종단 하나이고,
> 그건 로컬 self-signed로 세울 수 있다. 평문 h2c로는 안 된다 — 브라우저가 cleartext HTTP/2를
> 지원하지 않아서 브라우저로 재려면 TLS가 반드시 끼어야 하는데, **그 TLS가 로컬에서도 선다.**
> 그래서 이 항목은 034를 기다리지 않고 **Task 039_1**에서 닫았다(016 문서).

> [!note] 재측정 결과 (Task 039_1 — 016 문서 4.3·4.4절)
> **결론은 맞았고 근거 수치는 과장이었다.**
>
> | | 이 절이 적은 것 | 039_1 재측정 |
> |---|---|---|
> | 단일 서브셋 효과 (평문 h1, 홈 FCP) | 615 → 207ms = **-66.3%**, 산포 40.4% | 616 → **570ms = -7.5%**, 산포 0.4% (6회) |
> | 올바른 레버가 HTTP/2인가 | 추론 | **맞다.** TLS h1 690 → h2 **482ms (-30.1%)** |
> | 단일 서브셋 vs HTTP/2 | 비교 안 함 | HTTP/2가 **4.5배** 크다 |
> | HTTP/2 위의 단일 서브셋 | "바이트는 205~289KB로 유지된다" | **482 → 562ms = +16.6% 손해로 역전** |
>
> **207ms가 재현되지 않았다.** 같은 조건을 6회 재니 570ms로 0.4%에 수렴한다. 환경 변화 탓이
> 아니다 — 같은 세션의 before가 **616ms로 이 절의 615ms와 1ms 안에서 맞았고** 폰트 바이트도
> 289,305B로 009_1과 동일하다. 기준선은 재현됐고 단일 서브셋 군만 재현되지 않았다.
> **산포 40.4%가 무슨 뜻이었는지 이것으로 설명된다: 207ms는 그 산포 안의 이상치였다.**
>
> 그리고 이 절이 설명하지 못한 LCP +63ms도 풀렸다. HTTP/2는 LCP를 **852 → 642ms(-24.6%)** 로
> 내린다. 같은 "요청 수 감소"인데 방향이 반대인 이유는 **바이트**다 — 단일 서브셋은 요청을
> 줄이면서 +71KB를 늘렸고, HTTP/2는 바이트를 전혀 건드리지 않는다(전송 -0.95%).
>
> 이 절이 적은 예측 하나는 소수점까지 맞았다. "상세·좌석맵은 8조각 205,472B라 **+169,165B**"
> 였고 재측정의 상세 폰트 증가가 **+169,678B**다.
>
> **그래서 단일 폰트 서브셋은 영구 기각이다.** 재판단 조건이 닫혔다.

같이 나온 비용 둘:

- **페이지마다 손해가 다르다.** 홈은 11조각 289,305B를 받으니 +85,332B, 상세·좌석맵은 8조각
  205,472B라 **+169,165B**다. 글자 다양성이 적은 페이지일수록 단일 파일이 불리하다
- **서브셋 2,620자 밖의 글자는 대체 글꼴로 떨어진다.** 공연 제목이나 회원 이름에 빈도가 낮은
  글자나 한자가 들어오면 그 글자만 시스템 글꼴로 그려진다. dynamic subset에는 없던 문제이고,
  사용자 입력 텍스트를 다루는 서비스에서 성능 거래로만 볼 수 없다

만드는 과정에서 알게 된 것도 적어둔다. KS X 1001 2,350자 표를 재현하지 않고 009_1 3.4절의
발견(조각이 **글자 사용 빈도 순**이고 번호가 클수록 흔하다)을 써서 상위 24조각의
`unicode-range`를 합집합으로 모았다 — 2,620자. 단일 파일 374,336B는 같은 글자를 조각으로
받을 때(605,856B)보다 **-38.2%** 다. 파일별 중복 테이블이 한 번만 들어가는 몫이 그만큼이다.

### 3.9 `getMe()` 격리는 구조만 남기고 수치는 0으로 기록한다

ROADMAP은 "`(main)/layout.tsx`가 매 요청 `getMe()`를 호출해서 전 세그먼트가 동적"이라고 적었다.
`layout.tsx`에는 데이터 조회가 없다. 부르는 건 `header.tsx`의 `async function Header()`다.

문제는 Header 전체가 async였다는 것이다. `await getMe()`에 실제로 의존하는 건 로그인 상태 한
조각인데 로고·nav·테마 토글까지 같이 기다렸다. 그 조각만 떼어 `Suspense`로 감쌌다.

수치는 안 움직였다. TTFB 중앙값(12회):

| | 홈 | 상세 | 좌석맵 |
|---|---|---|---|
| 2,000석 before → final | 6.52 → 7.24ms | 7.28 → 7.32ms | 7.79 → 8.06ms |
| 10,000석 before → final | 6.01 → 6.97ms | 6.14 → 7.54ms | 7.85 → 8.06ms |

세 군 전부 **개선이 없고 미세하게 나쁘다.** 이유는 분명하다 —
`(main)/page.tsx:13`이 `export const dynamic = "force-dynamic"`을 선언해 뒀고 주석이
"목록은 요청마다 최신이어야 한다"고 적어뒀다. **홈은 Header를 격리해도 정적이 되지 않는다.**
`next build` 라우트 표도 before/after 모두 전 라우트가 `ƒ`(Dynamic)이다.

그래도 리팩터는 **남겼다.** `apiFetchRaw`에서 세션 주입을 떼어 공개/세션 두 진입점으로 나눈
것은 수치와 무관하게 값이 있다 — 호출부가 의도를 선언하게 만들어서, 새 API를 추가할 때
기본값이 한쪽으로 조용히 떨어져 인증이 깨지는 사고를 막는다. 그리고 `cacheComponents`를
나중에 켤 때의 선행 조건이기도 하다.

`revalidate`는 켜지 않았다. 근거를 코드 주석에 남겼다 — 목록은 `force-dynamic`이 "요청마다
최신"을 선언했고, 상세는 029가 이미 BE에서 TTL 60s로 캐시해서 FE에 60s를 더 얹으면 최악
지연이 두 배가 되는데 아끼는 것은 로컬 2~3ms 왕복뿐이다. 회차 등급·좌석은
`remainingQuantity`와 `status`가 실시간이라 영구히 캐시 대상이 아니다.

### 3.10 BE 좌석 응답 축소는 착수하지 않았다

계획이 "FE 전용 변경부터 측정 → 남은 몫을 보고 BE 축소 결정"이었고, 게이트에서 기각했다.

| 근거 | 수치 |
|---|---|
| FE 변경만으로 DOM·메모리 목표 달성 | DOM -58.5%, RecalcStyle -59.4%, heap -11.9%, 무스로틀 TBT 53 → 0 |
| 10,000석에서 깨진 지표 없음 | 점수 100, TBT 0, CLS 0.0011, FCP 327ms |
| 남은 체감 문제를 BE 축소가 못 고친다 | 클릭 commit 32.5ms는 **선택 가능 레이어** 몫이다 |

층②는 before와 동일하다(1,246,025B = 124.6B/좌석, `JSON.parse` 1,000석당 0.2912ms). BE를
한 줄도 안 건드렸으니 당연하고, 그 비용이 지금 병목이 아니라는 게 게이트의 결론이다.

**재판단 조건**: 좌석 수가 10,000석을 넘거나, 선택 오버레이 작업 후에도 ③층(인라인 RSC
10,000석에서 1,454KB)이 병목으로 남을 때.

- **`revalidate`/`cacheLife`** (3.9절) — 구조만 열고 켜지 않았다

## 5. 관문

### 5.1 `node -e "..."` 안의 템플릿 리터럴은 백슬래시를 두 번 깎는다

패치 스크립트를 `node -e "..."`로 돌리면서 정규식 `/\s+/`를 `\s+`로 적었는데 파일에는
`/s+/`가 들어갔다. **에러가 안 난다** — `split(/s+/)`는 "리터럴 s로 쪼개기"로 멀쩡히 동작하고
결과만 조용히 틀린다. 검증 없이는 못 잡는다.

겹따옴표 `node -e`는 셸이 `${...}`도 먹는다. 템플릿 리터럴이 들어간 패치 스크립트에서
`${API_BASE_URL}`이 빈 문자열로 치환돼 검색 문자열이 안 맞았다.

**파일은 따옴표 heredoc으로 직접 쓰면 이스케이프가 1단계라 안전하다.** 패치 스크립트를
경유해야 하면 백슬래시를 `String.fromCharCode(92)`로 만들거나 결과를 반드시 grep으로 확인한다.

### 5.2 `tail`로 파이프하면 Lighthouse 표가 사라진다

백그라운드 실행의 출력을 `| tail -25`로 줄였더니 회차별·중앙값 표가 잘리고 리소스 타입 표만
남았다. 원본 JSON(`.lighthouse/<label>/run-*.json`)에서 `audits`를 직접 읽어 복구했다.
**측정 출력은 파일로 받고 `tail`은 확인용으로만 쓴다.**

### 5.3 Docker Desktop은 `cmd /c start`로 안 뜬다

`cmd.exe /c start "" "Docker Desktop.exe"`가 성공을 반환하는데 프로세스가 안 떴다.
`powershell -Command "Start-Process ..."`로는 떴다.

### 5.4 009_1의 함정은 그대로다

frontend만 재빌드해도 `depends_on: backend1(healthy)` 때문에 backend1이 재생성되고 IP가 바뀌어
nginx가 502를 뱉는다. **변경마다 `restart nginx`가 필요하다.** 이번 Task에서 재빌드를 네 번
했고 네 번 다 필요했다.

### 5.5 Python이 없어서 서브셋 도구를 바꿨다

`pyftsubset`(fonttools)을 쓰려 했는데 이 환경의 `python`이 Windows 스토어 스텁이라
`python -V`가 "Python"만 출력한다. harfbuzz wasm 기반 `subset-font`(npm)로 바꿨다.
기각과 함께 의존성도 같이 지웠다.

## 7. 한계

- **교차점을 모른다.** RecalcStyle의 부호가 2,000석과 10,000석 사이 어딘가에서 바뀌는데 두
  점만 재서 그 지점을 특정할 수 없다
- **2,000석 FCP·LCP 회귀(+48 / +45ms)의 메커니즘을 규명하지 않았다.** path 1개에 서브패스
  1,200개를 래스터화하는 비용이 rect 1,200개보다 큰 것으로 보이지만 확인하지 않았다
- **10,000석 FCP가 2,000석보다 빠르다**(327 vs 540ms). 문서가 5배 큰데 첫 페인트가 이르다는
  건 직관에 반하는데 메커니즘을 확인하지 않았다. 추측을 적지 않고 미규명으로 둔다
- **무스로틀 FCP 이중분포가 단일 폰트로 10,000석에서는 풀리고 2,000석에서는 안 풀렸다**(3.6절)
- **heap을 "좌석당"으로 비교하면 틀린다.** 2,000석 2,433.9B/좌석, 10,000석 843.1B/좌석인데
  증분만 보면 8,000석 추가에 +3,480KB = 좌석당 약 435B이고 기저가 약 3,883KB다
- **모바일을 안 쟀다.** 009·009_1과 같은 한계다
- **재방문자를 안 쟀다.** Lighthouse는 항상 캐시 콜드다
- **자리표시자 높이가 뷰포트 기준 근사다.** 실제 좌석맵보다 짧은 공연장에서는 푸터가 위로
  올라오고, 그게 화면 안이면 다시 CLS가 생길 수 있다. 측정한 두 공연장에서는 둘 다 화면 밖이었다
- **BE 좌석 응답을 안 줄였다**(3.10절). 10,000석 인라인 RSC 1,454KB가 그대로 남아 있다
- **CLS 수정을 10,000석에서 6회만 쟀다.** 2,000석에서 이중분포였던 지표라 회차가 더 필요할 수 있다

## 재현 방법

```bash
# 0. 스택 기동 (monitoring 프로필은 끈다, CACHE_TYPE=none 확인)
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml restart nginx   # 재빌드마다 필요 (5.4절)
until curl -sf -o /dev/null http://localhost/healthz; do sleep 1; done

# 1. 시드 — 군을 바꿀 때마다 teardown부터. 01 / 01b / 01c는 공존 금지
PG="docker compose -f docker-compose.prod.yml exec -T postgres psql -U tikkit_user -d tikkit_db"
$PG -q -f - < load-test/sql/99-teardown.sql
$PG -f - < load-test/sql/01c-large-venue.sql        # 또는 01b-small-catalog.sql
$PG -f - < load-test/sql/02-bulk-schedule-seats.sql

# 2. 대상 id를 뽑는다 (시퀀스가 이어져서 매번 달라진다)
$PG -At -F'|' -c "SELECT p.id, s.id, tg.id
  FROM performances p JOIN venues v ON v.id = p.venue_id AND v.name = '[LOAD] 부하테스트 아레나'
  JOIN schedules s ON s.performance_id = p.id
  JOIN ticket_grades tg ON tg.schedule_id = s.id
  WHERE tg.grade = 'A';"

# 3. 워밍업 — TTFB가 평탄해질 때까지
cd tikkit-front
URL="http://localhost/performances/<P>/schedules/<S>/seats?gradeId=<G>&quantity=4"
for i in $(seq 1 20); do curl -s -o /dev/null "$URL"; done

# 4. perf 스펙 (payload-bytes / seat-interaction / stream-markers / dom-memory)
E2E_BASE_URL=http://localhost PERF_PERFORMANCE_ID=<P> PERF_SCHEDULE_ID=<S> PERF_GRADE_ID=<G> \
  npm run perf

# 5. JSON.parse 격리 측정
PB_BASE_URL=http://localhost PB_SCHEDULE_ID=<S> PB_RUNS=30 npm run parse-bench

# 6. Lighthouse — 스로틀 군과 무스로틀 군
LH_URL="$URL" LH_RUNS=6 LH_LABEL=seatmap npm run lh
LH_URL="$URL" LH_RUNS=6 LH_LABEL=seatmap-nothrottle \
  LH_EXTRA_FLAGS=--throttling-method=provided npm run lh

# 7. 출력은 파일로 받는다. tail로 파이프하면 표가 잘린다 (5.2절)
#    원본 JSON은 .lighthouse/<label>/run-*.json 에 남는다
```

귀속을 가르려면 군을 하나씩 더 잰다. 이 Task는 `items123`(폰트만 되돌림)과 `final`(자리표시자
수정 후)을 추가로 쟀고, **그 두 군이 없었으면 Layout·CLS·FCP를 전부 틀리게 귀속했을 것이다.**
