# 16. 로컬 TLS와 HTTP/2 재판정 (Task 039_1)

> **한 줄 결론**: HTTP/2가 홈 FCP를 **690 → 482ms(-30.1%)** 로 내렸고, 그 이득은 TLS 비용을
> 분리해서 봤을 때만 제대로 보인다(평문 대비로는 -21.8%로 깎여 보인다). **단일 폰트 서브셋은
> 영구 기각이다** — HTTP/2 위에서 부호가 뒤집혀 **+16.6% 손해**다. 그리고 009_2가 기각 근거로
> 적은 "-66.3%"는 **재현되지 않았다**. 같은 조건 6회로 재니 -7.5%고, 원래 수치는 산포 40.4%의
> "판단 불가" 구간이었다.

**1번은 이 Task의 판정 기준 자체를 바꿨다.**

## 1. 왜 지금 할 수 있었나 — "Task 034를 기다린다"가 틀렸다

009_2 §8과 ROADMAP이 이 항목을 "Task 034(클라우드 배포)에서 TLS가 붙으면"으로 넘겨 뒀다.
필요한 것은 클라우드가 아니라 **TLS 종단 하나**이고, 그건 로컬 self-signed로 선다.

평문 h2c로는 안 된다 — 009_1 §6이 "TLS가 없는 로컬에서는 `listen 80 http2;`가 필요하다"고
적었는데 **그 경로로는 브라우저 측정이 불가능하다.** 브라우저가 cleartext HTTP/2를 지원하지
않기 때문에 HTTP/2 이득을 브라우저로 재려면 TLS가 반드시 끼어야 하고, 그 TLS는 로컬에서도
세울 수 있다. 이것이 015가 "034를 기다린다고 적어 둔 여덟 항목 중 실제로 클라우드가 필요한
것은 셋뿐"으로 정리한 것의 세 번째 사례다(gzip·쿠키·HTTP/2).

## 2. 판정이 성립하는 근거를 착수 전에 확인했다

Lighthouse는 `--preset=desktop`에서 Lantern 시뮬레이터로 돈다. **그 시뮬레이터가 h2를 실제로
모델링한다**는 것을 코드에서 먼저 확인했다.

```js
// node_modules/@paulirish/trace_engine/models/trace/lantern/simulation/ConnectionPool.js
const CONNECTIONS_PER_ORIGIN = 6;                                            // :10
const isH2 = request.protocol === 'h2';                                      // :46
const minConnections = connections[0].isH2() ? 1 : CONNECTIONS_PER_ORIGIN;   // :55
```

두 가지가 여기서 정해졌다.

- **비교가 성립한다.** 009_2의 615ms도 같은 Lantern 수치였으므로 같은 자로 after를 재는 것이
  정당하다. 그리고 Lantern은 **바이트를 그대로 두고 커넥션 제한만 푸는** 구조라, HTTP/2는
  이 레포에서 **요청 수를 단독 변수로 재는 첫 실험**이 된다. §3.8의 추론은 요청 수와 바이트가
  같이 움직인 교락된 것이었다.
- **그게 동시에 함정이다.** 판정 전체가 `request.protocol === 'h2'` 한 줄에 달려 있어서, 그게
  `h2`로 안 찍히면 **경고 하나 없이 HTTP/1.1 모델로 계산된 수치가 나온다.** 지연·바이트·점수가
  전부 정상으로 보인다. 015가 두 번 밟은 그 모양이다(교훈 10).

### 판정 기준 (착수 전에 적었다)

| 항목 | 기준 |
|---|---|
| **프로토콜 무결성** | **선행 조건이다.** C군 전 회차가 100% `h2`가 아니면 그 군은 수치가 아니라 사고다. B군은 반대로 `h2`가 0%여야 한다 |
| HTTP/2 채택 | C군 홈 FCP가 A군보다 낮고, **그 차이가 B군(TLS만)으로 설명되지 않을 것** |
| 산포 | 홈·상세 FCP는 009·009_1·009_2가 일관되게 0.1~0.6%다. 20% 초과 군은 "판단 불가"로 적고 채택 근거로 쓰지 않는다 |
| LCP | 같이 본다(0절 정정 2). 내려가면 §3.8의 "요청 수" 추론이 보강된다 |
| 단일 서브셋 영구 기각 | C군 홈 FCP가 A군 대비 **-30% 이상**이면 기각 유지. **못 미치면 단일 서브셋을 다시 만들어 C군 위에서 A/B한다** |
| 기각 처리 | 코드째 지운다. 의존성도 같이 지운다(교훈 5) |

마지막 줄이 실제로 발동했다 — A군 대비 -21.8%로 -30%에 **못 미쳤다.** 사후에 "B군 대비로는
-30.1%니까 됐다"로 기준을 바꾸지 않고 D군을 만들었고, **그 D군이 이 Task의 결론을 만들었다.**

## 3. 만든 것

### 3.1 로컬 인증서 — `nginx/generate-local-cert.sh`

산출물은 커밋하지 않고(`.gitignore`) 스크립트만 추적한다. 기계마다 한 번 돌리면 된다.

**Windows 함정을 2단으로 밟았다.** `-subj "/CN=localhost"`를 쓰면 Git Bash의 MSYS가 `/CN=...`을
경로로 보고 `C:/Program Files/Git/CN=localhost`로 바꾼다. 그래서 `MSYS_NO_PATHCONV=1`을 붙이면
**`-keyout`/`-out` 경로 변환까지 같이 꺼져서** native openssl이 `/c/Users/...`를 못 열고
`No such file or directory`로 죽는다. 설정 파일(`-config`)로 가면 경로도 슬래시 인자도 없어서
둘을 동시에 비킨다.

> 같은 MSYS 함정을 이 Task에서 **세 번** 밟았다. 셋째는 k6 러너였다 — `/scripts/seatmap.js`가
> `C:/Program Files/Git/scripts/seatmap.js`로 바뀌어 종료코드 255가 났다. `run-group.sh:32`가
> "Git Bash면 `MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'`가 export돼 있다"를 **전제로 적어
> 두고 설정하지는 않는다.** 셸을 새로 열면 전제가 깨진다.

인증서는 `CA:TRUE` + `keyCertSign`으로 만든다. 서버 인증서로는 드문 조합인데, **자기 자신을
신뢰 앵커로 쓰려면** 필요하다(3.3절).

### 3.2 `nginx.conf` — 리스너가 둘이고 80을 지우지 않는다

```nginx
listen 80;
listen 443 ssl;
http2 on;                 # 1.25.1부터 `listen ... http2`는 deprecated다
ssl_certificate     /etc/nginx/certs/localhost-cert.pem;
ssl_certificate_key /etc/nginx/certs/localhost-key.pem;
ssl_protocols       TLSv1.2 TLSv1.3;
```

- **80을 남긴 이유: k6 하네스 전체가 평문으로 들어온다.** `load-test/k6/lib/config.js:6`이
  `BASE_URL || 'http://nginx'`이고 compose의 k6 서비스도 같다. 80을 지우거나 443으로
  리다이렉트하면 036·039가 쓴 포화 측정이 전부 죽는다. **이건 측정 장치의 구성이고 운영
  설정이 아니다** — 그 문장을 주석에 박았다.
- **HSTS를 넣지 않았다.** `localhost`에 HSTS를 심으면 브라우저가 그 호스트의 http 접근을
  **다른 포트·다른 로컬 프로젝트까지** 강제 업그레이드하고, 되돌리려면 브라우저 설정을
  손대야 한다. 측정을 위해 개발 기계에 되돌리기 어려운 상태를 남기지 않는다.
- **`ssl_session_cache`도 일부러 안 켰다.** Lighthouse는 회차마다 새 Chrome 프로필이라 세션
  재사용이 생기지 않는데, 켜 두면 나중에 수치를 볼 때 "재사용이 섞였나"를 의심해야 한다.
- `proxy_set_header X-Forwarded-Proto $scheme;`은 **수정이 필요 없었다.** 이미 있고 https에서
  자동으로 `https`가 된다.

### 3.3 하네스 — 프로토콜 집계가 이 Task의 영구 산출물이다

`scripts/lighthouse-runs.mjs` 수정 3건.

1. **`--chrome-flags`가 고정 문자열이었다.** self-signed로 재려면 `--ignore-certificate-errors`가
   필요한데 그 값은 `--chrome-flags` **안**에 들어가야 하고, `LH_EXTRA_FLAGS`는 공백으로
   쪼개므로 못 넘긴다. **그 파일이 L41~47에 이유를 적고 "바꿔야 하면 코드를 고치는 쪽이
   낫다"는 처방까지 남겨 뒀다.** 그 처방대로 `LH_CHROME_EXTRA`를 받아 문자열로 이어 붙인다.
2. **요청별 `protocol` 집계와 `LH_EXPECT_PROTOCOL` 검사.** `extract()`가 이미
   `audits["network-requests"].details.items`를 읽고 있어서 같은 자리에서 꺼낼 수 있었다.
   `LH_EXPECT_DOC_BYTES`가 문서 바이트로 하는 일을 프로토콜로 한다 — **기대와 다른 회차를
   집계에서 제외하고 사유를 찍는다.** 전부를 보는 이유는 "문서만 h2이고 정적 자원은 1.1"처럼
   반쯤 걸린 상태가 Lantern의 커넥션 모델을 섞어서 **어느 조건의 수치도 아닌 값**을 만들기
   때문이다. 폰트 표에도 조각별 프로토콜을 붙였다.
3. chrome 플래그를 실행 로그에 남긴다. 고정 문자열일 때는 찍을 이유가 없었는데 바뀔 수 있게
   된 뒤로는 측정 조건의 일부다.

`playwright.config.ts`에 `use.ignoreHTTPSErrors: true`를 넣었다.

**perf 스펙 하나가 그걸로 안 됐다 — 계획에 없던 세 번째 걸림돌이다.**
`e2e/perf/stream-markers.spec.ts`만 브라우저가 아니라 **Node 전역 fetch로** HTML 스트림을
읽는다(바이트 도착 시각을 재야 해서). `ignoreHTTPSErrors`는 브라우저 컨텍스트 옵션이라 안
걸리고, perf 5개 중 이 하나만 `self-signed certificate`로 떨어졌다.

```bash
NODE_EXTRA_CA_CERTS=./nginx/certs/localhost-cert.pem E2E_BASE_URL=https://localhost ... npm run perf
```

**`NODE_TLS_REJECT_UNAUTHORIZED=0`을 쓰지 않았다** — 프로세스 전역이라 다른 스펙의 검증까지
같이 끈다. 인증서를 신뢰 목록에 넣어서 **검증을 끄지 않고** 통과시키는 쪽을 골랐고, 그러려면
인증서가 자기 자신의 신뢰 앵커가 될 수 있어야 한다. `CA:FALSE`로 만들면 `NODE_EXTRA_CA_CERTS`에
넣어도 OpenSSL이 받아주지 않는다. 그래서 3.1절의 `CA:TRUE`다. 스펙 코드는 **한 줄도 안 바꿨고**
함정만 주석으로 남겼다.

### 3.4 세션 쿠키 `secure` — FE 한 군데

`lib/session.ts`에 환경변수 토글로 넣고 기본값은 `false`, compose의 frontend에 통로를 뚫었다.
BE는 건드리지 않았다(0절 정정 3).

## 4. 측정

### 4.1 조건

009_2 §2와 같다. prod 스택 전체(monitoring 프로필 끔), nginx 경유, `CACHE_TYPE=none`,
Lighthouse 13.5.0 `--preset=desktop --only-categories=performance`, 군마다 워밍업 `curl` 20회,
**홈 4회 / 상세 3회**. 브라우저 캐시는 항상 콜드다.

적용된 토글을 `docker exec env`로 읽어서 확인했다(교훈 10): BE 2대 모두
`CACHE_TYPE=none QUEUE_ENABLED=false SEATMAP_STRATEGY=local`. 좌석맵 전략은 홈·상세가 좌석맵을
조립하지 않으므로 이 측정에 걸리지 않는다.

| 군 | URL | nginx | 폰트 |
|---|---|---|---|
| **A** `h1-plain` | `http://localhost` | `listen 80` | dynamic subset |
| **B** `h1-tls` | `https://localhost` | 443 + `http2 off;` | dynamic subset |
| **C** `h2-tls` | `https://localhost` | 443 + `http2 on;` | dynamic subset |
| **D** `h2-single` | `https://localhost` | 443 + `http2 on;` | **단일 서브셋** |
| **E** `h1-plain-single` | `http://localhost` | `listen 80` | **단일 서브셋** |

**B군이 이 설계의 핵심이다.** A → C만 재면 HTTP/2 이득에 TLS 비용이 섞여 **과소평가**된다.
015가 `gzip_comp_level`을 맞춰 "누가 압축하나"와 "얼마나 세게 압축하나"를 가른 것과 같은 이유다.

기준선은 **같은 세션에서 다시 쟀다**(009_1 §2.2·009_2 §2.3의 규율). 그 값이 또 맞았다 —
A군 홈 FCP **616ms**, 009_1 after가 616ms, 009_2 before가 615ms다. 상세도 535ms로 같고,
폰트 바이트는 **289,305B로 009_1과 바이트까지 동일**하다. 세션을 세 번 건너서 ±0.2%다.

### 4.2 프로토콜 무결성 — 선행 조건부터 통과했다

| 검사 | 결과 |
|---|---|
| `openssl s_client -alpn h2` (`http2 on`) | `ALPN protocol: h2` |
| 같은 것, `http2 off` | `No ALPN negotiated` |
| Lighthouse C군 전 회차 | `h2` × 51 (홈) / × 34 (상세) |
| Lighthouse A·B군 전 회차 | `http/1.1` × 51 / × 34 |

**폰트 조각 11개가 전부 `h2`로 찍혔다.** 문서만 h2인 반쯤 걸린 상태가 아니다.
`--ignore-certificate-errors`가 ALPN 협상을 망치지 않는다는 것도 여기서 확인됐다 — ALPN은
인증서 검증 결과보다 먼저 끝난다.

| TLS 비용 (A → B) | **+74ms (+12.0%)** | +72ms (+13.5%) |
| **HTTP/2 순효과 (B → C)** | **-208ms (-30.1%)** | **-164ms (-27.0%)** |
| 평문 대비 합계 (A → C) | -134ms (-21.8%) | -92ms (-17.2%) |

**B군이 값을 했다.** B군 없이 쟀으면 HTTP/2 효과를 -21.8%로 적었을 것이고, 그건 TLS 비용
+74ms에 깎인 수치다. 순효과는 그보다 **38% 더 크다.**

**그리고 LCP가 같이 내려갔다** — 0절 정정 2가 던진 질문의 답이다. B → C에서 홈 852 → 642
(-210ms), 상세 769 → 563(-206ms)다. 009_2의 단일 서브셋은 같은 "요청 수 감소"인데 LCP를
**+63ms 악화**시켰다. 차이는 바이트다 — 단일 서브셋은 요청을 줄이면서 +71KB를 늘렸고,
HTTP/2는 바이트를 **전혀 건드리지 않는다**(전송 530,626 → 525,575B로 -0.95%, 폰트는 -920B).
**§3.8이 설명하지 못한 불일치가 여기서 풀린다.**

홈(-30.1%)과 상세(-27.0%)의 차이가 작은 것도 설명된다. 조각이 11개와 8개로 다르지만 커넥션
6개 제한에서는 **둘 다 2라운드**다(6+5, 6+2). 라운드 수가 같으니 이득도 비슷하다.

> A군 상세만 산포가 8.1%다(3회차가 493ms로 빠졌다). 009·009_1이 좌석맵에서 기록한 이중분포의
> 꼬리가 상세에서도 드물게 나온다는 뜻이다. B·C·D군 상세는 0.0~0.4%로 수렴했다.

### 4.4 단일 폰트 서브셋 — 영구 기각. 부호가 뒤집혔다

사전 등록 기준(A군 대비 -30%)에 -21.8%가 못 미쳐서 **D군을 만들었다.** 009_2와 같은 방법이다 —
009_1 §3.4의 발견(조각이 글자 빈도 순이고 번호가 클수록 흔하다)을 써서 상위 24조각(68~91)의
`unicode-range`를 합집합으로 모았다. **2,620자**가 나왔고 009_2와 같다. 파일은 `subset-font`
(harfbuzz wasm)로 **379,600B** — 009_2의 374,336B와 1.4% 차이다.

| 군 | 프로토콜 | 폰트 | 홈 FCP | 홈 LCP | 홈 전송 | 상세 FCP | 상세 전송 |
|---|---|---|---|---|---|---|---|
| C | h2 | 11개 288,385B | **482 (0.3%)** | **642** | 525,575 | **443 (0.0%)** | 438,535 |
| **D** | h2 | **1개 380,205B** | 562 (0.7%) | 682 | 600,988 | 564 (0.4%) | 591,989 |

**HTTP/2 위에서 단일 서브셋은 홈 +80ms(+16.6%) / 상세 +121ms(+27.3%) 손해다.**
HTTP/1.1에서는 빠른 쪽이었는데 **부호가 뒤집혔다.** 바이트도 홈 +75,413B / 상세 +153,454B다.

이게 §3.8 추론의 완성이다. 단일 서브셋의 이득은 **전부 요청 수 경쟁 해소**에서 왔고, HTTP/2가
그 경쟁을 없애자 남는 것은 **바이트 증가분의 손해뿐**이다. 그래서 역전됐다.

009_2가 적어 둔 예측 하나도 소수점까지 맞았다 — "상세·좌석맵은 8조각 205,472B라 **+169,165B**"
였고, 이번 상세 폰트 증가는 380,205 - 210,527 = **+169,678B**다.

**E군이 이 Task의 가장 큰 수확이다.** 평문 HTTP/1.1에서 단일 서브셋을 다시 재서 009_2의
207ms를 재현해 봤다.

| 군 | 프로토콜 | 폰트 | 홈 FCP | 홈 LCP |
|---|---|---|---|---|
| A | http/1.1 | 11개 289,305B | 616 (0.2%) | 739 |
| **E** | http/1.1 | **1개 379,901B** | **570 (0.4%, 6회)** | 770 |
| 009_2 `all5` | http/1.1 | 1개 374,336B | **207 (40.4%)** | 807 |

**재현되지 않았다.** 같은 조건 6회가 **570ms, 산포 0.4%** 로 수렴했고, 효과는 616 → 570 =
**-46ms(-7.5%)** 다. 009_2가 적은 -408ms(-66.3%)의 **9분의 1**이다.

환경 변화 탓으로 돌릴 수 없다 — **같은 세션의 A군이 616ms로 009_2의 before(615ms)와 1ms 안에서
맞았다.** 기준선은 재현됐고 단일 서브셋 군만 재현되지 않았다. 산포 40.4%가 무슨 뜻이었는지
이것으로 설명된다: **207ms는 그 산포 안의 이상치였다.** 0절 정정 1이 괄호를 되돌린 그 자리다.

정리하면 009_2는 **결론은 맞았고 근거 수치는 과장이었다.**

| | 009_2가 적은 것 | 이번 재측정 |
|---|---|---|
| 단일 서브셋 효과 (평문 h1) | -408ms (-66.3%), 산포 40.4% | **-46ms (-7.5%)**, 산포 0.4% |
| 올바른 레버가 HTTP/2인가 | 추론 | **맞다 — -208ms (-30.1%)** |
| 단일 서브셋 vs HTTP/2 | 비교 안 함 | HTTP/2가 **4.5배** 크다 |
| HTTP/2 위의 단일 서브셋 | "바이트는 205~289KB로 유지된다" | **+16.6% 손해로 역전** |

**기각이라 코드째 지웠다**(교훈 5) — `globals.css`의 `@font-face`, 생성한 woff2,
`subset-font` 의존성까지 전부. 009_2도 같은 처리를 했다.

### 4.5 무스로틀 — 로컬 루프백에서는 실측이 안 된다

`--throttling-method=provided` 홈 6회씩.

| 군 | FCP 중앙값 | 산포 | 판정 |
|---|---|---|---|
| A 평문 h1 | 94ms | 33.1% | **판단 불가** |
| B TLS h1 | 90ms | 32.4% | **판단 불가** |
| C TLS h2 | 96ms | 54.6% | **판단 불가** |

**세 군이 사실상 같고 셋 다 판단 불가다.** 루프백은 RTT가 ~0이라 커넥션 6개 제한이 비용을
만들지 않고, TLS 핸드셰이크 비용도 나타나지 않는다(스로틀 군에서는 +74ms였다).

**그래서 4.3절의 616 / 690 / 482는 전부 Lantern의 RTT 40ms 모델 안의 수치다.** 이게 이 Task의
가장 중요한 한계이고, 동시에 **판정이 성립하는 이유**다 — 009_2의 615ms도 같은 모델로 잰
값이라 같은 자 안의 비교다. 실제 네트워크에서 얼마인지는 다른 측정이다.

## 6. 한계

- **전부 Lantern 모델 안의 수치다**(4.5절). 루프백 실측에서는 HTTP/2 이득도 TLS 비용도 재지
  못했다. 실제 RTT가 있는 경로에서 재려면 Task 038(전용 부하 노드)이나 Task 034(배포)가 필요하다.
- **로컬 self-signed는 운영 TLS가 아니다.** 체인 검증·OCSP·세션 재사용·TLS 종단 위치가 모두
  다르다. 특히 `ssl_session_cache`를 안 켰고 `CA:TRUE` 인증서를 자기 신뢰 앵커로 쓴다 —
  둘 다 운영에서는 안 하는 선택이다.
- **TLS 비용 +74ms의 내역을 쪼개지 않았다.** 핸드셰이크 RTT인지 암복호 CPU인지 가르지 않았고,
  Lantern 모델에서는 사실상 RTT 몫일 것으로 보이지만 확인하지 않았다.
- **80과 443이 동시에 열려 있다.** 운영이라면 80은 443으로 보내야 한다. k6 하네스가 평문으로
  들어와서 내린 타협이고, Task 038이 부하 생성기를 분리하면 다시 볼 자리다.
- **HTTP/2의 다른 레버를 안 건드렸다.** 서버 푸시(이미 deprecated), 우선순위,
  `http2_max_concurrent_streams` 기본값(128)을 전부 기본으로 뒀다. 폰트 조각이 11개라 128에
  닿지 않는다.
- **재방문자는 여전히 측정 밖이다.** Lighthouse는 항상 캐시 콜드다. HTTP/2가 조건부 요청
  11번의 비용을 어떻게 바꾸는지는 Task 041 몫이고, **이 Task 결과가 그 판단의 전제를 바꿨다** —
  조각 11개를 줄일 이유가 없어졌으므로 041은 "11개를 그대로 두고 재방문 비용을 재는" 쪽이 된다.
- **모바일을 안 쟀다.** 009·009_1·009_2가 모두 n=1로 남긴 그 구간이고 이번에도 데스크톱만이다.
  모바일은 RTT가 크니 HTTP/2 이득이 더 클 방향인데 재지 않았다.
- **E군을 상세에서 안 쟀다.** 홈 6회로 207ms 비재현이 확정됐다고 보고 상세는 생략했다.
- **세션 쿠키 `secure`의 "깨지는 조건"을 못 만들었다.** `http://localhost`에서도 Secure 쿠키가
  저장돼서(Chrome의 localhost 예외) 토글의 필요성을 음성으로 확인하지 못했다. localhost가
  아닌 평문 호스트에서 깨질 것으로 보지만 그 환경이 없다.

## 7. 범위 밖 발견: 주석에 쓴 예측이 반증됐다

`secure` 토글을 넣으면서 "기본값이 false인 이유는 true로 고정하면 http 경로에서 쿠키가 저장되지
않아 로그인이 조용히 실패하기 때문"이라고 주석에 적었다. **확인해 보니 틀렸다.**

`SESSION_COOKIE_SECURE=true`로 띄우고 `http://localhost`로 가입·로그인하니 **e2e 3개가 통과하고
쿠키도 `secure: true`로 정상 저장된다.** Chrome이 localhost를 trustworthy origin으로 취급해서
Secure 쿠키를 예외적으로 허용하기 때문이다. CI도 `http://localhost:3000`이라 하드코딩해도 안 깨진다.

**교훈 4의 적중이다** — 반증된 설명을 주석에 남기면 다음 사람이 그걸 근거로 움직인다. 주석을
실측으로 고치고, 토글을 남기는 근거도 바꿨다: "http에서 깨지기 때문"이 아니라 **"그 통과가
Chrome의 localhost 예외에 기대고 있어서"** 다.

확인 방법도 기록해 둔다. **e2e가 통과하는 것만으로는 플래그가 붙었는지 알 수 없었다** —
Next가 `process.env`를 빌드 시점에 인라인하면 런타임 값이 안 먹는데, 통과는 양쪽 다 똑같이
난다. Playwright의 `context.cookies()`로 쿠키를 직접 읽어서 `secure: true`를 봤다. 교훈 10이
"설정이 걸렸다고 믿는 것과 실제로 걸린 것은 다르다"로 적은 그 자리이고, 이번 Task에서
프로토콜 집계와 같은 처방을 두 번째로 적용한 셈이다.
