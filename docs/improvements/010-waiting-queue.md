## 1. 왜 만들었나

Phase 9의 로드맵 한 줄은 "Redis 대기열(ZSET) + 입장 제어"였다. 만들고 나니 두 숫자가 근거 없이
박혀 있었고, 두 문서에 그 사실을 적어뒀다.

> `admit-batch-size=50`과 폴링 백오프 숫자에 **근거가 없다**(Task 033이 정한다).
> — `tikkit-back/CLAUDE.md`

> 값은 Task 033이 측정해 고치고 프론트는 그대로 둔다.
> — `docs/ROADMAP.md` Task 032

그리고 선행 문서 셋이 이 Task를 재판정 자리로 지정해뒀다.

| 문서 | 넘긴 숙제 | 이 문서의 답 |
|---|---|---|
| 006 9절 | "포화점을 찾지 않았다" | 3절 — `R_sat` = 도착률 120/s |
| 008 결론 | "채택 근거는 지연이 아니라 용량이고 검증은 033" | 8절 — 용량 +37~41% |
| 009_2 기각 | "BE 좌석 응답 축소" | 9절 — 다시 기각. 이번에는 이유가 다르다 |

**대기열의 가치는 "메커니즘이 있는가"가 아니라 "숫자가 맞는가"에 있다.** 입장 속도가 좌석 API

아니라 **설정값 도출**이 본체다.

Task 031·032의 **설계 결정**은 이 문서 끝의 [부록 A](#부록-a-설계-기록--zset-두-개가-전부다-task-031032)에
모았다. 본문은 측정이고, 부록은 "왜 그렇게 만들었나"다.

## 2. 측정 환경

### 2.1 군을 일곱으로 가른 이유

"대기열 유무"만 가르면 네 가지를 놓친다.

| 군 | 구성 | 재는 것 |
|---|---|---|
| **A** `a-noqueue` | `QUEUE_ENABLED=false` | **before.** 포화점 `R_sat` |
| **B** `b-flagoff` | 기능 on, 회차 플래그 off | **"배포했지만 이 회차는 안 켠다"의 비용.** 실서비스 트래픽의 대부분이 이쪽이다 |
| **C** `c-preadmit` | 플래그 on, 전원 `active`에 미리 심음 | 보호 경로의 용량. B와의 차이 = 입장권 검증 비용 |
| **D** `d-batch{N}` | `admit-batch-size` 스윕 | 실제 입장 속도가 공칭값을 따라가는가 |
| **E** `e-poll` | 합성 대기 + 상태 API 단독 | `R_poll`, 깊이 의존성, 메모리 |
| **F** `f-cache-*` | 대기열 off, `CACHE_TYPE` 토글, **포화까지** | 008이 넘긴 숙제 |
| **G** `g-evict` | 대기 10만 + `maxmemory` 하향 | 축출의 실제 모양 |

B군이 특히 중요하다. `QueueWebConfig`가 인터셉터를 **조건 없이** 등록하므로 모든 좌석 조회가
`QueueFlagRegistry.enabled()`를 지난다. Task 031이 "꺼진 상태는 예전과 같다"고 적었지만 **재본
적이 없었다.**

### 2.2 로컬에서는 "같은 도착률을 before/after에 흘린다"가 성립하지 않는다

서로 다른 대기열 멤버 수는 **`maxVUs`가 상한**이다(멤버십이 `memberId` 기준이고 VU 하나가 계정
하나를 쓴다). 300명이면 `admit-batch-size=50`에서 **6초에 전원 입장**한다 — 줄이 서지 않고,
측정 구간 대부분이 "대기열을 켠 채로 전원 입장한 상태"다.

그래서 **대기열의 양쪽 끝을 각각 만들었다.**

| 상태 | 만드는 방법 | 재는 것 |
|---|---|---|
| 전원 입장 | `load-test/redis/preadmit.sh` | 보호 경로 용량 (C군) |
| 줄이 깊음 | `load-test/redis/seed-waiting.sh` | 상태 API 용량·메모리·축출 (E·G군) |

그리고 **"대기열이 좌석 API를 막는다"는 결론은 p95 비교가 아니라 산술 + 두 실측값으로 성립한다.**
좌석 API에 도달하는 부하가 도착률이 아니라 `초당 입장 인원 × 입장자당 요청 수`로 상한이 걸린다.

### 2.3 폴링을 VU 루프가 아니라 iteration 반복으로 표현했다

`queue-spike.js`에서 폴링을 VU 내부 `while`로 돌리면 한 iteration이 수 분으로 늘어나
arrival-rate executor가 VU 고갈로 `dropped_iterations`를 쌓는다. 그건 **부하 생성기의 한계이지
서버 거동이 아니다** — 측정이 조용히 오염된다.

대기열 멤버십은 Redis에 남으므로, 같은 계정이 다음 iteration에서 진입 API를 다시 부르면
(`ZADD NX`라 순번이 유지된 채) 폴링하는 대기자가 된다.

### 2.4 계정을 500 → 2,000으로 올렸다

006이 "VU를 더 띄우려면 `03-loadtest-members.sql`의 500을 같이 올려야 한다"고 적어둔 그대로다.
`maxVUs = min(300, ACCOUNT_COUNT)`에 묶여 있었다.

### 2.5 회차와 수렴 판정

군마다 워밍업 1회를 돌리고 버린다(008 2.2절). **이번에는 그 효과가 ms가 아니라 에러로
나타났다** — 백엔드 재생성 직후 첫 회차는 캐시 on/off와 무관하게 목록 조회가 4.2~4.5%
실패했고, 두 번째 회차부터 0%였다. 워밍업을 버리는 규칙이 없었으면 "캐시를 켜면 에러가 난다"는
틀린 결론을 적었을 것이다.

본 측정은 3회 중앙값이고, 스윕(지점 탐색)은 1회씩이다.

## 3. 포화점을 먼저 닫았다 (A군)

대기열 없이 서버가 무너지는 지점을 모르면 "대기열이 막아줬다"를 말할 수 없다.

`booking-spike.js`를 `ramping-arrival-rate`로 계단식 상승시켰다. 한 iteration은
좌석 조회 → 선점 → 결제(10%)/취소다.

| 도착률/s | req/s | p95 ms | p99 ms | 선점 성공률 | drop | Hikari pending |
|---|---|---|---|---|---|---|
| 30 | 79.1 | 26.01 | 33.34 | 99.9% | 0 | 0 |
| 60 | 156.0 | 28.41 | 34.02 | 100.0% | 0 | 0 |
| **120** | **308.5** | **64.54** | 98.78 | 99.7% | 35 | **0** |
| 140 | 344.2 | **214.32** | 446.87 | 98.6% | 481 | 5 |
| 160 | 346.9 | 474.86 | 968.15 | 97.7% | 1,856 | 61 |
| 180 | 354.7 | 439.80 | 976.80 | 97.2% | 3,062 | 6 |
| 240 | 363.8 | 513.10 | 932.08 | 97.1% | 7,146 | 86 |
| 300 | 370.5 | 526.36 | 1098.40 | 96.7% | 11,288 | 20 |

**`R_sat` = 도착률 120/s (309 req/s, 122 MB/s).** p95가 120 → 140에서 64.5 → 214.3ms로

140/s에서 Hikari pending이 생기는 걸 보고 "풀이 벽"이라고 적었다. **틀렸다.**
`application.yml`에 Hikari 설정이 아예 없어서 기본값 10으로 돌고 있었고, 환경변수로 빼서 재봤다.

## 4. 꺼진 회차는 정말 예전과 같다 (A·B·C군)

도착률 120/s에서 3회씩 쟀다.

|---|---|---|---|---|

## 5. `admit-batch-size`를 도출했다 (D군)

### 5.1 식

```
입장한 사용자 1명이 내는 보호된 요청 k = 좌석 조회 + 선점 = 약 2
  (결제·취소는 비보호 — 이미 좌석을 잡은 사람은 거래를 끝낼 수 있어야 한다)

상한 = R_sat x 안전계수 = 120 x 0.7 = 84명/s      (상태 API 몫 + 새로고침 분산)
하한 = 재고 / 1인 평균 / 목표 판매 시간 = 10,000 / 2.5 / 600 = 6.7명/s
```

**유효 구간 [6.7, 84]명/s.** 현재 값 50은 그 안에 있고, 양쪽에 여유가 있어 유지했다
(10,000석을 80초에 판다).

### 5.2 `admit-batch-size`는 전역이 아니라 회차당이다

`QueueAdmissionScheduler.run()`이 `queue_enabled`가 켜진 회차를 **전부 순회**하면서 회차마다
배치를 입장시킨다. 즉

```
초당 입장 인원 = admit-batch-size x 켠 회차 수 / admit-interval
```

**회차를 2개 켜면 100명/s가 되어 상한 84를 넘는다.** 50은 회차 1개를 전제한 값이다.
그래서 측정에서도 `04-enable-queue.sql`이 **정확히 1개만** 켠다 — N개를 켜면 batch가 초당 입장
인원과 1:1로 대응하지 않아 스윕 결과를 해석할 수 없다. 3,000회차를 켜면 틱마다 Redis 왕복이
약 9,000회가 되는 문제도 같이 생긴다.

### 5.3 실제 입장 속도는 공칭값과 같았다 — 031의 설명이 틀렸다

| batch | 공칭 명/s | 관측 명/s | 비율 | 표본 | 실제 배출 |
|---|---|---|---|---|---|
| 5 | 5 | 5.000 | 1.0000 | 31 | 155 |
| 10 | 10 | 10.333 | 1.0333 | 30 | 310 |
| 25 | 25 | 25.000 | 1.0000 | 31 | 775 |
| 50 | 50 | 50.000 | 1.0000 | 31 | 1,550 |
| 100 | 100 | 100.000 | 1.0000 | 31 | 3,100 |

비율이 1.000~1.033이다. **Task 031이 "`fixedDelay`라 실제 주기가 설정값보다 길어서 ETA가
낙관적이다"라고 적어둔 설명은 틀렸다** — 작업이 수 ms라 1초에 묻힌다. ETA가 낙관적인 진짜
원인은 **유령**이다(브라우저를 닫아도 `waiting`에 남아 그 틱의 슬롯을 먹는다).

그리고 이 표가 031 한계 4번("입장 속도가 좌석 API 처리량보다 크면 대기열이 막지 못한다")의
재현이다. 배치를 키우면 그만큼 그대로 흘러들어간다 — 대기열은 유입을 **차단**하는 장치가 아니고
**계량**하는 장치다.

## 6. 폴링 백오프: 구간이 하나 부족했다 (E군)

### 6.1 역산으로 판정한 이유

로컬에서 10만 명을 만들 수 없다. 대신 **상태 API 단독 처리량을 재고 공식을 역으로 풀었다.**
백오프가 닫힌 식이라 가능하다.

```
RPS(N) = min(N,100)/2 + min(max(N-100,0),900)/5 + max(N-1000,0)/10      (031의 3구간)

N = 100,000 -> 50 + 180 + 9,900 = 10,130 RPS     (백오프가 없으면 50,000)
```

판정 기준을 p95가 아니라 **용량**으로 뒀다. 008이 저부하 p95로 캐시를 판정하려다 실패한 것과
같은 실수를 피하려는 것이다.

### 6.2 깊이를 100배 늘려도 요청당 비용이 같았다

합성 멤버를 심어 깊이를 만들고 같은 도착률을 흘렸다.

| 도착률 | 깊이 1,000 req/s | p95 ms | 깊이 100,000 req/s | p95 ms | p95 비율 |
|---|---|---|---|---|---|
| 200 | 172.1 | 2.98 | 172.1 | 2.82 | 0.95 |
| 1,000 | 854.4 | 2.72 | 854.4 | 2.77 | 1.02 |
| 2,000 | 1,707.3 | 2.83 | 1,707.3 | 2.92 | 1.03 |
| 3,500 | 2,898.2 | 3.70 | 2,985.7 | 3.63 | 0.98 |

**비율 0.95~1.03.** 수용 기준(1.2 이하)을 크게 통과했으므로 역산이 성립한다.
`ZRANK`가 O(log N)이니 이론상 1.66배여야 하는데 보이지 않는다 — **순번 계산이 요청 비용에서
차지하는 몫이 측정 한계 아래**라는 뜻이다. 상태 API의 비용은 순번 계산이 아니라 왕복 횟수와
직렬화다.

### 6.3 `R_poll` = 2,986 req/s는 하한이다

그 지점의 CPU 분배(최대값):

| 컨테이너 | CPU |
|---|---|
| backend1 / backend2 | 210.0% / 210.1% |
| **k6** | **128.0%** |
| redis | 77.8% |
| nginx | 54.9% |
| **postgres** | **5.5%** |
| 합계 | 686.3% = 6.9 / 16코어 (43%) |

postgres 5.5%는 **상태 조회가 DB를 건드리지 않는다**는 설계의 확인이다.

그리고 더 올리면 **부하 생성기가 먼저 막혔다.** k6의 VU 상한을 600 → 2,000으로 올리자
처리량이 **떨어졌다**.

| 도착률 | VU 상한 600 | VU 상한 2,000 |
|---|---|---|
| 3,500 | 2,898 req/s · p95 3.70 · drop 8,079 | 2,684 · 4.64 · **27,652** |
| 5,000 | 4,127 req/s · p95 8.94 · drop 12,368 | 3,807 · 8.18 · **41,005** |

서버는 43% CPU에서 p95 3.6ms인데 생성기가 한계다. 그래서 **진짜 `R_poll`은 더 위에 있고,
2,986은 "이 호스트에서 증명된 범위"다.**

### 6.4 그래서 4번째 구간을 넣었다

측정 하한 2,986 RPS로 3구간 식을 역으로 풀면 **약 28,000명**이 한계다 — 목표 10만 명의 1/3이다.

`rank >= 10,000 -> T초` 구간을 추가하고 T를 고르면:

| T | N=100,000의 요구 RPS | 판정 |
|---|---|---|
| 20초 | 5,630 | 하한 초과 (미검증) |
| 30초 | 4,130 | 하한 초과 (미검증) |
| 40초 | 3,380 | 하한 초과 (미검증) |
| **60초** | **2,630** | **측정 하한 안** |
| 90초 | 2,130 | 측정 하한 안 |

**60초를 채택했다.** 30초가 체감에 낫지만 4,130 RPS는 증명되지 않은 영역이라, 증명된 쪽을 골랐다.
서버 CPU가 43%였으니 30초도 아마 된다 — 다만 "아마"를 설정값으로 박지 않는다.

1,000~10,000 구간을 10초로 남긴 이유는 체감이다. 입장 속도가 50~84명/s이므로 rank 10,000의
예상 대기가 119~200초인데, 그 사람에게 60초 간격을 주면 남은 대기 동안 화면이 두세 번만
갱신된다. 60초는 예상 대기가 분 단위로 넘어가는 구간에만 쓴다.

**FE는 한 줄도 고치지 않았다.** Task 032가 `pollAfterSeconds`를 계약으로 내려주고 `setInterval`이
아니라 `setTimeout` 체인으로 구현했기 때문이다. 그 설계가 여기서 처음 효과를 봤다.

### 6.5 10초 구간을 처음 밟았다

Task 032는 앞에 150명을 심어 5초 구간까지만 확인하고 `rank >= 1,000`(10초)을 미검증으로 남겼다.
깊이 1,000을 심으니 VU의 순번이 950~1,044에 걸리면서 `tikkit_queue_poll_after_seconds`가
min 5 / med 5 / p95 10 / max 10으로 찍혔다 — **두 구간을 한 실행에서 같이 밟았다.**

## 8. 캐시 재판정 — 008의 채택 근거가 증명됐다 (F군)

008은 캐시를 채택하면서 "현 규모에서는 p95를 개선하지 못한다(2.20 → 2.27ms). 채택 근거는 지연이
아니라 **용량**이고 그 검증은 Task 033이 한다"고 적었다. BE CPU 4.2%의 저부하에서 쟀기 때문이다.

### 8.1 포화를 만들려면 think time을 꺼야 했다

`browse`·`browse-skewed`·`seatmap`은 `ramping-vus`(닫힌 모델)이고 iteration마다 `think()`가
들어간다. 기본값으로 VU 600을 띄워도:

| VU | req/s | p95 ms | iteration 전체 | 그중 HTTP |
|---|---|---|---|---|
| 50 | 32.7 | 5.78 | 3,770ms | 약 6ms |
| 150 | 95.7 | 2.83 | 3,761ms | 약 6ms |
| 300 | 191.3 | 2.13 | 3,733ms | 약 6ms |
| 600 | 382.5 | 1.96 | 3,742ms | 약 6ms |

처리량이 VU에 **정확히 비례**하고(VU당 0.638 req/s) p95가 2ms다. 재고 있던 것이 서버 용량이
아니라 `sleep`이었다. **008이 용량을 재지 못한 구조적 이유가 이것이다.**

`THINK_MIN`/`THINK_MAX` 환경변수를 넣어 끌 수 있게 했다. 기본값은 바꾸지 않았다 —
006·008·029의 수치가 그 값으로 측정됐고, 바꾸면 그 비교가 깨진다.

> **함정**: `seatmap.js`는 `think(1.0, 4.0)`으로 **인자를 직접 넘긴다.** 그러면 기본값이
> 덮이지 않아 `THINK_MAX=0`이 무시되고, 증상은 "포화를 만들었는데 97 req/s다"로만 나타난다.
> 인자보다 우선하는 전역 스위치를 따로 둬서 막았다.

### 8.2 용량 +37~41%

| 시나리오 | VU | 캐시 없음 | 캐시 켬 | 차이 |
|---|---|---|---|---|
| `browse` | 50 | 7,111.6 req/s · p95 12.58 | 9,574.2 · 9.14 | **+35%** |

**한계 처리량이 7,400 → 10,150 req/s로 올랐다 (+37%).** 적중률 99.9%이고, 같은 VU에서 p95도
같이 내려간다. 008의 채택 근거가 증명됐다.

치우친 분포가 더 유리한 것(+41% vs +37%)도 방향이 맞다 — 핫 키가 집중되면 적중률이 올라간다.

좌석맵은 캐시 토글에 영향받지 않는다(+0.4%). 캐시 대상이 아니라서 당연하지만, "캐시를 켜면
좌석맵이 손해를 본다"가 아니라는 확인도 된다.

### 8.3 008의 (2)번은 이 Task 안에서 답할 수 없다

"포화 구간에서 좌석맵 캐시가 뒤집히는지"를 재려면 좌석맵 캐싱이 구현돼 있어야 하는데, 008이
기각해서 코드에 없다. 토글만으로는 재볼 수 없다.

대신 9.2절의 귀속 측정이 기각 근거를 **다른 방향에서** 보강한다. 좌석맵 비용의 68%가 조립(DB

## 10. 거절이 공짜가 아니었다 — 가드를 트랜잭션 밖으로 옮겼다

### 10.1 재현

`ReservationService.create()`는 `@Transactional`이고 그 **첫 줄**이
`queueGateway.requireAdmitted()`였다. 대기열의 목적이 DB를 지키는 것인데, 거절이 트랜잭션 안에서
일어나면 커넥션을 먼저 잡고 나서 던진다.

전원이 403을 받는 60초 구간을 만들어 쟀다(`QUEUE_ADMIT_BATCH_SIZE=0`으로 입장을 완전히 멈춘다 —
`peekWaiting`이 `count <= 0`을 막아준다). 누적값이라 무부하 구간을 먼저 재서 상시 증가분을 뺐다.

| | 무부하 60초 | 거절 부하 60초 | 순증 | 요청당 |
|---|---|---|---|---|
| **before** | 219 | 11,344 | 11,125 | **1.0114** |
| **after** | 220 | 410 | 190 | **0.0173** |

거절 10,950건(403 비율 100%)에 대해 **커넥션 획득이 요청당 1.01개**였다. SQL은 한 줄도 돌지
않는다 — 트랜잭션 시작 시점에 획득하기 때문이다.

### 10.2 해결

가드를 `ReservationController`로 올렸다. 인터셉터를 못 쓴 이유는 `scheduleId`가 **요청 본문**에
있어서 인터셉터가 읽으면 `@RequestBody` 역직렬화가 빈 스트림을 만난다는 것이었는데, 컨트롤러에는
이미 역직렬화된 본문이 있다. 좌석 조회를 `QueuePassInterceptor`가 막는 것과 같은 웹 계층이 된다.

**요청당 1.0114 → 0.0173 (-98.3%).** 같은 부하에서 획득 횟수가 11,125 → 190이고, 남은 190은
로그인 요청 50건과 플래그 스냅샷 TTL 갱신이다 — 거절 경로 자체는 커넥션을 한 개도 쓰지 않는다.

**대가**: 서비스가 스스로를 보호하지 않으므로 다른 호출부가 생기면 대기열을 우회한다. 지금
호출부는 `ReservationController` 하나이고, 늘어나면 가드를 같이 옮겨야 한다.

## 12. 관문 — 밟은 함정

### 12.1 compose에 `QUEUE_ENABLED`가 없어서 스택을 켤 수조차 없었다

`x-backend-env` 앵커에 `AUTH_SESSION_STORE`·`CACHE_TYPE`은 있는데 `QUEUE_ENABLED`가 **없었다.**
`application.yml`이 그 이름으로 읽고 있으니 Task 031의 기능을 prod 스택에서 켤 방법이
처음부터 없었다. 측정 Task가 아니었으면 배포 때 발견했을 것이다.

### 12.2 셸 환경변수가 `.env` 파일을 덮는다

스크립트가 `. ./.env`로 값을 export한 뒤 `sed`로 파일만 고쳤다. `docker compose`는
**셸 환경변수를 `.env`보다 우선**하므로 export된 옛 값을 썼다 — **"대기열을 껐다"고 믿으면서
켜진 상태를 측정했다.** `set_env_var`가 파일과 셸을 같이 바꾸게 고쳤고, 전제 검증이 잡아냈다.

### 12.3 수치가 좋아지는 가장 흔한 이유는 요청이 일을 안 한 것이다

대기열이 켜진 상태로 `booking-spike.js`를 돌렸더니 좌석 조회가 전부 403이 되어 iteration이 즉시
끝났고, **p95가 64ms에서 2.95ms로 "개선"됐다.** 서버가 빨라진 게 아니다.

그래서 `run-group.sh`에 두 겹을 넣었다.

- **전제 검증** — 컨테이너에서 읽은 `QUEUE_ENABLED`, DB의 켠 회차 수, 좌석 API의 HTTP 상태
  (`off`=200 / `flagoff`=200 / `on`=401) 세 개가 기대와 다르면 시작하지 않는다
- **워크로드 무결성** — iteration당 요청 수 2.5개 이상, 수신 100KB 이상. 임계값으로는 못 잡는다.
  붕괴하면 지연이 **좋아지므로** 지연 임계값은 오히려 통과한다

### 12.4 간헐적으로 깨지는 테스트에 이분 탐색이 필요했다

전체 스위트가 `CacheQueryCountTest`에서 한 개 깨졌다. 폴링 구간 변경과 가드 이동을 의심해
되돌려 봤는데 **되돌린 상태도 통과하고 전부 복원한 상태도 통과했다** — 간헐적 실패였다.
이분 탐색을 안 했으면 멀쩡한 변경을 되돌렸을 것이다.

원인은 레포에 이미 적혀 있었다. `AbstractRedisCacheContainerTest.awaitCached()` Javadoc이
"캐시 쓰기가 간헐적으로 늦게 보인다. 넣고 바로 꺼내는 단정형 검증이 실행마다 다르게 깨졌다"고
적고 헬퍼를 제공하는데, **깨지는 세 테스트가 그 헬퍼를 안 쓰고 있었다.** `awaitCached()`를
넣고 전체 스위트 3회 연속 통과를 확인했다.

### 12.5 종료되지 않은 샘플러가 처리량을 40% 깎았다

중단된 스크립트가 남긴 백그라운드 샘플러가 2초마다 `docker compose exec`(무거운 경로)를 돌면서
처리량을 309 → 186 req/s로 떨어뜨렸다. A군 3회를 폐기하고 시드를 다시 만들어 재측정했다
(4절 — 다시 잰 3회가 309.37 / 309.63 / 309.44로 범위 0.08%다).
`docker exec`(가벼운 경로) + `trap 'exit 0' TERM INT HUP`으로 고쳤다. 백그라운드 작업에 뒤에
`&`를 붙이면 부모와 함께 죽어서 아예 안 도는 반대 문제도 같이 겪었다.

### 12.6 Git Bash·Python 환경

- `/scripts/x.js` 같은 컨테이너 내부 경로가 `C:/Program Files/Git/scripts/x.js`로 번역된다 →
  `MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'`
- Python stdout이 cp949로 잡혀서 em dash 하나에 `UnicodeEncodeError`로 **측정 도중 죽는다.**
  증상이 "결과 CSV가 비어 있다"라 원인이 안 보인다 → `PYTHONIOENCODING=utf-8`
- `awk`로 힙 지표를 뽑을 때 `$2`를 쓰면 `id="G1 Eden Space"`의 공백 때문에 "Eden"을 집는다 → `$NF`
- Git Bash가 한국어 쿼리 파라미터를 cp949로 보내서 목록 API가 500(`MalformedInputException`)이
  됐다. 앱 문제가 아니라 curl 문제다 — k6는 UTF-8을 보낸다

1. **A군의 바이트 조건이 B·C군과 엄밀히 같지 않다.** 샘플러 사고로 버린 3회를 재측정하면서

   세 군을 같은 세션에서 다시 재지는 않았다.
2. **`R_poll`은 하한이다.** 부하 생성기가 서버보다 먼저 막혀서 상한을 못 찾았다(6.3절).
   그래서 폴링 60초는 **증명된 범위 안에서 고른 보수적인 값**이고, 전용 부하 노드가 있으면
   30초로 당길 수 있을 가능성이 크다.
3. **좌석 응답 (a)안의 효과는 두 점 외삽이다**(9.2절). 직접 구현해서 재지 않았다.
4. **008의 (2)번을 닫지 못했다**(8.3절). 좌석맵 캐싱 구현이 없어서 토글로 재볼 수 없다.
5. **`k=2`(입장자당 보호 요청 수)가 낙관적이다.** 선점은 쓰기라 좌석 조회보다 비싼데 같은
   비용으로 셌고, `pass-ttl`이 15분이라 입장한 사람이 그 안에 좌석 조회를 여러 번 할 수 있다.
   그래서 안전계수 0.7을 곱했다.
6. **`admit-batch-size` 상한이 좌석 수에 비례한다.** 10,000석 기준으로 도출했는데 2,000석
   회차면 응답이 1/5이라 상한이 훨씬 높다. **전역 상수로 두는 것 자체가 의심스럽다.**
7. **활성 인원 절대 상한이 없다.** 입장권이 활동하면 무한 연장되고(`admittedAt`용 ZSET이
   하나 더 필요하다), 유령을 치우지 않는다. 둘 다 구조 변경이라 측정 Task의 범위가 아니다.
8. **단일 호스트에서 쟀다.** BE 2대·PG·Redis·nginx·k6가 16코어를 나눠 쓴다. 절대값은
   이 구성의 값이고, 비교(A vs B vs C, none vs redis)만 이식 가능하다.

## 부록 A. 설계 기록 — ZSET 두 개가 전부다 (Task 031·032)

031·032에 개별 문서가 없어서 여기 모았다. 로드맵 문구를 **그대로 구현하지 않은 지점들**이 수확이다.

### A.1 Redis 키는 회차당 두 개다

```
tikkit:queue:{12}:waiting   ZSET  member = memberId, score = 진입 epoch millis
tikkit:queue:{12}:active    ZSET  member = memberId, score = 입장권 만료 epoch millis
```

중괄호는 **리터럴**이다(Redis Cluster hash tag). 지금은 standalone이라 영향이 없지만 지금 넣는
이유는 **나중에 넣는 게 공짜가 아니기 때문**이다 — 운영 중에 키 포맷을 바꾸면 이미 줄 서 있는
사람들의 큐가 사라진다.

### A.2 "활성 세트 + TTL 토큰"에서 벗어났다

로드맵 문구는 "활성 세트 + TTL 토큰"이었다. 그대로 만들면 **토큰 키가 만료돼도 SET에는 멤버가
영구히 남아 `SCARD`가 틀린 값을 준다.** 유령을 치우려면 SET 전체를 순회해 토큰 키의 존재를
확인해야 한다(O(N) 왕복).

score에 만료 시각을 넣으면 그게 전부 사라진다 — 검증은 `ZSCORE` 왕복 1회, 만료 일괄 수거는
`ZREMRANGEBYSCORE` 명령 1개, 연장은 `ZADD GT` 명령 1개다. 부수 효과로 **만료 테스트가 `sleep`
없이 결정적**이 됐다(과거 score를 심으면 된다).

### A.3 Lua 없이 명령 두 개의 순서로 닫았다 (at-least-once)

스케줄러 한 틱: `ZREMRANGEBYSCORE active`(만료 수거) → `ZRANGE waiting`(선두 N명) →
**`ZADD active`(먼저)** → **`ZREM waiting`(나중)**.

두 명령 사이에서 죽으면 사용자가 양쪽에 남는데, 상태 조회가 `active`를 먼저 보므로 **정상
입장**한다. 남은 중복은 다음 틱이 치운다. 거꾸로 하면 양쪽에서 사라져 **선두 몇 명이 조용히 맨
뒤로 간다** — 설명할 수 없고 로그에도 안 남는다. 멱등성 방향을 at-most-once가 아니라
**at-least-once로 고정**하는 것이다.

**Lua를 쓰지 않는다.** Lua도 "프로세스가 죽는 것"은 못 막고 비원자 창을 0.3ms에서 0으로 줄일
뿐인데, 그 창에 끊긴 결과가 이미 무해하다. ShedLock이 단일 writer를 보장하므로 경쟁 자체도 없다.

진입은 `ZADD NX` 하나로 닫힌다 — 더블클릭·폴링 중복·새로고침이 순번을 밀지 않고, 재진입으로
앞자리를 살 수도 없다.

### A.4 별도 토큰을 발급하지 않는다

입장권의 실체는 `active` ZSET의 `(memberId → 만료시각)` 엔트리이고 전송되는 비밀이 없다.
랜덤 UUID 토큰은 같은 인증 세션에 내려줄 수밖에 없어서 **보안 이득이 0이다** — 새 비밀을 만드는
게 아니라 같은 비밀을 두 번 적는 것이다.

### A.5 인터셉터 + 서비스 가드 하이브리드였고, 지금은 둘 다 웹 계층이다

"인터셉터 적용"이 **절반만 성립했다.** `POST /reservations`의 `scheduleId`가 요청 본문에 있어
인터셉터가 읽으면 `@RequestBody` 역직렬화가 빈 스트림을 만난다. 그래서 031은 서비스가 가드를
직접 부르게 했는데, 그게 10절의 커넥션 누수를 만들었다. **Task 033에서 컨트롤러로 올렸다.**

보호 대상은 둘뿐이다. 등급 조회는 대기 화면이 공연·가격을 보여줘야 해서 열어두고, 결제·취소는
**이미 좌석을 잡은 사람이 거래를 끝낼 수 있어야** 해서 열어둔다.

**대기열을 켠 회차는 로그인이 필수다.** 좌석 조회는 `permitAll`인데(Task 022가 "자리를 보고 나서
가입하는 흐름이 정상"이라고 의도적으로 열었다) `memberId`로 줄을 세워야 1인 1자리가 성립한다.
`SecurityConfig`를 `authenticated()`로 올리지 않고 **인터셉터가 401을 던지는** 이유가 이것이다 —
그러면 플래그가 꺼진 회차의 공개 조회가 그대로 보존된다.

### A.6 꺼진 상태를 구현으로 표현했다

`tikkit.queue.enabled=false`면 `DisabledQueueGateway`가 올라가 **전부 통과**시킨다. 호출부를
지우지 않고도 기능이 완전히 꺼지고, `cache.type=none`이 `NoOpCacheManager`를 올리는 것과 같은
구조다. 4절이 그 비용이 0임을 처음 측정했다.

토글이 **두 층**이다. `tikkit.queue.enabled`(이 애플리케이션에 기능이 있는가)와
`schedules.queue_enabled`(이 회차에 줄을 세우는가). 앞이 꺼져 있으면 뒤가 true여도 아무 일도
일어나지 않는다.

### A.7 플래그를 요청마다 DB에서 읽지 않는다

`QueueFlagRegistry`가 `volatile` 스냅샷 + 조회 시 자기 갱신(TTL 10초)으로 캐시한다.

- **Spring Cache를 못 쓴다** — `cache.type` 기본값이 `none`이라 거기 얹으면 캐시를 끈 환경에서
  좌석 조회마다 DB로 간다. 세 토글이 독립이어야 한다는 전제가 깨진다.
- **`@Scheduled`로 갱신하면 안 된다** — `SchedulingConfig`가 `@Profile("!test")`라 테스트에서
  스냅샷이 영원히 비고 **대기열 테스트 전체가 "플래그 off"로 조용히 통과한다.**
- 스탬피드는 **의도적으로 감수한다.** 쿼리가 ms 단위이고, 락으로 막으면 모든 조회가 락을 지난다.

### A.8 폴링 간격을 백엔드가 지시한다 (032의 설계가 033을 가능하게 했다)

032의 초안은 "2초 고정"이었다. 10만 명이면 상태 API에 50,000 RPS가 몰린다. 그래서 응답의
`pollAfterSeconds`로 백엔드가 지시하게 바꿨고, FE는 `setInterval`이 아니라 **`setTimeout`
체인**으로 구현했다(간격이 매 응답마다 바뀐다).

그 덕에 Task 033이 6.4절에서 구간을 하나 더 넣으면서 **FE를 한 줄도 고치지 않았다.**
계약에 값을 넣어두는 설계가 실제로 효과를 본 사례다.

예상 대기시간은 `rank / 초당 입장 인원`이다. 관측 속도로 계산하지 않는 이유는 분모가 흔들리면
ETA의 단조 비증가가 깨져 **진행바가 되감기기** 때문이다 — 사용자는 그걸 버그로 읽는다.

### A.9 031·032에서 밟은 함정 셋

- `@Repository` 하나를 조건부 설정 밖에 남겨 **테스트 176개가 한꺼번에 빨개졌다.** 증상은
  "대기열과 무관한 리포지토리 테스트 전부 실패"였다.
- Redis 팩토리가 생기면 **Spring Session이 따라 켜져** `MockHttpSession`이 무시되면서 403 대신
  **401**이 나왔다. 008 8절이 적어둔 구조가 대기열을 세 번째 트리거로 삼아 처음 드러났다.
- `QueueFlagRegistry`를 `@Scheduled`로 갱신하면 `@Profile("!test")` 때문에 **대기열 테스트
  전체가 "플래그 off"로 조용히 통과**할 뻔했다 (A.7).
