# 15. nginx 포화 안정화와 gzip 재판정 (Task 039)

> **한 줄 결론**: 측정을 무효로 만든 범인은 `max_fails`였고 **그건 닫혔다**(`no live upstreams`
> 977,264건 → 0건). 그런데 **처리량은 안 변했다**(768.6 → 780.6 req/s, 산포 안) — 같은 로그에
> 찍히던 `proxy_buffers` 임시파일도 없앴는데 CPU조차 안 움직였다. gzip은 포화에서도 **기각**이고,
> 이번에는 "어디서 압축하든 손해"까지 갈렸다(BE -11.1%, nginx -17.5%).

## 0. 착수하면서 로드맵 네 줄을 고쳤다

Phase 11 서문이 "착수할 때 근거 문서의 해당 절을 먼저 읽고, 어긋나면 로드맵을 고치는 것부터
한다"고 적어 둔 그대로다. 011·012·014가 모두 이 자리에서 시작했고, 이번에도 네 건이 나왔다.
**교훈 6("기각 기록이 다음 문서로 전달되지 않으면 그 기각은 없는 것과 같다")의 다섯 번째 적중이다.**

| # | 로드맵이 적고 있던 것 | 원문 | 어떤 종류의 손실인가 |
|---|---|---|---|
| 1 | "`no live upstreams` 977,264건으로 **전부 502**" | `no live upstreams` 977,264 / **502 984,911** / **504 11,735**건. 떨어진 것은 각 군 **3회차만** | 두 숫자를 하나로 붙였다. 504가 사라졌다 |
| 2 | "**`check-run.py`가 아니었으면** 채택했을 것" | 014 본문에 `check-run` 0건. 임계값("iteration당 요청 2.5개·수신 100KB")을 정의한 것은 [010](010-waiting-queue.md) 6절 | 귀속이 한 단계 밀렸다 |
| 3 | "단일 폰트 서브셋 FCP 66%의 정체가 요청 수"를 **009_1** 근거로 배치 | 출처는 [009_2](009_2-seatmap-structure.md) 3.8절. 009_1의 폰트 변경은 dynamic subset이고 FCP는 1,892 → 536ms(-71.7%), 요청은 1 → **11개로 늘어난** 쪽 | 문서를 잘못 가리켰다. 숫자는 맞는데 근거가 다른 문서다 |
| 4 | "`proxy_buffers`를 009·009_1·010이 **전부 넘겼다**" | **009가 진단까지 하고 범위 밖으로 이월했다.** 6.2절이 저부하에서 재서 **57만 줄 로그에 0건**을 확인했고(여유 16KB의 1차 출처가 014가 아니라 여기다), 6.4절이 `max_fails=1`/`fail_timeout=10s`를 원인으로 특정해 1분간 **502 285건**을 셌다 | "넘겼다"가 "진단이 없었다"로 읽힌다 |

**4번이 이 Task의 설계를 바꿨다.** 009는 **저부하에서 0건**, 014는 **포화에서 매 요청**이다. 같은
설정을 두 부하에서 재서 결과가 갈렸다는 뜻이고, 그러면 이 항목은 **포화에서만 판정된다.** 그래서
이 Task의 측정은 전부 포화이고 저부하 비교군을 두지 않았다. 4번을 못 봤으면 "저부하 Lighthouse로
버퍼 효과를 재 보자"는 군을 하나 넣었을 것이다.

## 1. 재현 — 이미 되어 있었다

재현을 새로 만들 필요가 없는 Task다. [014](014-seatmap-assembly-cost.md) 4.7절이 그대로 재현이다.

```
1차 측정 각 군 3회차: 처리량 7,000 req/s (정상 400), iteration당 수신 9.5KB (정상 248KB)
nginx 로그: no live upstreams 977,264 / 502 984,911 / 504 11,735
```

`max_fails`를 명시하지 않으면 nginx 기본값 **1회 실패 → 10초 배제**가 걸린다. 포화에서 타임아웃
하나가 BE 한 대를 10초간 배제하고, 남은 1대에 부하가 2배로 가서 그쪽도 배제되면 nginx는 요청을
즉시 502로 돌려준다. **일을 안 한 요청이 빠르게 끝나므로 처리량 지표는 17배 "개선"으로 보인다**
(교훈 1).

## 2. 판정 기준을 착수 전에 적었다

- **`max_fails`**: `no live upstreams`와 502·504가 **0건**이면 성공이다. **처리량은 판정 기준이
  아니다** — 이 수정의 목적은 빨라지는 것이 아니라 측정이 조용히 무효가 되지 않는 것이다
- **`proxy_buffers`**: `an upstream response is buffered to a temporary file`이 0건이면 성공.
  처리량 변화는 산포(040의 ±4%) 안이면 "효과 없음"으로 적는다
- **gzip**: 처리량 차이가 산포 안이면 채택하지 않는다. 기각이면 **코드째 지운다**(교훈 5)
- **로컬 캐시 재측정**: 014의 +29.5%가 고친 nginx에서도 산포 밖으로 유지되면 "재현됨"

## 3. 만든 것

### 3.1 `nginx.conf` — 두 줄이 아니라 두 판단

```nginx
server backend1:8080 max_fails=0;
server backend2:8080 max_fails=0;
```

**값을 올리는 게 아니라 껐다.** 이유 셋을 주석에 남겼다.

- `max_fails=5`처럼 올리는 것은 트립 **시점만** 늦춘다. 포화에서는 타임아웃이 금방 쌓이고,
  트립한 뒤의 연쇄는 같다
- **BE가 2대라서 배제의 이득이 0이다.** 셋 이상이면 한 대를 빼고 버티는 게 맞지만, 2대에서
  1대를 빼면 남은 쪽 부하가 2배가 되어 같은 일이 반복된다
- **끄더라도 진짜 죽은 BE는 우회된다.** `proxy_next_upstream` 기본값(`error timeout`)이
  **요청 단위로** 다음 업스트림을 시도하기 때문이다. 배제는 "다음 요청들까지 보내지 않는" 추가
  장치일 뿐이고, 끄면 잃는 것은 죽은 쪽으로 가는 커넥트 시도 1회의 비용이다

```nginx
proxy_buffer_size 16k;
proxy_buffers     32 16k;      # 256KB -> 512KB
proxy_busy_buffers_size 32k;   # 기본값을 명시만 했다
```

주석의 "좌석맵 응답이 약 59KB다(004_3 측정)"가 낡아서 256KB가 **248KB 응답에 여유 16KB**뿐인
상태로 남아 있었다. 10,000석 시드(009_2가 만든 것)는 응답이 약 1.2MB라 512KB로도 넘친다는 것을
한계로 같이 적었다.

### 3.2 하네스 — 산출물 5종 → 6종

`run-group.sh`가 실행마다 nginx 로그를 집계한다(`results/<tag>-<n>-nginx.txt`).

```
로그 줄 수            54449
no live upstreams     0
임시파일 버퍼링       0
502                   0
504                   0
```

**이게 이 Task의 영구 산출물이다.** 고친 설정은 다음에 누가 되돌릴 수 있지만, 집계가 남으면
17배를 채택하지 않는다. 014의 977,264건은 **사후에 손으로** 찾은 것이었다.

**총 줄 수를 같이 남기는 게 핵심이다.** 009 6.2절이 `error_log /dev/stderr`를 빈 파일로 읽어
"0건"을 증거로 쓸 뻔했다 — **빈 파일에서 나온 0건은 증거가 아니라 측정 실패다.** 줄 수가 0이면
경고를 찍는다.

### 3.3 `check-run.py`에 `seatmap-gzip` 프로필

압축 군은 `seatmap` 프로필의 수신 바이트 하한(200,000B)에 **전 군이 FAIL**로 걸린다. 압축이
걸리면 k6가 받는 바이트가 18.3:1로 줄기 때문이다(248,424 → 13,559B).

장치를 끄는 게 아니라 **무결성의 본체를 바이트에서 좌석 수로 옮겼다.** 이 파일이 이미 적어 둔
근거를 그대로 쓴다 — "바이트는 `schedule_seats.id` 자릿수에도 반응하므로 좌석 수가 더 믿을 만한
신호다." 압축은 그 덜 믿을 만한 축을 한 번 더 흔드는 변경이라, 압축 군에서는 `seatmap_seats`가
유일한 붕괴 탐지기다.

## 4. 측정

### 4.1 하네스와 조건

014 4.1절과 같다 — 회차 3,020개 × 2,000석(좌석 6,026,894행), DB 1,015MB, `shared_buffers` 128MB,
`CACHE_TYPE=none`, `QUEUE_ENABLED=false`, BE 2대 + nginx, k6까지 같은 호스트.
포화는 `VUS=300 THINK=0 DURATION=45s SAMPLE_SCHEDULES=600`이고 군마다 postgres를 재시작한 뒤
`run-group.sh`가 warmup 1회를 버린다.

군 사이에 바꾼 것은 **한 번에 하나씩**이다.

| 군 | 좌석맵 전략 | 압축 | 비고 |
|---|---|---|---|
| A | `single` | — | 014 D군(768.6)의 대조군 |
| B | `local` | — | 014 E군(995.1)의 대조군. B2·B3는 같은 조건 재측정 |
| C | `local` | **BE**(`server.compression`) | 009_1이 실제로 잰 수단 |
| D | `local` | **nginx**(`gzip on`, `gzip_comp_level 6`) | 압축 레벨을 C와 맞춰 바이트까지 동일하게 했다 |

### 4.2 `max_fails`와 `proxy_buffers` — 재현은 사라졌고 수치는 안 변했다

**모든 군의 모든 회차에서 `no live upstreams` 0 / 임시파일 버퍼링 0 / 502 0 / 504 0이다.**
로그 줄 수는 회차당 54,449~71,005줄이라 "안 읽힌 0건"이 아니다.

| 군 | nginx 수정 전 (014) | 수정 후 (이 Task) | 차이 |
|---|---|---|---|
| `single` | **768.6** req/s (767.3~769.9) | **780.6** (773.1~782.0) | +1.6% |
| `local` | **995.1** req/s (990.9~999.3) | **1004.8** (989.2~1009.3, 11점) | +1.0% |

**둘 다 040이 잡은 산포 ±4% 안이다.** 즉 이 수정은 처리량을 바꾸지 않았다.

**CPU도 안 움직였다.** 같은 하네스로 비압축 `local` 군의 컨테이너별 CPU를 다시 쟀다(부하 구간
중앙값, `docker stats`는 논리 스레드 기준이다).

| 지표 | 014 E군 (수정 전) | 이 Task B3군 (수정 후) |
|---|---|---|
| nginx | 97.9% | **101.1%** |
| postgres | 144.6% | 149.7% |
| BE 2대 합 | 279.9% | 269.2% |

**임시파일 버퍼링을 매 요청에서 0건으로 없앴는데 nginx CPU가 그대로다.** 240KB를 디스크 임시
파일로 쓰던 것이 실은 WSL2에 할당된 31.5GB 페이지 캐시에 머물러 진짜 디스크를 치지 않았을
가능성이 크다 — 012가 `shared_buffers`에서 본 것과 같은 모양이다.

> [!warning] 확인 필요
> 위 한 문장은 **추론이다.** 임시파일이 실제로 디스크에 닿았는지(`/var/cache/nginx`의 write
> 지연)를 재지 않았다. 확인하려면 컨테이너의 블록 I/O를 따로 떠야 하고 이번 범위 밖이다.

**교훈 7의 또 다른 판본이다** — "무엇이 줄어드는지"와 "무엇이 빨라지는지"는 매번 따로 확인해야
한다. 007은 버퍼 접근을 88% 줄였고, 012는 디스크 읽기를 0으로 만들었고, 이번에는 디스크 임시
파일을 없앴다. **셋 다 처리량이 안 변했다.**

그래도 `max_fails` 쪽은 값을 한다. **이 수정의 산출물은 수치가 아니라 "앞으로의 측정이 조용히
무효가 되지 않는다"는 것**이고, 그건 판정 기준에 착수 전부터 그렇게 적어 뒀다.

### 4.3 로컬 캐시 +29.5%가 재현됐다

| 군 | req/s (중앙값) | 014 대조 |
|---|---|---|
| A `single` | 780.6 | D군 768.6 |
| B `local` | **1004.8** | E군 995.1 |
| **차이** | **+28.7%** | +29.5% |

범위가 전혀 겹치지 않고(782.0 < 989.2) 040의 산포를 압도한다. **Task 036의 채택 근거는 고친
nginx에서도 유지된다.**

덤으로 `local` 군을 네 번에 걸쳐 **11점** 모았다(989.2~1009.3, **±1.0%**). 040이 `single`
계열에서 잡은 ±4%보다 훨씬 좁다 — 캐시 히트 경로가 DB 쪽 변동을 덜 받기 때문으로 보인다.
014가 "040의 ±4%를 직접 재지 않고 빌려 썼다"고 남긴 한계가 이쪽에서는 줄었다.

### 4.4 gzip — 포화에서도 기각이고, 어디서 압축하든 손해다

압축비는 **18.3:1**(248,424 → 13,559B/iter)로 009_1의 19:1과 같다. 좌석 수는 네 군 모두
min=2000이라 k6가 제대로 해제했다.

| 군 | 압축 위치 | 바이트/iter | req/s (중앙값) | B군 대비 | p95 |
|---|---|---|---|---|---|
| B | 없음 | 248,424 | **1004.8** | — | 292~335ms |
| C | **BE** | 13,559 | **893.3** (882.2~901.0, 5점) | **-11.1%** | 329~489ms |
| D | **nginx** | 13,551 | **828.9** (817.6~829.7) | **-17.5%** | 412~506ms |

**둘 다 산포 밖 손해다.** 009_1이 저부하에서 본 "+2.0ms(+29%)"가 포화에서 처리량 -11.1%로
나타났고, 방향이 같다. **재판단 조건 중 "포화 구간"은 이걸로 닫혔다.**

CPU가 왜 그런지까지 말해 준다.

| 군 | nginx | postgres | BE 2대 합 | 합계 |
|---|---|---|---|---|
| B3 비압축 | 101.1% | 149.7% | 269.2% | **520%** |
| C2 BE 압축 | **25.3%** | 131.4% | **499.1%** | **656%** |
| D nginx 압축 | **338.7%** | 123.3% | 224.7% | **687%** |

**압축이 프록시를 싸게 만드는 것은 사실이다** — BE가 압축하면 nginx가 101.1 → **25.3%**로 내려간다
(작아진 응답을 나르니 일이 줄어든다). 그런데 **그 절약 -75.8pp가 BE가 더 내는 +229.9pp를 전혀
못 메운다.** 009_1이 "한 호스트라서 아낀 바이트로 얻는 게 없다"고 적은 것의 포화 판본이고,
이번에는 pp 단위로 갈렸다.

**nginx 쪽이 더 나쁜 이유는 분산이다.** BE는 2대라 압축 CPU를 112%씩 나눠 내지만 **nginx는
1대라 338%를 혼자 낸다.** 모든 요청이 지나가는 단일 지점에 CPU를 얹은 것이고, 총 CPU도 31pp
더 든다(687 vs 656).

> [!warning] 확인 필요
> 총 CPU가 nginx 쪽에서 더 큰 이유는 **추정이다.** nginx는 upstream 응답을 버퍼에 받아서 압축하고
> chunked로 다시 내보내는 반면 BE는 직렬화하면서 압축 스트림에 바로 쓰므로 복사가 한 번 적다 —
> 그럴듯하지만 재지 않았다.

### 4.5 범위 밖 발견: 함정 둘을 밟았고 둘 다 "조건이 안 걸린" 종류였다

교훈 1이 말하는 "요청이 일을 안 해서 수치가 좋아지는" 함정은 이번에 안 밟았다. 대신 **설정이
의도와 다르게 걸려서 두 군이 같은 것을 잰** 일이 두 번 있었다.

**① `.env`에 `SEATMAP_STRATEGY=local`이 남아 있었다.** 036 측정 때 넣고 지우지 않은 값이다.
`single` 군을 잰다고 믿고 `local`을 쟀고, 처음 나온 988~1,000 req/s를 그대로 믿었으면
**"nginx 수정이 single을 768 → 995로 올렸다"**는 완전히 틀린 결론을 적었을 것이다. 잡아낸 것은
컨테이너 `env`를 직접 확인한 것이고, **033이 "셸 환경변수가 `.env`를 덮어 껐다고 믿으며 켜진
상태를 쟀다"로 남긴 함정의 재발**이다. 그때는 셸이 `.env`를 덮었고 이번에는 `.env`가 기본값을
덮었다 — 방향이 반대인데 증상은 같다.

**② k6는 `Accept-Encoding`을 기본으로 보내지 않는다.** BE 압축을 켜고 쟀는데 iteration당 수신이
248,424B로 비압축 군과 **소수점까지 같았다.** 압축을 켠 게 아니라 "켰지만 아무도 요구하지 않은"
상태를 잰 것이다. 층②의 실제 클라이언트인 Next(undici)는 이 헤더를 기본으로 보내므로(009_1
3.6절), 압축 군에서는 k6도 보내야 같은 것을 재는 것이 된다 — `ACCEPT_ENCODING` 환경변수를
하네스에 넣었다.

**②가 잡힌 경로가 중요하다.** 무결성 검사가 **FAIL이 아니라 OK로** 잡아냈다 — 압축 군에
`seatmap-gzip` 프로필(하한 10,000B)을 쓰고 있었는데 수신이 248KB로 통과한 것이다. 기대값이
"작아야 한다"인 군에서 큰 값이 통과했으니 조건이 안 걸린 것이다. **프로필을 따로 만들지 않고
하한만 낮췄다면** 두 군의 수치가 같은 것을 보고 "압축은 무해하다"로 적었을 것이다.

## 6. 한계

- **처리량이 안 변한 이유를 `max_fails` 쪽에서 분리하지 못했다.** 두 설정을 한 번에 고쳤다.
  각각의 기여를 가르려면 군이 둘 더 필요한데, 014가 수정 전 조건을 이미 기록했고 **둘 다
  "재현 제거"가 목적이라** A/B를 하지 않기로 착수 전에 정했다
- **임시파일이 진짜 디스크에 닿았는지 모른다.** 4.2절의 `확인 필요`가 그것이다. 페이지 캐시
  가설이 맞으면 **메모리가 작은 기계에서는 이 수정이 효과를 낼 수 있다** — 그쪽은 안 쟀다
- **gzip을 `single` 전략에서 재지 않았다.** `local`에서만 봤다. 캐시가 꺼진 상태에서는 BE CPU
  여유가 더 적으므로 손해가 더 클 것으로 보이지만 측정은 아니다
- **`gzip_comp_level`을 C군과 맞추느라 nginx 기본값(1)을 쓰지 않았다.** 레벨 1은 바이트가
  5,092B(레벨 6은 3,653B)라 CPU가 덜 든다 — **nginx 압축의 가장 유리한 설정은 재지 않았다.**
  다만 그 군은 "바이트도 다른" 비교가 되므로 C군과 나란히 놓을 수 없다
- **호스트 분리는 여전히 열려 있다.** 009_1의 재판단 조건은 "포화 **또는** 호스트 분리"였고
  포화만 닫았다. **4.4절의 "nginx CPU 101.1 → 25.3%"가 그 조건의 근거를 오히려 강화한다** —
  BE와 Next 사이에 진짜 네트워크가 끼면 아낀 235KB가 비용이 되고, 프록시 쪽 절약도 그대로다.
  Task 038(전용 부하 노드) 또는 034(배포)에서 다시 본다
- **k6가 같은 호스트에서 돈다**(006의 첫 한계, 038이 미해결). 압축 군에서는 k6가 **해제** 비용도
  내므로 이 한계가 비압축 군보다 더 크게 작용한다 — gzip 손해의 일부가 생성기 몫일 수 있다.
  방향은 기각 쪽이라 결론은 안 바뀌지만 **-11.1%는 상한으로 읽어야 한다**
- **저부하 p95를 다시 재지 않았다.** 014와 같은 선택이고, 009_1의 저부하 수치와 이어붙지 않는다
