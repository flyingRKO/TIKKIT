# 014. 좌석맵 조립 비용 — 로컬 캐시 (Task 036)

| 항목 | 내용 |
|---|---|
| 문제 | 좌석맵 포화가 768.6 req/s에서 막히고 벽은 **Postgres CPU 390%(약 4코어)** 다. 그 4코어는 2,000행 튜플 구성과 237KB 전송이라 `shared_buffers`로 I/O를 0으로 만들어도 안 줄었다(012) |
| 결론 | **로컬 캐시(Caffeine)를 채택했다.** 포화 **768.6 → 995.1 req/s(+29.5%)**, Postgres CPU **390.1% → 144.6%(-62.9%)**, DB 내부 실행 시간 요청당 **14.85 → 1.98ms(-86.7%)**. 적중률 99.4% |
| 단 | **상한이 작업 집합보다 작으면 이득이 사라진다.** 600회차를 200칸에 담은 군은 적중률 33.5%에 +1.7%(산포 안)이고, 축출 52,768건이 만든 쓰레기 때문에 **힙을 오히려 더 썼다**(Old Gen 311 → 497MB) |
| 유지되는 기각 | 좌석맵을 **Redis에** 올리는 것(029), 응답 축소(033), 커버링 인덱스·`shared_buffers` 상향(040) |

---

## 1. 이 Task는 "안 재본 것"을 재는 게 아니었다

착수 전에 근거 문서를 열어 보니 **로드맵이 세 군데 틀렸다.** Phase 11 규칙("근거 문서를 먼저 읽고
어긋나면 로드맵부터 고친다")대로 측정 전에 고쳤고, 그 과정에서 이 Task의 질문 자체가 바뀌었다.

| 로드맵 | 원문 |
|---|---|
| "25.50ms 중 조립 17.46ms(68%)"의 근거가 007 | **010 9.2절**이다. 007에 그 숫자가 0건이고, 좌석맵 미배정 항목도 010 15절이다 |
| "Caffeine에는 029의 기각 근거가 적용되지 않는다" | 원문(010 8.3·15절)은 **조건절** "기각 근거가 Redis의 역직렬화 비용이었다면". 로드맵이 단정으로 바꿨다 |
| Task 044의 "구조 분해가 그 Task의 절반" | **029가 이미 했다.** 쿼리 분리 구조를 만들어 측정하고 되돌렸다 |

두 번째가 핵심이다. **008 4.1절이 Caffeine을 이미 쟀고 네 군 중 가장 빨랐다.**

| 029의 군 | 좌석맵 전체 p95 | 생성(DB+조립) p95 | 적중률 |
|---|---|---|---|
| A. 단일 쿼리 (현행) | 6.63 ms | — | — |
| A′. 분리, 캐시 off | 8.62 ms | 6.89 ms | — |
| **B. Caffeine (로컬)** | **4.98 ms** | **2.79 ms** | 97.0% |
| C. Redis (공유) | 7.22 ms | 5.50 ms | 99.97% |

008이 로컬을 안 고른 이유는 역직렬화가 아니라 셋이었다 — ① 힙 용량(회차 3,000개면 1.15GB)
② 분산 evict가 반쪽(만료 배치가 `@SchedulerLock`으로 한 인스턴스에서만 돈다) ③ "대안이 응답
축소다". **③은 010 9.3절이 기각했고**(바이트 -49.4%인데 처리량 +1~7%), ②는 이 설계에 적용되지
않는다(3절). ①만 남았다.

그리고 008이 직접 남긴 반례 조건이 아직 열려 있었다.

> 이 기각은 "이 규모에서"가 아니라 "값이 큰 캐시 일반"에 대한 판단이다. 다만 반례가 있을 수
> 있다 — **DB가 포화에 가까워지면 "DB를 안 가는 것" 자체의 가치가 올라가므로**, 역직렬화
> 비용을 내고도 이득일 수 있다. Task 033 breakpoint에서 다시 볼 후보로 남긴다. (008 4.2절)

010 8.3절이 "구현이 코드에 없어서 이 Task 안에서 답할 수 없다"고 못 닫은 자리다. 그리고 **040이
벽을 Postgres CPU 4코어로 특정해 그 반례 조건을 측정으로 세웠다.** 즉 이 Task의 질문은
"로컬 캐시가 이득인가"(이미 답이 있다)가 아니라 **"그 warning이 포화에서 뒤집히는가"** 였다.

> [!note] 전달 손실이 두 단계였다
> 008이 근거 셋을 들었는데 010이 그중 하나만 **조건절로** 옮기고, 로드맵이 그 조건절을
> **단정으로** 요약했다. 한 번 좁혀지고 한 번 단정이 되면 원문과 반대가 된다 —
> 로드맵은 "로컬 캐시는 안 쟀다"로 읽혔다. `README.md` 교훈 6에 네 번째 사례로 올렸다.

## 2. 판정 기준을 착수 전에 적었다

저부하 p95는 이미 알고 들어갔다(-25%). **교훈 2대로 그걸로 판정하지 않았다.**

- **채택**: 포화 처리량이 **+4% 초과**(040의 9회 산포 736~796 밖)이고 Postgres CPU가 같이 내려갈 때
- **조건부**: 처리량은 산포 안인데 CPU만 내려가면 "용량 여유는 생겼고 처리량 이득은 없다"로 기록
- **기각**: 둘 다 안 움직이거나 힙 상한이 실용 범위를 못 만들 때. 그러면 토글째 지운다(교훈 5)

이득 천장도 알려져 있었다 — 008 4.3절이 전체−생성 차이가 어느 군에서나 **1.7~2.2ms로 일정**하다고
쟀다. 응답 시간의 약 30%는 캐시로 줄일 수 없다.

## 3. 왜 이 캐시에는 무효화가 필요 없나

캐시에 담는 것은 `ScheduleSeatResponse` 8필드 중 **`status`를 뺀 7개**다(좌표·구역·행·번호·등급 id).
그 7개를 런타임에 바꾸는 코드 경로가 **0건**이다.

- 좌석 상태를 바꾸는 조건부 UPDATE 3개(`holdSeats`/`markSold`/`releaseSeats`)와 만료 배치가
  전부 `status`·`reservation_id`·`updated_at`만 SET한다
- `Seat`·`ScheduleSeat` 엔티티에 좌표·등급 변경 메서드가 없다(생성자만 있다)

그래서 `@CacheEvict`가 없고 TTL(10분)은 무효화 수단이 아니라 **안전망**이다 — 좌석 구성을
마이그레이션으로 바꿨을 때 재기동 없이 따라오게 하는 정도다. `gradePrices`가 가격만 캐시하고
잔여 수량을 매번 세는 것과 같은 선이다.

**이것이 008의 기각 근거 ②를 무효화한다.** evict가 필요한 것은 "변하는 값을 캐시했기 때문"인데
여기서는 변하는 값을 캐시하지 않는다. 그리고 같은 이유로 **BE 2대가 서로 다른 값을 들 수가 없다** —
4.5절에서 이것이 로드맵 Phase 12에 어떤 영향을 주는지 적는다.

조립 경로는 캐시된 배치를 순서대로 돌며 상태 맵에서 꺼내 응답을 만든다. 상태 맵에 없는 좌석은
응답에서 빼고 **경고를 남긴다** — 일어나지 않는 경우이지만 조용히 넘기면 없는 좌석이
AVAILABLE로 보인다(교훈 4).

## 4. 측정

### 4.1 하네스와 조건

040과 같다 — 600만 행(회차 3,020개 × 2,000석), DB 1,014MB, `shared_buffers` 128MB,
`CACHE_TYPE=none`, `QUEUE_ENABLED=false`, BE 2대 + nginx, k6까지 같은 호스트.
포화는 `VUS=300 THINK=0 DURATION=45s SAMPLE_SCHEDULES=600`이고 `run-group.sh`가 warmup 1회를
자동으로 버린다.

**040의 B군 776 req/s가 이번 D군 768.6으로 1.0% 차이로 재현됐다.** 하네스가 같은 것을 보고 있다는
확인이고, 이 Task의 비교값이 012와 이어붙는다는 뜻이다.

새로 만든 것: `pg_stat_statements`(compose `command` + `sql/08`·`09`, 012 8절이 "036의 입구"로 지정),
`sample-container-cpu.sh`(컨테이너별 CPU 2초 샘플링), `sql/06`에 `pg_stat_statements_reset()`,
`run-group.sh` 산출물 4종 → 5종.

### 4.2 처리량과 CPU — 채택

| 군 | 전략 | 상한 | req/s (2회) | Postgres CPU | BE 2대 | nginx | 적중률 | Old Gen |
|---|---|---|---|---|---|---|---|---|
| **D** | `single` | — | **768.6** (767.3~769.9) | **390.1%** | 273.1% | 79.1% | — | ~45MB |
| **E** | `local` | 700 | **995.1** (990.9~999.3) | **144.6%** | 279.9% | 97.9% | **99.4%** | 311MB |
| **F** | `local` | 200 | **781.4** (777.1~785.7) | 345.0% | 300.3% | 80.3% | 33.5% | **497MB** |

> **Task 039가 고친 nginx에서 다시 쟀고 재현됐다.** `single` 768.6 → **780.6**,
> `local` 995.1 → **1004.8** req/s로 **+28.7%**다(둘 다 040의 산포 ±4% 안에서 같은 값이다).
> 아래 4.7절이 넘긴 `max_fails`·`proxy_buffers`를 고쳐도 **이 Task의 채택 근거는 그대로**이고,
> 포화 CPU 분포(postgres 149.7% / BE 269.2% / nginx 101.1%)도 E군과 거의 같다.
> 자세한 것은 [015](015-nginx-saturation.md) 4.2~4.3절.

D → E가 **+29.5%**이고 범위가 전혀 겹치지 않는다. 040의 산포(±4%)를 압도하므로 교훈 8의
"산포를 모르면 3%를 채택한다"에 걸리지 않는다. Postgres CPU도 **-62.9%** 로 같이 내려갔다 —
채택 조건 둘 다 충족이다.

**040이 특정한 벽이 실제로 그 벽이었다.** 012가 "그 4코어는 I/O가 아니라 2,000행 튜플 구성과
237KB 전송이고, 그래서 `shared_buffers`로 I/O를 0으로 만들어도 안 줄어든다"고 적었는데,
캐시 히트가 그 쿼리를 아예 안 돌리니 4.0코어가 1.45코어가 됐다.

### 4.3 F군이 008의 기각 근거 ①을 되살렸다 — 방향은 반대다

상한을 200으로 내리면(600회차를 200칸에) 적중률이 33.5%가 되고 **처리량 이득이 +1.7%로 산포 안에
들어간다.** 즉 이 캐시는 작업 집합을 담아야 의미가 있다.

그런데 008이 예상한 것과 방향이 반대다. 008은 "보관 가능한 회차 수가 힙에 묶인다"고 적었는데,
**상한을 줄이면 힙이 더 든다**: Old Gen 311MB(E) → **497MB**(F). 축출 52,768건이 만든 쓰레기다.
캐시가 작으면 미스마다 2,000행을 다시 꺼내 객체를 만들고 그게 바로 쓰레기가 되므로, **상한을
줄이는 것으로 힙을 아낄 수 없다. 담거나 안 하거나다.**

회차당 약 420KB를 본다(E군 311MB 중 기본 사용량 ~45MB를 빼고 600으로 나눈 값). 008이 Redis
직렬화 기준으로 추정한 384KB와 같은 자리수이고, **"회차 3,000개면 1.26GB"도 008의 1.15GB와
맞는다** — ①의 수치 자체는 틀리지 않았다.

### 4.4 쿼리 단위로 쪼갰다 — 012 8절이 남긴 입구

`pg_stat_statements`로 본 좌석맵 경로의 **DB 내부 실행 시간**이다(요청당 평균).

| 군 | 쿼리 | calls | mean | total |
|---|---|---|---|---|
| A `single` | 배치+상태 단일 조회 | 16,984 | **14.850 ms** | 252,220 ms |
| B `split` | 배치만 | 18,043 | 13.871 ms | 250,272 ms |
| | 상태만 | 18,040 | 3.256 ms | 58,739 ms |
| | **합계** | | **17.127 ms** | 309,011 ms |
| C `local` | 상태만 | 26,738 | **1.982 ms** | 52,993 ms |

**분리 자체가 DB 시간을 늘린다**(14.85 → 17.13ms, +15%). 029가 p95로 본 "+30% 순손실"의 DB 쪽
몫이고, 처리량에서도 같은 방향이 나왔다(4.6절). 캐시를 켜면 **14.85 → 1.98ms(-86.7%)** 다.

C군의 상태 쿼리가 B군보다 빠른 것(3.256 → 1.982ms)도 방향이 맞다. 호출 수는 더 많은데
(18,040 → 26,738) 더 빠르다 — DB 경합이 줄어서 같은 쿼리가 빨라진 것이다.

### 4.5 범위 밖 발견: 이 결과가 Phase 12의 전제를 바꾼다

로드맵 Phase 12(모놀리스 + 카프카)의 경로 A는 "로컬 캐시 무효화 전파"이고 Task 044·045가 그
근거다. 그런데 **이 캐시에는 무효화가 없다**(3절). 그러면

- Task 044가 재현하려는 "BE 2대가 서로 다른 좌석 상태를 내려주는 화면"이 **만들어지지 않는다**
- Task 045의 Redis Pub/Sub → 카프카 전환은 전파할 메시지가 없다

불일치를 만들려면 **상태까지 캐시해야 하는데, 그건 008부터 이 레포가 일관되게 거부해 온
선택이다**(매진이 TTL만큼 늦게 보인다). 즉 경로 A는 "캐시가 이득인가"에서는 살아남았지만
"그 캐시에 무효화가 필요한가"에서 막힌다. 로드맵에 그대로 반영했다.

**카프카 근거 셋 중 Phase 13(실패와 보상)은 그대로다** — 002가 남긴 실재 버그이고 036과 무관하다.

### 4.6 1차 측정에 순서 편향이 있었다 — 040이 왜 군마다 재시작했는지 알았다

처음 A·B·C를 연속으로 돌렸을 때 A군이 **402.7 req/s**였다. 같은 코드·같은 설정의 D군이 768.6인데
절반이다. 차이는 **OS 페이지 캐시 온도**뿐이었다 — 시드 직후라 1차는 cold에서 출발해
A → B → C 순으로 데워졌고, **뒤 군이 유리한 편향**이 있었다.

040의 재현 절차가 군마다 `docker restart tikkit-postgres-prod`를 끼운 이유가 이것이다
("모든 군이 cold에서 출발한다. warmup 1회를 버려 조건을 맞춘다"). **`run-group.sh`의 warmup은
군 내부만 데운다 — 군 사이의 조건은 맞춰주지 않는다.** 그걸 놓쳤다.

다행히 결론은 안 바뀌었다. 1차 +26.8% vs 2차 +29.5%로 이득 폭이 같고, 1차의 B군(369.5)이 A군
(402.7)보다 **뒤에 돌아 유리한 조건인데도 -8.2%** 라 분리 손해는 실재한다. 주 수치는 2차를 쓴다.

### 4.7 범위 밖 발견: nginx `max_fails` 미명시가 포화에서 터졌다

1차 측정의 **각 군 3회차만** 무결성 검사에서 떨어졌다. 처리량이 7,000 req/s로 뛰고(정상 400)
iteration당 수신이 **9.5KB**였다(정상 248KB). 교훈 1이 적은 그대로다 — "수치가 좋아지는 가장
흔한 이유는 요청이 일을 안 한 것이다."

nginx 로그에서 원인이 나왔다: **`no live upstreams` 977,264건, 502 984,911건, 504 11,735건.**
upstream에 `max_fails`/`fail_timeout`을 명시하지 않아 기본값(1회 실패 → 10초 배제)이 걸렸고,
포화에서 타임아웃 하나가 BE를 10초간 배제하면 남은 1대에 부하가 2배로 가서 그쪽도 배제되고,
그러면 nginx가 요청을 즉시 502로 돌려준다. **처리량 지표만 보면 17배 "개선"으로 보인다.**

**009·009_1·010이 전부 넘기고 Task 039가 "곁딸린 nginx 미해결 2건"으로 적어둔 항목이다.**
같은 로그에 다른 하나도 찍혔다 — `an upstream response is buffered to a temporary file`,
즉 **240KB 좌석맵 응답이 매 요청 디스크 임시 파일을 거친다**(`proxy_buffers` 여유 16KB).
둘 다 039로 이관한다. 이 Task에서 고치지 않은 이유는 측정 조건을 바꾸면 A·B·C를 전부 다시
재야 하고, 유효 실행 3점씩으로 판정이 이미 섰기 때문이다.

### 4.8 범위 밖 발견: `pg_stat_statements.track=all`의 오버헤드가 무시할 만하다

2차 측정 전에 `ALTER SYSTEM SET pg_stat_statements.track='none'` + `pg_reload_conf()`로 수집을
끄려 했는데 `SHOW`가 계속 `all`을 돌려줬다. `pg_settings`를 보니 `context=superuser`,
`pending_restart=f`인데 값은 `all`이었다.

**compose의 `command: -c pg_stat_statements.track=all`이 커맨드라인 인자라서
`postgresql.auto.conf`보다 우선순위가 높다.** 즉 `ALTER SYSTEM`으로는 덮을 수 없다.

그래서 2차 측정도 pgss가 켜진 상태로 돌았는데, 그 D군이 040(pgss 없음)을 1.0% 차이로 재현했다.
**`track=all`의 오버헤드가 이 워크로드에서 산포 안**이라는 뜻이다. 끄려던 시도가 실패해서 얻은
답이고, 덤으로 1차 A군이 느렸던 이유가 pgss가 아니라 cold였다는 것도 갈렸다(4.6절).

## 5. 만든 것

| 파일 | 내용 |
|---|---|
| `CacheProperties` | `seatmap`(single \| local), `seatmapMaxEntries`, `seatmapTtl` |
| `CacheConfig.seatmapCacheManager` | `CaffeineCacheManager`. `@Primary`가 아닌 쪽이라 이름으로 지정한다 |
| `SeatLayoutCache` | `@Cacheable(cacheManager = "seatmapCacheManager")`. 008 3.1절의 자기호출 함정을 피해 빈을 분리했다 |
| `ScheduleSeatLayoutRow` | 불변 7필드. 029가 만들었다 지운 record를 되살렸다 |
| `ScheduleSeatRepository` | `findSeatLayoutByScheduleId`(캐시 대상), `findSeatStatusesByScheduleId`(실시간) |
| `ScheduleService.assembleFromLayout` | 배치 + 상태 합성. 상태 없는 좌석은 빼고 경고 |
| `SeatmapLocalCacheQueryCountTest` | 미스 3문장 / 히트 2문장 고정, 응답이 단일 쿼리와 동일한지, 선점 직후 상태 즉시 반영 |

**`CacheManager`를 둘로 둔 이유는 측정이다.** 좌석맵만 로컬이고 카탈로그는 Redis에 남는다.
`cache.type`을 건드려 전부 로컬로 돌리면 군 사이에 카탈로그 캐시 조건이 달라져 처리량 변화를
좌석맵에 귀속할 수 없다. 실제로 이 분리 덕에 "분리 손해 -8.2%"와 "캐시 이득 +29.5%"를 따로 적을
수 있었다.

**측정 전용이던 `split` 전략은 판정 후 지웠다**(교훈 5). 수치는 4.4·4.6절에 남아 있고, 분리 손해를
다시 재야 하면 상한을 1로 낮추면 같은 방향을 볼 수 있다.

**쿼리 카운트**: 기존 21개 경로의 숫자가 하나도 안 바뀌었다(기본 전략이 `single`이므로).
`local` 경로는 미스 3문장(존재 확인 + 배치 + 상태) / 히트 2문장이다. **히트가 1이 아닌 게
핵심이다** — 상태를 캐시하면 팔린 좌석이 TTL 동안 "선택 가능"으로 보인다.
