## 1. 왜 만들었나

009_2가 정적 좌석을 등급별 `<path>`로 합쳐 10,000석 DOM 노드를 10,245 → 4,253으로 줄이고
하이드레이션 무스로틀 TBT를 53 → 0ms로 만들었다. 그런데 **클릭 비용은 32.5 → 32.5ms로 한 톨도
안 움직였다**(009_2 6.5절). `StaticSeatLayer`가 이미 `memo`로 끊겨 있어서 클릭 때 안 돌았기
때문이고, 남은 비용은 **선택 가능 레이어**(2,000석 800개 / 10,000석 4,000개) 몫이었다.

009_2는 그 사실을 적으면서 "이 Task가 남기는 가장 큰 레버"라고 지목했고, ROADMAP이 Phase 11의
1순위로 받았다. **부하 생성기가 전혀 필요 없는 유일한 큰 항목**이라 Task 038(전용 부하 노드)의
한계를 안 받는 것도 1순위 근거였다.

## 2. 원인 진단을 정정한다

### 2.1 ROADMAP과 improvements/README가 같은 오진을 적고 있었다

둘 다 원인을 **"`selectedSeatIds.includes(seat.id)`가 좌석마다 O(n)"** 으로 적었다.
**그런데 009 4.8절이 그걸 이미 실측으로 배제해 뒀다** — 선택 깊이별 비용을 쪼개 쟀더니 평탄했고,
그 이유도 적혀 있다. 선택 상한이 4매(BE `@Size(max = 4)`)라서 `includes()`가 도는 배열 길이가
최대 4이고, 수천 개를 다시 그리는 비용이 그걸 완전히 가린다.

이번 기준선에서도 그대로 재현됐다.

| 선택 좌석 수 | 10,000석 before commit |
|---|---|
| 0 → 1 | 29.7 ms |
| 1 → 2 | 29.8 ms |
| 2 → 3 | 29.7 ms |
| 3 → 4 | 30.4 ms |

**깊이가 4배가 되는 동안 비용이 2% 움직였다.** `includes()`가 원인이면 여기서 기울기가 보여야 한다.

> 이 오진을 고치지 않았으면 `Set` 전환부터 시도해서 한 라운드를 버렸을 것이다. 009 4.8절이
> 같은 항목을 "이 규모에서 이득 없음"으로 **기각**해 둔 것을, 읽지 않고 ROADMAP에 원인으로
> 올려 둔 셈이다. **기각 기록은 남겼는데 그 기록이 다음 문서로 전달되지 않았다.**

### 2.2 실제 비용은 좌석당 반복이었고, 트리거가 둘이었다

클릭 한 번에 `SeatMap` 함수 전체가 다시 돌면서 좌석마다 이게 반복됐다.

| 좌석당 반복 작업 | 10,000석에서 |
|---|---|
| `cn(...)` 4인자 — tailwind 클래스 병합 | 4,000회 |
| `selectedGrade.price.toLocaleString()` — Intl | 4,000회 |
| `formatSeatLabel(seat)` — 문자열 조립 | 4,000회 |
| `seatX`/`seatY` 산술 + `rowY` 객체 조회 | 4,000회 |
| **인라인 ref 콜백** — 매 렌더 새 참조라 ref detach/attach | 4,000회 |
| 인라인 `onClick`/`onKeyDown` 화살표 생성 | 8,000회 |
| vdom 엘리먼트 생성 + props 재조정 | 4,000개 |

그리고 **트리거가 두 개였다.** `onClick`이 `onToggleSeat(seat.id)`와 `setFocusIndex(index)`를
둘 다 호출했다. 선택을 완벽히 끊어도 **roving tabindex가 혼자서 4,000개를 다시 돌린다.**
선택만 보고 설계했으면 수치가 안 움직였을 것이다.

### 2.3 before를 다시 쟀다 — 세션을 건너서도 맞았다

009_2 2.3절과 같은 방식으로 교차 확인했다.

| 지표 | 009_2 6.5·6.4절 | 이번 재측정 | 차이 |
|---|---|---|---|
| 토글 commit (2,000석) | 7.1 ms | 6.75 ms | -4.9% |
| 토글 commit (10,000석) | 32.5 ms | 30.3 ms | -6.8% |
| 리스너 (2,000 / 10,000) | 1,134 / 4,335 | 1,134 / 4,335 | **0%** |
| DOM 노드 (2,000 / 10,000) | 1,053 / 4,253 | 1,054 / 4,254 | +1개 |
| heap KB (2,000 / 10,000) | 4,476.99 / 7,254.11 | 4,475.36 / 7,247.82 | -0.04% / -0.09% |
| 선택 4매 Script 증가 (10,000석) | +146.54 ms | +135.49 ms | -7.5% |

**리스너는 개수까지 똑같이 나왔다.** 이번 세션의 before를 기준으로 삼는다.

## 3. 군을 둘로 나눴다

한 번에 다 적용하면 "레이어 분리가 벌어준 몫"이 총합에 묻힌다. 009_2가 `items123`/`final`을
따로 재서 "path 합치기가 Layout을 79% 줄였다"는 틀린 귀속을 막은 전례를 따랐다.

| 군 | 내용 |
|---|---|
| **before** | main 기준 |
| **C+** | 좌석별 `memo` + 이벤트 위임 + 핸들러 안정화 + 좌석당 반복 제거. 선택·포커스는 여전히 props |
| **final** | 선택·포커스를 레이어 props에서 **완전히** 제거 |

**C+를 안 쟀으면 "레이어 분리가 30.3 → 0.4ms를 만들었다"로 적었을 것이다.** 실제로는 C+가
30.3 → 3.4ms를 하고 final이 나머지를 했다. 두 변경의 성격이 완전히 다르므로 귀속이 중요하다.

### 3.1 C+ — 좌석별 memo로 어디까지 가나

- `SeatMap`을 `SeatMap`(svg 셸) / `SelectableSeatLayer`(memo) / `SelectableSeat`(memo) 셋으로 쪼갰다
- 좌표·`aria-label`·클래스 문자열을 레이어의 `useMemo`에서 **한 번만** 만든다 (Intl 호출 4,000 → 1)
- 핸들러를 좌석마다 달지 않고 `<g>` 하나에 **위임**했다
- `seatRefs` 배열과 인라인 ref 콜백을 없앴다
- `seat-selector.tsx`의 선택 상태를 `useReducer`로 합쳤다 (3.2절)

결과: 10,000석 30.3 → **3.4ms**. 2,000석 6.75 → **1.0ms**. 그런데 **비가 3.4배로 여전히
좌석 수를 따라간다.** 자식이 render를 건너뛰어도 부모는 엘리먼트 4,000개를 계속 만든다.

### 3.2 `useReducer`가 필요했던 이유 — memo의 선행 조건

`handleToggleSeat`이 `useCallback` 없이 매 렌더 새 참조로 내려가고 있었다. **핸들러 하나가
새 참조면 좌석 수천 개의 memo가 전부 무효화된다.**

고정 참조로 만들려면 핸들러가 `selectedSeatIds`를 클로저로 읽지 않아야 하는데, **상한 초과
판정이 현재 선택 수에 달려 있고 그때 안내 문구를 띄워야 했다.** `useState`의 함수형 업데이트
안에서는 안내를 띄울 수 없다 — 업데이터는 순수해야 하고 StrictMode에서 두 번 돌 수 있다.

그래서 "고른 좌석"과 "안내 문구"를 한 reducer로 합쳤다. `dispatch`는 React가 영구 안정 참조로
보장하고 `quantity`는 URL 쿼리에서 온 prop이라 이 화면에서 안 바뀐다.

> 최신값 ref(`selectedIdsRef`)로 끊는 방법도 있었지만 쓰지 않았다. `useActionState`가 전환
> (transition) 안에서 렌더하므로, 버려지는 렌더가 ref를 커밋되지 않은 값으로 남길 수 있다.

### 3.3 final — 레이어를 선택 상태에서 완전히 떼어낸다

`SelectableSeatLayer`의 props에서 `selectedSeatIds`와 `focusIndex`를 뺐다. 남은 props가
**세션 중에 하나도 안 바뀐다.**

| 상태 변화 | 레이어가 다시 그려지나 |
|---|---|
| 좌석 선택/해제 | ✗ |
| 안내 문구 변경 | ✗ |
| **줌 변경** | ✗ — 줌이 SVG `transform`이 아니라 **바깥 div 폭**이다 |
| 등급 변경 | 라우트 이동이라 마운트부터 다시 |

**줌 구현이 이 설계를 가능하게 했다.** 줌이 SVG 안에 있었다면 `zoomIndex`가 레이어 props로
내려가서 이 분리가 성립하지 않는다. 009 시절에 다른 이유(확대 배율을 컨테이너가 정한다)로
고른 구조가 여기서 값을 했다.

## 4. 두 가지 설계 제약이 해법을 정했다

### 4.1 `aria-checked`를 좌석에서 뗄 수 없다

`role="checkbox"`의 의미론이기도 하지만, **측정 하네스가 그 속성 변경을 t1 신호로 쓴다**
(`seat-interaction.spec.ts`, 009 3.2절이 못 박은 계약). `booking-flow.spec.ts`도
`getByRole("checkbox")`에 의존한다. 즉 **클릭한 좌석의 `aria-checked`는 계속 바뀌어야 하고,
나머지 3,999개는 안 바뀌어야 한다.**

그래서 `SeatMap`에 layout effect를 두고 **이전 선택과 현재 선택의 차집합만** 쓴다. 만지는
요소가 최대 9개(해제 4 + 선택 4 + 포커스 1)다. React 상태가 여전히 진실의 원천이고 DOM 쓰기는
그 투영일 뿐이라, **선점 실패 리셋도 저절로 처리된다.**

### 4.2 왜 이벤트 핸들러가 아니라 layout effect인가

핸들러에서 바로 쓰면 t1이 클릭 직후 **0.0x ms**가 된다. 수치는 좋아지지만 그건 개선이 아니라
**자를 부러뜨린 것**이다 — t1의 정의가 "React 커밋"이기 때문이다. layout effect는 커밋 단계에서
DOM 변경 뒤·페인트 전에 돌아서 그 정의를 그대로 유지한다.

이걸 안 지켰으면 "클릭 비용 0.05ms"라고 적고 **before와 다른 것을 잰 줄 몰랐을 것이다.**

### 4.3 JSX의 `aria-checked`를 상수로 두는 것이 안전장치다

React는 DOM이 아니라 **이전 렌더의 props**와 비교한다. 좌석 JSX가 `aria-checked={false}`
상수면, 레이어가 다시 그려져도 React는 그 속성에 손대지 않는다 — 우리가 쓴 값이 살아남는다.
등급 변경처럼 좌석이 통째로 리마운트되는 경우만 JSX 초기값으로 돌아가고, 그때는 같은 커밋의
layout effect가 복원한다(페인트 전이라 깜빡임이 없다).

> 위험: 누가 나중에 `aria-checked={selected}`로 되돌리면 **두 주체가 같은 속성을 두고 싸운다.**
> 주석으로 못 박았고, `dom-memory.spec.ts`가 선택 상태의 rect를 세는 것이 그 회귀의 그물이다.

## 5. 관문

### 5.1 Tailwind 유틸리티는 요소 수만큼 HTML에 복사된다 — 이번 Task에서 가장 비싼 실수

선택 표시를 CSS로 뽑으면서 좌석 클래스에 `aria-checked:stroke-foreground`,
`aria-checked:[stroke-width:1.5]`, `aria-checked:hover:opacity-100`을 넣었다. 동작은 완벽했다.

| 문서 HTML 전체 | before | 유틸리티를 좌석마다 | 자식 선택자로 올린 뒤 |
|---|---|---|---|
| 2,000석 | 649.88 KB | 723.35 KB (**+11.3%**) | **636.79 KB (-2.0%)** |
| 10,000석 | 3,111.46 KB | 3,478.68 KB (**+11.8%**) | **3,045.25 KB (-2.1%)** |

클래스 문자열이 **요소마다 HTML에 그대로 복사**되므로, 좌석 4,000개에서는 "CSS 한 줄"이 아니라
**HTML 367KB**다.

**같은 함정을 같은 파일에서 두 번 밟을 뻔했다.** 이벤트 위임을 설계할 때 `data-seat-index`를
좌석당 23B(10,000석 +2.9%)라는 이유로 기각해 놓고, 바로 다음 줄에서 +11.8%를 만들었다.
한쪽만 지키면 앞뒤가 안 맞는다.

고친 방법은 선택 규칙을 좌석이 아니라 **좌석을 담는 `<g>`에 자식 선택자 변이자로 한 번만**
올리는 것이다.

```
[&>rect[aria-checked=true]]:stroke-foreground
[&>rect[aria-checked=true]]:[stroke-width:1.5]
[&>rect[aria-checked=true]]:hover:opacity-100
```

생성되는 CSS는 `.<클래스> > rect[aria-checked=true] { ... }`이고, 이 문자열은 문서에 **딱 한 번**
들어간다. 덤으로 좌석마다 찍히던 `stroke-width="0"` 속성이 사라져서(SVG 기본 `stroke`가 `none`이라
폭이 얼마든 안 보인다) **문서가 기준선보다 2% 작아졌다.**

### 5.2 `data-seat-index`를 안 쓰면 O(n)이 하나 남는다 — 숨기지 않는다

이벤트 위임이 좌석 인덱스를 **형제 중 위치**(`indexOf.call(group.children, target)`)로 찾는다.
네이티브 포인터 비교라 4,000개를 훑어도 µs 수준이지만, **엄밀히는 클릭당 O(n) 스캔이 하나
남는다.** 그래서 이 문서는 "완전한 상수 시간"이라고 적지 않는다.

**재판단 조건**: 2,000석과 10,000석의 클릭 비용 비가 1에서 멀어지면 이 스캔이 원인인지 확인하고,
그때 `data-seat-index`(+2.9% 바이트)와 맞바꾼다. 지금은 비가 **0.67배**라 스캔이 보이지 않는다.

### 5.3 하네스는 기준선 측정보다 먼저 커밋했다

009 4.9절에서 밟고 009_2 4.1절이 규칙으로 못 박은 것이다. **측정 계약은 바꾸지 않았다** —
`seat-interaction.spec.ts`·`payload-bytes.spec.ts`·`stream-markers.spec.ts`·`target.ts`는
한 줄도 안 건드렸다. `dom-memory.spec.ts`에 선택 상태의 rect를 세는 행을 **추가만** 했고,
그 행은 main에서도 통과한다(결과 0). 그래서 before/after가 같은 자로 잰 값이다.

같이 넣은 것: `booking-flow.spec.ts`에 **키보드 경로**(roving tabindex → 화살표 → Enter 토글)를
넣었다. 이 Task가 그 경로를 통째로 다시 쓰는데 그물이 마우스 클릭 하나뿐이었다.

## 6. 수치

### 6.1 클릭 응답성 (토글 20회 중앙값)

| 지표 | 2,000석 before | C+ | **final** | 10,000석 before | C+ | **final** |
|---|---|---|---|---|---|---|
| 토글 commit | 6.75 ms | 1.0 | **0.6** | 30.3 ms | 3.4 | **0.4** |
| 토글 frame | 16.5 ms | 16.5 | 16.55 | 32 ms | 16.6 | **16.7** |
| 첫 클릭 commit | 9.3 ms | 3.4 | 2.5 | 36.4 ms | 6.5 | 2.4 |

**좌석 수 민감도(10,000 ÷ 2,000): 4.49배 → C+ 3.4배 → final 0.67배.**
선택 가능 좌석이 800 → 4,000으로 5배인데 클릭 비용이 늘지 않는다.

**체감에 가장 가까운 것은 `frame`이다.** 10,000석에서 32 → 16.7ms, 즉 **2프레임이 1프레임**이
됐다. 2,000석은 before에도 이미 1프레임(16.5ms)이라 `frame`이 안 움직인다 — commit이 6.75 →
0.6ms로 내려가도 다음 프레임을 기다리는 시간은 같다. **작은 공연장에서 이 작업의 체감 이득은
거의 없고, 그게 정상이다.**

선택 깊이별(10,000석): before 29.7 / 29.8 / 29.7 / 30.4 → final 0.4 / 0.4 / 0.5 / 0.5.
양쪽 다 평탄하다 — 2.1절이 적은 대로 깊이는 원래 원인이 아니었다.

### 6.2 DOM·메모리·리스너 (하이드레이션 직후)

| 지표 | 2,000석 before | C+ | **final** | 10,000석 before | C+ | **final** |
|---|---|---|---|---|---|---|
| **리스너** | 1,134 | **335** | **335** | 4,335 | **336** | **336** |
| DOM 노드 | 1,054 | 1,055 | **1,054** | 4,254 | 4,255 | **4,254** |
| heap KB | 4,475.36 | 4,549.93 | **4,388.53** | 7,247.82 | 7,355.29 | **6,798.25** |
| RecalcStyle ms | 21.89 | 11.6 | 12.51 | 38.19 | 28.7 | **26.89** |
| 선택 4매 Script 증가 | +33.61 | +9.14 | **+5.75** | +135.49 | +20.38 | **+7.15** |

**리스너가 좌석 수에서 풀렸다.** 2,000석 335 / 10,000석 336 — 좌석이 5배인데 1개 차이다.
before에는 좌석당 정확히 1개가 붙어 있었다(1,134 - 334 = 800, 4,335 - 335 = 4,000).
남은 335는 좌석과 무관한 앱 고정 바닥이다.

**C+에서 heap이 늘었다가 final에서 내려갔다.** C+의 +1.5~1.7%는 좌석별 memo 래퍼와 사전 계산
배열 몫이고, final에서 memo 래퍼 4,000개가 사라지면서 **before보다 6.2% 낮아졌다.**

### 6.3 전송량 — 줄이려던 게 아닌데 줄었다

## 7. 수용/기각 기준 판정

기준은 **측정 전에** 계획서에 적었다(009_2 3.8절의 전례 — 사후 합리화를 막는 자리다).

| # | 기준 | 결과 | 판정 |
|---|---|---|---|
| 1 | 10,000석 토글 commit ≤ 10.7 ms | 0.4 ms | ✅ |
| 2 | 10,000석 / 2,000석 비 ≤ 1.3 | 0.67배 | ✅ |
| 3 | 10,000석 선택 4매 Script 증가 ≤ +40 ms | +7.15 ms | ✅ |
| 4 | 10,000석 리스너 ≤ 50개 | 336 | ❌ **기준이 틀렸다** |
| 5 | 무스로틀 TBT가 0에서 오르면 기각 | 0 (6/6, 양 지점) | ✅ |
| 6 | 하이드레이션 DOM 노드·heap이 before보다 나빠지면 기각 | DOM 동일, heap -1.9% / -6.2% | ✅ (**C+는 위반**) |
| 7 | 점수 100 / CLS ≤ 0.0011 (과반) | 100 (6/6), CLS ≤ 0.0011 | ✅ |
| 8 | 2,000석 commit이 9 ms 이상이면 회귀 | 0.6 ms | ✅ |

**기준 4를 잘못 적었다.** "리스너 ≤ 50"은 앱에 좌석과 무관한 고정 바닥이 335개 있다는 걸
모르고 쓴 숫자다. 재려던 것은 **"리스너가 좌석 수에 비례하지 않는가"**였고 그건 달성됐다
(2,000석 335 vs 10,000석 336). 기준을 고쳐 적지 않고 틀린 채로 남긴다 — 측정 전에 적은
문장을 사후에 바꾸면 이 절의 의미가 없어진다.

**기준 6은 C+ 단계에서 위반됐다**(heap +1.5~1.7%). 그 단계에서 멈췄으면 기각선에 걸린
상태로 출하할 뻔했다. final이 해소했지만, **군을 나눠 재지 않았으면 이 사실 자체를 몰랐다.**

## 8. 한계

- **`frame`이 2,000석에서 안 움직인다.** commit이 6.75 → 0.6ms인데 다음 프레임까지는 16.5ms
  그대로다. 작은 공연장에서 이 작업의 **체감 이득은 사실상 없다.** 10,000석에서만 2프레임이
  1프레임이 됐다.
- **클릭당 네이티브 O(n) 스캔이 남아 있다**(5.2절). 재판단 조건을 코드 주석에 적었다.
- **실제 사용자 입력으로 재지 않았다.** 하네스가 `dispatchEvent(new MouseEvent("click"))`로
  디스패치하므로 포인터 히트 테스트 비용이 빠져 있다. 009 4.7절이 Playwright API 경유를
  "7.5배 과대 측정"으로 적은 것과 같은 축의 한계이고, 이번에도 계약을 안 바꿨다.
- **모바일·저사양 기기를 안 쟀다.** 009·009_1·009_2와 같은 한계다. 좌석 4,000개를 다시 그리는
  비용은 CPU에 비례하므로 before의 30.3ms는 저사양에서 훨씬 컸을 것이다 — 즉 이 개선의 실제
  이득은 측정값보다 클 가능성이 있는데 확인하지 않았다.
- **등급 변경 후 리마운트 경로를 자동 검증하지 않았다.** layout effect가 복원하도록 설계했고
  코드로는 닫혀 있지만, e2e가 그 경로를 타지 않는다.
- **선점 실패 리셋 경로도 자동 검증이 없다.** 같은 좌석을 두 세션에서 집어야 재현되는데
  e2e 시나리오에 없다.
- **다크 모드를 스크린샷으로 안 봤다.** 선택 테두리가 `stroke-foreground`(= `var(--foreground)`)로
  before와 같은 토큰을 쓰므로 구조상 같아야 하지만 확인하지 않았다.
- **교차점을 모른다.** 009_2가 RecalcStyle 부호 반전의 교차점을 모른다고 적은 것과 같이,
  이 변경이 "몇 석부터 의미 있는가"는 두 점으로 말할 수 없다.

# 0. 스택 기동 (monitoring 프로필은 끈다, CACHE_TYPE=none 확인)

  JOIN schedules s ON s.performance_id = p.id
  JOIN ticket_grades tg ON tg.schedule_id = s.id
