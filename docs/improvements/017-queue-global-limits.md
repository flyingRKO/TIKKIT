### 0.1 `## 남은 과제` 절은 존재하지 않는다

로드맵이 근거를 "`010-waiting-queue.md` 남은 과제 6·7 + 미배정 후속"으로 적고 있었는데, 010의

### 0.2 조건절이 단정으로 바뀌었다 (교훈 6)

로드맵은 유효 구간 `[6.7, 84]명/s`를 좌석 수와 무관한 고정 구간처럼 적었다. 010 5.1절의 도출은
둘 다 **10,000석 1회차**에 묶여 있다 — 상한 84 = `R_sat`(도착률 120/s) × 0.7이고 그 `R_sat`을
10,000석 좌석맵 응답 1,173,675 B로 쟀으며, 하한 6.7 = 10,000석 / 2.5석 / 600초다.

더 큰 손실은 **한계 6의 실질이 통째로 빠진 것**이다:

> 6. **`admit-batch-size` 상한이 좌석 수에 비례한다.** 10,000석 기준으로 도출했는데 2,000석
> 회차면 응답이 1/5이라 상한이 훨씬 높다. **전역 상수로 두는 것 자체가 의심스럽다.**

로드맵은 그 문장에 붙어 있던 근거(좌석 수 의존성)를 떼고 마지막 한 문장만 **회차 순회의 결론으로
옮겨 붙이고** 있었다. 두 문제가 같은 문장에 있었는데 하나만 전달된 것이다.

### 0.4 `@SchedulerLock` 줄은 010 출처가 아니다

로드맵 4번째 근거 줄이 `@SchedulerLock`의 `lockAtLeastFor` 결합을 적고 있었는데,
`SchedulerLock`·`lockAtLeastFor`·`lockAtMostFor`가 **010에서 0건**이다. 실제 출처는
`QueueAdmissionScheduler` javadoc + `application.yml`·`.env.example`·`docker-compose.prod.yml`

내용도 방향이 지워져 있었다. 로드맵은 "한쪽만 바꾸면 조용히 틀린다"로 **양방향 대칭처럼** 적었지만

나타난다.

## 1. 문제 — 회차를 하나 더 켜면 보호가 뚫린다

```
(before)  초당 입장 인원 = admit-batch-size × 켠 회차 수 / admit-interval
(after)   초당 입장 인원 = admit-rate-per-second            (켠 회차 수와 무관)
```

`QueueAdmissionScheduler.run()`이 `queue_enabled`가 켜진 회차를 전부 순회하면서 **회차마다
독립적으로** `peekWaiting(id, admitBatchSize)`를 돌렸다. 기본값 50은 회차 1개를 전제한 값이라
회차 2개면 100명/s이고, 010이 실측한 상한 84명/s를 넘는다.

**대기열의 목적이 좌석 API를 지키는 것인데, 운영자가 회차를 하나 더 켜는 것만으로 그 보호가
조용히 뚫린다.** 아무 로그도 남지 않고 설정값도 그대로다 — 증상은 "대기열을 켰는데 좌석 API가
느리다"로만 나타난다.

부수 문제로 **ETA도 같이 틀렸다.** `estimatedWaitSeconds`의 분모가 회차당 값이라, 회차 2개면
실제 입장 속도는 2배인데 ETA는 그대로였다. 표시보다 빨리 입장하는 방향이라 사용자에게는
안전했지만(010 5.3절의 유령과 같은 방향) 틀린 것은 맞다.

## 3. 해결안 비교

### 3.1 설정 키 — "초당 전역"으로 교체

010 15절이 남긴 두 후보 중 **"초당 입장 인원을 설정값으로"** 를 골랐다.

| 후보 | 채택 | 이유 |
|---|---|---|
| `admit-rate-per-second`로 교체 | ✅ | 유효 구간 `[6.7, 84]`와 **단위가 같아진다.** 설정값이 구간 안인지 바로 읽힌다 |
| `batch / 켠 회차 수`로 나눈다 | ❌ | 설정 키의 뜻이 "틱당 회차당"으로 남아 혼동이 유지되고, 켠 회차 수가 바뀌면 회차당 몫이 조용히 달라진다 |
| `batch` 유지 + `admit-max-per-second` 추가 | ❌ | 설정 키가 둘이 되어 "실제 입장 속도가 얼마인가"를 두 값에서 계산해야 한다 |

전에는 `admitRatePerSecond()`가 `admitBatchSize / admitInterval`로 **역산**이었다. 단위 불일치가
"회차당인가 전역인가" 혼동의 뿌리 중 하나였고, 이제 ETA 분모가 설정값 그 자체다.

**`int`로 뒀다.** 구간을 정수로 읽으면 `[7, 84]`이고 하한 6.7은 "600초 안에 다 팔리려면 최소
6.7명/s"라 7로 올리는 것이 안전한 방향이다. `double`로 받으면 틱당 예산을 반올림해야 해서
ETA 분모와 실제 속도가 어긋난다.

> **그 `int` 전환이 함정을 하나 만들었다.** `estimatedWaitSeconds`가
> `(long) Math.ceil(rank / properties.admitRatePerSecond())`였는데, 분모가 `int`가 되면서
> **정수 나눗셈이 먼저 잘려 `ceil`이 아무 일도 하지 않는다** — rank 1~2가 0초가 되어 화면에
> "곧 입장"으로 표시된다. `Math.ceilDiv`로 옮기고 `QueueOrderingTest`에 rank 1·2를 1초로
> 고정하는 어서션을 넣었다. 타입을 좁히는 변경이 나눗셈을 지나가면 반올림을 같이 봐야 한다.

**상한을 코드로 강제하지 않았다.** 84가 10,000석 1회차 기준이고(0.2절) Task 036·039가 2,000석
좌석맵 포화를 768.6 → 1004.8 req/s로 올려서 `R_sat` 자체가 바뀌었다. 환경에 따라 틀린 값을
강제하는 쪽이 더 비싸다.

### 3.2 예산 분배 — 순회하며 이어받기

| 후보 | 채택 | 이유 |
|---|---|---|
| 순회하며 남은 예산 이어받기 | ✅ | 빈 회차가 슬롯을 낭비하지 않고 Redis 왕복이 늘지 않는다 |
| 균등 분배(`budget / N`) | ❌ | 빈 회차 몫이 버려지고, 켠 회차가 예산보다 많으면 **몫이 0이 되어 아무도 입장하지 못한다** |
| 대기 인원 비례 | ❌ | 가중치를 구하려면 틱마다 `ZCARD`가 회차 수만큼 추가된다 — 010 5.2절이 전역화의 이유로 적은 "3,000회차 → 왕복 9,000회"를 **더 키운다** |
| 라운드로빈 커서 | ❌ | 커서가 JVM 로컬 상태라 BE 2대 + ShedLock 환경에서 인스턴스마다 다른 위치에서 시작한다. 순서 편향을 없애려다 **재현 불가능한** 편향을 만든다 |

**왕복이 오히려 줄어든다.** `peekWaiting`에 넘기는 count가 고정값에서 남은 예산으로 바뀌는
것뿐이고, 예산이 소진되면 뒤 회차는 `ZRANGE`를 아예 돌지 않아 회차당 3회에서 2회가 된다.
전역 상한이 안전장치이면서 동시에 비용 절감이 되는 흔치 않은 경우다.

**대가는 순서 편향이다** — id가 작은 회차가 예산을 먼저 먹고 뒤쪽 회차는 굶을 수 있다.
없앨 수 없으므로 **설명 가능하게** 만들었다: `QueueFlagRegistry`가 `Set.copyOf`(해시 순서)
대신 id 오름차순 `LinkedHashSet`을 돌려준다. `contains`는 그대로 O(1)이라 요청 경로의
`enabled(long)` 비용이 안 변한다.

> 해시 순서도 **결정적**이었다 — 틱마다 같은 회차가 먼저 먹었다. 문제는 재현성이 아니라
> **설명 가능성**이다. "왜 저 회차만 들어가나"에 답하려면 `Long.hashCode`를 계산해 봐야 했다.

### 3.3 루프를 셋으로 쪼갰다 — 수거를 예산에 묶으면 안 된다

예산 `break`를 한 루프에 그냥 얹으면 **예산이 소진된 뒤 회차의 만료 입장권 수거가 멈춘다.**
만료 판정 자체는 score 비교라 안전하지만(만료권으로 통과하지 않는다) 수거가 밀린 만큼 Redis
메모리가 남고, 켠 회차가 많을수록 뒤쪽이 영구히 밀린다.

대기 인원 집계(Gauge)도 같은 이유로 전 회차를 돈다 — 예산이 소진된 회차의 줄이 대시보드에서
사라지면 "대기열이 비었다"로 오독한다. 2절 표의 4번째 줄(게이지 7 vs 4)이 그 재현이다.

```
① ZREMRANGEBYSCORE  — 전 회차 (예산과 무관)
② ZRANGE → ZADD/ZREM — 예산을 순회하며 소비, 소진되면 break
③ ZCARD             — 전 회차 (예산과 무관)
```

### 3.4 ShedLock 결합 — 한쪽을 없애서 풀었다

어노테이션 속성은 컴파일 타임 상수여야 하므로 `lockAtLeastFor`에 "간격의 90%"를 쓸 수 없다.
`admit-interval`만 `${...}` 플레이스홀더였던 것이 결합의 정체다.

| 후보 | 채택 | 이유 |
|---|---|---|
| `admit-interval`을 상수로 내린다 | ✅ | 설정값이 "초당 인원"이면 틱 간격은 구현 디테일이고 바꿀 근거가 없다(010도 1s 고정으로만 쟀다). **결합의 한쪽이 사라지면 결합이 사라진다** |
| `lockAtLeastFor`도 프로퍼티로 뺀다 | ❌ | 설정 키가 하나 늘고 결합은 그대로다. 조용히 틀리는 창도 안 닫힌다 |
| `LockingTaskExecutor`로 내려가 계산식을 쓴다 | ❌ | `SchedulingConfig`가 `@Profile("!test")`라 테스트 프로필에 `LockProvider` 빈이 없다. 생성자 주입하면 **대기열 통합 테스트 전체가 컨텍스트 로딩에서 깨진다**(`QueueAdmissionTest`가 `run()`을 직접 호출한다). `ObjectProvider` 우회 비용이 상수 2개 + 테스트 1개보다 비싸다 |

남은 것은 상수 2개 사이의 관계이고, `QueueAdmissionSchedulerContractTest`가 어노테이션을
리플렉션으로 읽어 고정한다 — 틱 간격이 1초인지, `lockAtLeastFor < 간격`인지,
`간격 < lockAtMostFor < 1분`인지. **드리프트가 조용한 버그가 아니라 빨간 테스트가 된다.**

013이 쿼리 카운트 기준값을 외부 베이스라인 파일로 빼지 않은 것과 같은 이유다 — 관계가 테스트
코드 안에 있으면 고치려면 왜 바뀌었는지를 PR에 써야 하고, 데이터 파일이면 한 줄 diff로 지나간다.

## 4. 범위 밖 발견 — 하네스 주석이 이유를 틀리게 적고 있었다

`load-test/k6/queue-reject.js`가 측정 성립 조건을 이렇게 적고 있었다:

> 1) `QUEUE_ADMIT_BATCH_SIZE=0` — 아무도 입장하지 않는다(`peekWaiting`이 `count<=0`을 막아준다).

**메커니즘이 두 가지로 틀렸다.**

1. `QueueProperties`의 compact constructor가 `admitBatchSize <= 0`을 **기본값 50으로 보정**한다.
   그래서 0을 넘겨도 `peekWaiting`은 `count=50`을 받는다 — 설정으로 입장을 멈출 수 없다
2. 애초에 막아야 할 후보가 없다. 이 스크립트는 `POST /reservations`만 때리고
   `POST /queue/schedules/{id}/entries`를 부르지 않으므로 `waiting` ZSET이 비어 있다

**결과는 맞았고 이유가 틀린 경우다.** 실제 그물은 조건 3(403 비율이 1에 가까운지)이었고
010의 거절 경로 측정(요청당 커넥션 1.0114 → 0.0173)은 유효하다. 교훈 4의 판본이라 주석을
고치고 이 군에는 입장 속도 환경변수를 넘기지 않게 했다.

## 5. 산출물

**수치가 아니라 "설정값 하나가 실제 입장 속도와 1:1로 대응한다"는 것이다.** 039가 `max_fails`를
끄고 "앞으로의 포화 측정이 조용히 무효가 되지 않는 것"을 산출물로 적은 것과 같은 성격이다.

- `QueueProperties`: `admit-batch-size`·`admit-interval` → `admit-rate-per-second` 하나
- `QueueAdmissionScheduler`: 전역 예산 + 루프 3분할 + 간격·락 상수 인접 배치
- `QueueFlagRegistry`: 순회 순서 id 오름차순 고정
- `RedisQueueGateway`: ETA를 `Math.ceilDiv`로 (3.1절 인용 참조)
- 테스트 7개 2클래스: `QueueGlobalAdmissionRateTest`(4), `QueueAdmissionSchedulerContractTest`(3)
- **010 5.2절의 측정 제약이 풀렸다** — `04-enable-queue.sql`로 N회차를 켜도 입장 속도가
  설정값과 1:1이다. 다회차 군이 Task 037의 회귀 확인 군이 된다
- `run-group.sh`의 토글 에코에 `QUEUE_ADMIT_RATE_PER_SECOND` 추가(교훈 10의 집행 장치)

**구 환경변수를 쓰면 조용히 기본값 50이 적용된다.** `QUEUE_ADMIT_BATCH_SIZE`와
`QUEUE_ADMIT_INTERVAL`은 사라졌고 오래된 `.env`에 남아 있으면 아무 경고 없이 무시된다.
측정 전에 `docker compose -f docker-compose.prod.yml exec backend1 env | grep QUEUE_`로 확인한다.

## 6. 한계

- **부하로 확인하지 않았다.** 재현과 고정이 통합 테스트로 닫혔고, 입장 속도가 공칭값과 1:1인
  것은 010이 이미 쟀다. 다회차 군(prod 스택 + `queue-spike.js`)은 돌리지 않았다 — 이 변경의
  판정이 처리량에 달려 있지 않고, Task 038이 안 닫혀서 040이 쟀듯 같은 조건 9회 산포가 ±4%다
- **id 순서 편향이 남아 있다.** 켠 회차가 많고 앞 회차 줄이 깊으면 뒤쪽 회차는 계속 굶는다.
  로그에 "예산 소진" 플래그를 남겨 신호는 보이게 했지만 **조치는 하지 않았다** — 공평한 분배가
  필요해지는 조건(회차 여럿을 동시에 오픈하는 운영)이 지금 없다
- **상한 84를 재도출하지 않았다.** 10,000석 1회차 기준이고 036·039가 `R_sat`을 바꿨다(0.2절).
  부하 측정이라 Task 038 몫이다
- **`k=2`와 `pass-ttl` 15분을 안 쟀다**(010 한계 5). "입장자당 보호 요청 수 2"가 낙관적이라
  안전계수 0.7을 곱한 것이고, 이게 **상한 84의 신뢰도 자체**를 좌우한다
- **활성 인원 절대 상한이 그대로다.** 입장권이 활동하면 `ZADD XX GT`로 무한 연장된다.
  `admittedAt` ZSET이 하나 더 필요하고(한 score에 두 시각을 담을 수 없다) 010 한계 7이
  "구조 변경이라 측정 Task의 범위가 아니다"로 넘긴 항목이다
- **유령을 여전히 치우지 않는다.** 전역 상한을 넣어도 이 낭비는 그대로다 — 브라우저를 닫은
  사람이 `waiting`에 남아 예산 한 칸을 먹고, 그게 ETA 과대 추정의 진짜 원인이다(010 5.3절).
  `seen` ZSET이 필요하고 임계값은 **90초 이상**이어야 한다(백그라운드 탭 타이머 스로틀)
- **세션 Redis 분리를 안 했다.** 008 8절의 차단 조건을 먼저 뚫어야 하고(빈이 둘이 되면 Spring
  Session 자동설정이 캐시 팩토리에도 걸린다) 010 A.9절이 이미 한 번 밟았다
- **틱 간격을 바꿀 수 없게 됐다.** 상수로 내린 대가다. 바꿀 근거가 없다는 판단에 기댄 것이고,
  필요해지면 `admit-interval`을 되살리는 대신 **예산 계산과 락 관계를 같이 손봐야 한다**
  (계약 테스트가 그걸 강제한다)
- **중복 입장이 예산을 한 칸 먹는다.** 프로세스가 `ZADD active`와 `ZREM waiting` 사이에서 죽으면
  그 사람이 다음 틱 후보에 다시 뽑히는데(자가 치유), 그때 전역 예산도 한 칸 쓴다. 중복 자체가
  프로세스 사망 경로라 지표 오차로 감당한다 — Task 031의 판단을 그대로 유지했다
