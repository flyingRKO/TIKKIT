# 고도화 기록 인덱스

각 문서는 **재현 → 해결 → 수치** 순서로 쓴다. 기각한 것도 같이 남긴다 — 왜 안 썼는지가 왜 썼는지보다
자주 필요하다.

## 측정 환경 (공통)

모든 수치가 **같은 데스크톱 한 대**에서 나왔다. 기재가 문서마다 어긋나 있어서 여기로 모았다 —
본문의 "16코어"는 전부 **논리 스레드**를 가리킨다.

| 항목 | 값 |
|---|---|
| 기종 | **데스크톱**(조립). 노트북이 아니다 |
| CPU | AMD Ryzen 7 7800X3D — **물리 8코어 / 16 논리 스레드**(SMT), 4.2GHz |
| L3 캐시 | **96MB** (3D V-Cache) |
| RAM | 63GB DDR5-5600. 이 중 Docker Desktop(WSL2) 할당 **31.5GB** — `.wslconfig`가 없어 기본값(호스트의 50%)이다 |
| 디스크 | NVMe 2TB (SK hynix Platinum P41) |
| OS | Windows 11 Home 26300 |
| 구성 | nginx 1 + BE 2 + FE 1 + PostgreSQL + Redis + Prometheus + Grafana, **k6까지 같은 호스트** |

**이 기재가 결론에 걸리는 지점 셋.**

1. **`docker stats`의 CPU%는 논리 스레드 기준이다.** [010](010-waiting-queue.md)의 포화
   "11.4 / 16"을 71%로 읽으면 "29% 남았다"가 되는데, 물리 코어는 8개라 **이미 SMT로 짜내는
   구간**이다. 커넥션 풀 10/20/30이 전부 365 req/s에서 막힌 것과 일관된다.
   반면 [012](012-shared-buffers-retrial.md)의 좌석맵 포화는 합계 671%라 그 선 아래이고,
   거기서는 "postgres 400% = 물리 4코어"로 읽어도 된다. **같은 % 표기가 두 문서에서 다른 뜻이다.**
2. **L3 96MB는 X3D 전용 특성이다.** PostgreSQL `shared_buffers` 기본값(128MB)과 같은 자리수다.
   클라우드 vCPU(= 논리 스레드 1개, L3 몫도 작다)로 옮기면 **절대값이 더 낮게 나올 가능성이 크다.**
3. **페이지 캐시는 31.5GB이고 호스트 RAM 63GB가 아니다.** 012 4.2절의 "shared buffer miss가
   memcpy였다"는 이 31.5GB 기준이라 결론은 안 바뀐다. 다만 **줄이는 쪽이 열려 있다** —
   `.wslconfig`로 할당을 DB 아래로 내리면 장비 없이 진짜 디스크를 칠 수 있다(012 9절, 미검증).

> 수치를 외부에 말할 때는 **"데스크톱 8코어 / L3 96MB / k6 동일 호스트"** 를 같이 말한다.
> 셋 중 하나만 바뀌어도 절대값이 달라진다. 비교값(A vs B)만 이식 가능하다.

## 이 기록들을 꿰는 교훈 아홉

세 Phase를 지나며 같은 함정을 반복해서 밟았다. 순서대로 읽으면 하나의 이야기가 된다.

1. **수치가 좋아지는 가장 흔한 이유는 요청이 일을 안 한 것이다.** 007은 버퍼를 88% 줄였는데
   빨라지지 않았고, 010은 좌석 조회가 전부 403이 되면서 p95가 64 → 2.95ms로 "개선"됐다.
   그래서 하네스에 **워크로드 무결성 검사**(iteration당 요청 수·수신 바이트)가 들어갔다 —
   붕괴하면 지연이 좋아지므로 지연 임계값은 오히려 통과한다.

2. **저부하 p95로 채택/기각하지 않는다.** 008이 캐시를 "지연은 그대로지만 용량 때문에 채택"으로
   남겼고, 010이 포화까지 올려 +37%를 확인했다. 008이 용량을 재지 못한 **구조적 이유**는
   하네스의 think time이 iteration의 99.8%였다는 것이다(010 8.1절).

3. **측정 지점이 하나면 결론이 뒤집힌다.** 009_2의 같은 변경이 2,000석에서는 회귀, 10,000석에서는
   개선이었다. 010도 깊이 1,000과 100,000을 둘 다 재서 외삽을 정당화했다.

4. **반증된 설명을 코드 주석에 남기면 다음 사람이 그걸 근거로 움직인다.** 010에서 커넥션 풀이
   벽이라고 쓴 주석과 ETA가 `fixedDelay` 때문에 낙관적이라는 주석을 둘 다 실측이 뒤집었고,
   수치뿐 아니라 **그 주석들을 같이 고쳤다.**

5. **기각한 구현은 토글로도 남기지 않는다.** 009_1의 gzip, 003의 Redisson, 010의 좌석 응답 축소를
   모두 코드째 지웠다. 검증되지 않은 코드가 계약에 남으면 다음 사람이 그게 유효한 선택지라고 읽는다.

6. **기각 기록이 다음 문서로 전달되지 않으면 그 기각은 없는 것과 같다.** 009 4.8절이 `includes()`를
   "원인이 아니다"로 **실측해서 기각**했는데, ROADMAP과 이 README의 「다음 후보」가 바로 그걸
   Task 035의 원인으로 적고 있었다(011 2.1절). 수치는 문서에 남아 있었고 읽히지 않았을 뿐이다.
   **그래서 011은 원인 정정을 문서 맨 앞에 뒀다** — 결론보다 먼저 와야 하는 것은 "앞 문서가
   이미 답한 것"이다. 012도 같은 자리에서 로드맵 두 줄을 고치고 시작했다.

   **014에서 네 번째로 걸렸고, 이번에는 전달 손실이 두 단계였다.** 008 4.1절이 Caffeine 로컬
   캐시를 **실제로 쟀고**(좌석맵 p95 6.63 → 4.98ms, 네 군 중 최속) 역직렬화와 무관한 근거로
   기각했는데 — 힙 용량, 분산 evict, "대안이 응답 축소다" — 010이 그중 하나만 **조건절로**
   옮겨 적고("기각 근거가 Redis의 역직렬화 비용이었다면"), ROADMAP이 그 조건절을 **단정으로**
   요약했다. 그래서 로드맵은 "로컬 캐시는 안 쟀다"로 읽혔다. **한 번 좁혀지고 한 번 단정이
   되면 원문과 반대가 된다.** 덤으로 세 번째 근거는 010 9.3절이 이미 폐기한 것이었다 —
   기각 근거의 유효성도 전달되지 않는다. **요약을 옮길 때 조건절을 떼면 안 된다.**

7. **대리지표는 한 겹씩 벗겨진다.** 007이 "버퍼 접근 수는 I/O의 대리지표가 아니다"를 증명했고
   (2,130 → 354인데 실제 페이지 읽기는 같았다), 012가 한 겹 더 벗겼다 — **이 규모에서는 I/O도
   처리량의 대리지표가 아니다.** 디스크 읽기를 요청당 9.8페이지에서 0으로 없앴는데 처리량이
   안 변했고, 벽은 postgres CPU 400%였다. **"무엇이 줄어드는지"와 "무엇이 빨라지는지"를 매번
   따로 확인한다.**

8. **산포를 모르면 3%를 채택한다.** 012의 커버링 인덱스가 3회 측정에서 +3.0%, 범위도 안 겹쳐
   채택 쪽으로 보였다. 인덱스를 떼고 두 번 더 재서 **같은 조건 9회를 모으니 산포가 736~796
   req/s(±4%)로 벌어져 그 +3%를 삼켰다.** 007 7.4절이 "같은 데이터 위에서 old/new를 번갈아 재야
   한다. 하지 않았다"를 한계로 남긴 자리였다. **비교군을 한 번만 재면 산포를 효과로 읽는다.**

9. **테스트가 돈다는 것과 결과가 읽힌다는 것은 다르다.** 013의 쿼리 카운트 테스트 21개 경로는
   처음부터 CI에서 돌고 있었는데, **통과한 실행에는 숫자가 한 톨도 남지 않아서** 문장 수 계약이
   테스트 소스 안에만 있었다. 그래서 로드맵이 이 항목을 "CI에 안 걸려 있다"로 적어 두고도
   한동안 아무도 어긋남을 못 봤다. 교훈 6의 변종이다 — **6은 기각이 전달되지 않은 경우이고
   9는 요약이 뜻을 바꾼 경우다.** 둘 다 원문을 열면 바로 보인다.
