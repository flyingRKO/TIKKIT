# TIKKIT 개발 로드맵

단순한 예매 MVP에서 출발해 동시성·지정석·대기열·성능·운영을 단계적으로 개선하며, 매 단계를 재현 → 해결 → 수치로 증명하는 티켓 예매 서비스를 만든다.

## 개요

TIKKIT은 공연 탐색, 등급·수량 기반 예매(10분 선점), 모의 결제, 예매 관리 기능을 갖춘 MVP를 먼저 완성한 뒤, 포트폴리오 관점에서 의미 있는 고도화 트랙(동시성 제어, 지정석 전환, 운영/배포, 성능 최적화, 대기열)을 순서대로 진행한다. 각 고도화 Task는 "문제 재현 → 원인 분석 → 해결 → before/after 수치"를 `docs/improvements/`에 기록해 개선 과정 자체를 증거로 남긴다.

## 개발 워크플로우

1. `/git:branch feature/slug`로 브랜치 생성 (Task 번호는 넣지 않는다)
2. 구현 및 테스트 작성
3. `/git:commit` → `/git:pr`
4. `/docs:update-roadmap`으로 완료 표시
5. 고도화 Task는 `docs/improvements/NNN-*.md` 작성 (문제 → 재현 방법 → 원인 분석 → 해결안 비교 → before/after 수치 → 한계·다음 단계)
6. 마일스톤 완료 시 git tag 추가: `v0.1.0-mvp` → `v0.2.0-concurrency` → `v0.3.0-seatmap` → `v0.4.0-ops` → `v0.5.0-performance` → `v1.0.0`

### Phase 10: 클라우드 배포 — 보류

**원래 이 자리가 배포였다.** 비용이 드는 유일한 Task라서 Task 034로 떼어 Phase 10으로 분리했고(`6e829f8`), 그 뒤 **배포를 프로젝트가 완성된 뒤에 하기로 정하면서 Task 034를 「보류 Task」로 내렸다**(`8f109d9`). 그래서 이 Phase는 비어 있다 — 없어진 게 아니라 **내용이 맨 끝으로 옮겨 갔다.**

**번호는 비워 둔다.** Phase 11 이후를 당기지 않는 이유는 Task 번호와 같다 — 본문과 `docs/improvements/README.md`가 "Phase 11"을 참조하는 자리가 있고, 당기면 그 참조가 미아가 된다. Task 026_1·030_1·042_1이 번호를 비틀어 가며 참조를 지킨 것과 같은 선택이다.

**재개 조건은 Task 043(간섭 재현)의 판정 완료다.** 「보류 Task」 절과 「Phase 12~14를 묶는 규칙」의 '배포 게이트' 절에 근거를 적었다.

### Phase 11: 성능 잔여 과제

`docs/improvements/` 15개 문서가 "한계·다음 단계"로 남긴 항목을 영향도 순으로 모았다. **전부 근거와 수치가 이미 있고 조치만 안 된 것들이다** — 새로 발굴한 문제가 아니다. 기존 `후속 Task 후보` 5개도 여기로 흡수했다.

이 Phase의 특징은 **"안 고친 것"보다 "못 잰 것"이 많다**는 점이다. Task 035만 코드 결함이고 나머지는 측정 범위·장비·조건의 한계다. 기각을 수치로 뒷받침해 온 대가로, 그 기각의 **유효 범위가 좁다**는 게 드러난 상태다.

> **Task 035에서 배운 것을 남은 Task에 적용한다.** 035의 원인 진단이 틀렸던 이유는 **앞 문서가 이미 실측으로 기각해 둔 항목을 이 로드맵이 원인으로 적고 있었기** 때문이다(011 2.1절). 아래 Task들의 "근거" 줄도 같은 종류의 전달 손실이 있을 수 있다 — **착수할 때 근거 문서의 해당 절을 먼저 읽고, 어긋나면 로드맵을 고치는 것부터 한다.**

**순서**: ~~035~~(✅ 완료) → ~~040~~(✅ 완료) → ~~042_1~~(✅ 완료) → ~~036~~(✅ 완료) → ~~039~~(✅ 완료) → ~~039_1~~(✅ 완료) → ~~037~~(✅ 완료) → 041 → 042 → **043**. **039가 둘로 쪼개졌다** — nginx 설정과 포화 측정으로 끝나는 쪽(039)과 인증서·Lighthouse 하네스를 건드리는 쪽(039_1)이다. **039_1을 041 앞에 둔 이유는 041의 재방문자·폰트 항목이 HTTP/2 판정 결과에 달려 있기 때문이고, 실제로 041의 전제가 바뀌었다** — HTTP/2가 조각 11개의 경쟁을 없애서(홈 FCP -30.1%) 조각 수를 줄일 이유가 사라졌다. 041은 "11개를 줄일지"가 아니라 "11개를 그대로 두고 재방문 비용을 재는" 쪽이 된다. **039를 앞으로 당겼다** — 036이 nginx `max_fails` 미명시가 포화에서 터지는 것을 재현했고(각 군 3회차가 전부 502인데 처리량은 17배로 개선되어 보였다), 고치지 않으면 남은 포화 측정이 같은 자리에서 조용히 무효가 된다. **Task 038은 전용 부하 노드가 선행이라 순서 밖**이고, 036·037·039는 그 038이 안 닫힌 하네스로 측정한다는 한계를 안고 간다. **040이 그 한계의 대가를 처음 수치로 봤다** — 같은 조건 9회 산포가 ±4%라 3%대 변경은 판정이 안 된다. 다만 **DB I/O 지표는 ±1.2%로 거의 안 흔들린다**는 것도 같이 알았다.

**Task 043(간섭 재현)을 Phase 12에서 가져와 이 Phase의 맨 끝에 뒀다.** 두 가지 이유다.

- **성격이 이 Phase다.** 043은 "섞어서 잰 적이 없다"는 **미측정 항목**이고, 위 문단이 적은 이 Phase의 정의가 바로 그것이다. Phase 12에 남은 044·045는 로컬 캐시 무효화의 근거를 만드는 작업이라 결이 다르다
- **이 Phase 전체가 043의 전제를 바꾼다.** 036이 좌석맵 조립 비용을 줄이면 `seatmap` 846 req/s가 올라가 `browse`와의 12배 차이가 줄고, 042의 `open-in-view`·`@Cacheable` 프록시 비용은 043이 보는 지표(요청별 커넥션 보유 시간, CPU)를 직접 건드린다. **먼저 재면 Phase 11이 끝난 뒤 다시 재야 한다** — 040을 036 앞으로 당긴 것과 같은 논리다

그리고 043은 이제 **이 로드맵의 단일 분기점**이다. 결과가 Phase 14를 열거나 닫고, 그 판정이 Task 034(배포)의 재개 조건이다. 자세한 것은 「Phase 12~14를 묶는 규칙」의 '배포 게이트' 절에 있다.

**번호순이 아니다.** Phase 7이 026_1을 맨 앞에 둔 것과 같은 이유로, **남의 전제를 바꾸는 작업과 회귀를 잡는 장치를 앞으로 당겼다.**

- **035가 1순위였던 이유**: 가장 큰 레버이면서 **부하 노드 없이 Playwright/Lighthouse로 닫을 수 있는 유일한 큰 항목**이다. BE 작업과 완전히 독립이다. ✅ 그대로 성립했다 — 생성기를 한 번도 안 띄웠고 BE는 한 줄도 안 바뀌었다
- **040을 036 앞으로**: 040이 올리는 `shared_buffers`가 036이 공략하는 좌석맵 조립 비용의 **DB 조회 부분을 빠르게 만든다** — 036을 먼저 하면 캐시 이득을 재서 채택한 뒤 040이 그 결론을 뒤집는다. 040은 설정 한 줄이라 가장 싸다. ✅ **이 근거는 틀렸다** — 저부하 60회차에서는 128MB에서도 디스크 읽기가 0이라 036의 before가 안 바뀐다(p95 7.20 vs 6.97ms, 산포 안). **순서가 옳았던 이유는 다른 것이었다**: 040이 036의 과녁을 I/O에서 **Postgres CPU 4코어**로 바꿨다. 036을 먼저 했다면 "DB 조회가 빨라졌다"로 캐시 이득을 잘못 귀속했을 것이다
- **042_1을 036 앞으로**: 뒤따르는 036·044·045가 전부 캐시를 고치는데 **쿼리 카운트 회귀를 잡는 CI 게이트가 없는 상태**였다. 042에서 그 항목만 떼어냈다. ✅ **순서는 옳았지만 근거의 전제가 틀렸다** — 게이트가 "없던" 게 아니라 테스트가 이미 CI에서 돌면서 **결과가 안 읽히고 있었다**. 036을 먼저 했어도 회귀는 빌드 실패로 잡혔을 것이고, 못 봤을 것은 "문장 수가 몇에서 몇으로 바뀌었나"다. 그게 캐시를 세 번 고치는 작업에서 더 비싸다는 판단은 그대로 성립한다

- ✅ **Task 035: [FE] 좌석 선택 레이어 오버레이** (`feature/seat-selection-overlay`)
  - ✅ **여기 적혀 있던 원인이 틀렸다.** 원래 이 자리는 "`selectedSeatIds.includes(seat.id)`가 좌석마다 O(n)"이라고 적고 있었는데, **009 4.8절이 그걸 이미 실측으로 배제해 뒀다** — 선택 상한이 4매라 배열 길이가 최대 4이고, 깊이별 비용이 평탄하다. 이번 기준선에서도 29.7 / 29.8 / 29.7 / 30.4ms로 재현됐다. 실제 비용은 **클릭 한 번에 선택 가능 레이어 4,000개가 전부 다시 조립되는 것**이었고, 트리거도 둘이었다(`onToggleSeat`과 `setFocusIndex`). 기각 기록이 다음 문서로 전달되지 않으면 그 기각은 없는 것과 같다 — `improvements/README.md` 교훈 6으로 올렸다
  - ✅ **군을 둘로 나눠 귀속을 갈랐다.** C+(좌석별 `memo` + 이벤트 위임 + 좌석당 반복 제거)가 30.3 → **3.4ms**를 하고, final(선택·포커스를 레이어 props에서 제거)이 나머지를 했다. 한 번에 적용했으면 "레이어 분리가 전부 했다"로 틀리게 적었을 것이다
  - ✅ **10,000석 클릭 commit 30.3 → 0.4ms, 좌석 수 민감도 4.49배 → 0.67배.** 선택 가능 좌석이 800 → 4,000으로 5배인데 클릭 비용이 늘지 않는다. 체감에 가까운 `frame`은 32 → 16.7ms로 **2프레임이 1프레임**이 됐다. 리스너도 좌석 수에서 풀렸다(4,335 → 336, 2,000석군 335와 사실상 같다)

"회차 2개면 틱당 6명"은 `ZCARD` 두 번으로 보이는 것이고, 입장 속도가 공칭값의 1.000~1.033배라는 것은 010이 이미 쟀다. 042_1이 게이트가 실제로 잡는 것을 재현한 것과 같은 방식이다
  - ✅ **루프를 셋으로 쪼갰다 — 예산 `break`를 그냥 얹으면 안 됐다.** 만료 입장권 수거와 대기 인원 집계는 **예산과 무관하게 전 회차**를 돈다. 한 루프에 묶으면 예산이 소진된 뒤 회차의 만료 엔트리가 영구히 남아 `activeSize`가 틀리고, 집계까지 같이 끊기면 그 회차의 줄이 대시보드에서 사라져 **"대기열이 비었다"로 오독**한다. 위 재현 표의 3·4번째 줄이 그것이다
  - ✅ **왕복이 오히려 줄어든다.** `peekWaiting`에 넘기는 count가 고정값에서 남은 예산으로 바뀌는 것뿐이고, 예산이 소진되면 뒤 회차는 `ZRANGE`를 아예 돌지 않아 회차당 3회에서 2회가 된다. 010 5.2절이 전역화의 두 번째 이유로 적은 "3,000회차 → 틱당 왕복 약 9,000회"가 완화되는 방향이다 — **전역 상한이 안전장치이면서 동시에 비용 절감이 되는 흔치 않은 경우다**
  - ✅ **ShedLock 결합은 한쪽을 없애서 풀었다.** `admit-interval`을 설정에서 빼고 `QueueAdmissionScheduler.ADMIT_INTERVAL` 상수(1s)로 내렸다 — 설정값이 "초당 인원"이면 틱 간격은 "얼마나 잘게 나눠 흘리나"라는 구현 디테일이고 바꿀 근거가 없다(010도 1s 고정으로만 쟀다. 교훈 5의 적용이기도 하다 — 측정된 적 없는 손잡이다). `LockingTaskExecutor`로 내려가 계산식을 쓰는 쪽은 기각했다 — `SchedulingConfig`가 `@Profile("!test")`라 **생성자 주입하면 대기열 통합 테스트 전체가 컨텍스트 로딩에서 깨진다**. 남은 상수 관계는 `QueueAdmissionSchedulerContractTest`가 리플렉션으로 고정해 **드리프트를 빨간 테스트로 바꿨다**(013이 기준값을 외부 파일로 빼지 않은 것과 같은 이유)
  - ✅ **순서 편향을 없애지 못해서 설명 가능하게 만들었다.** 예산을 이어받는 구조라 id가 작은 회차가 먼저 먹고 뒤쪽은 굶을 수 있다. `QueueFlagRegistry`가 `Set.copyOf`(해시 순서) 대신 id 오름차순 `LinkedHashSet`을 돌려준다 — **해시 순서도 결정적이었고 문제는 재현성이 아니라 설명 가능성이었다**("왜 저 회차만 들어가나"에 답하려면 `Long.hashCode`를 계산해야 했다). `contains`는 그대로 O(1)이라 요청 경로 비용이 안 변한다. 균등 분배(켠 회차가 예산보다 많으면 몫이 0)·대기 인원 비례(틱마다 `ZCARD` N회 추가)·라운드로빈 커서(JVM 로컬 상태라 BE 2대에서 인스턴스마다 다른 위치)는 기각했다
  - ⚠️ **타입을 좁힌 변경이 나눗셈을 지나가 버그를 만들 뻔했다.** ETA 분모가 `double` → `int`가 되면서 `(long) Math.ceil(rank / rate)`의 나눗셈이 **정수 나눗셈으로 먼저 잘려 `ceil`이 아무 일도 하지 않는다** — rank 1~2가 0초가 되어 화면에 "곧 입장"으로 표시된다. `Math.ceilDiv`로 옮기고 `QueueOrderingTest`에 rank 1·2를 1초로 고정하는 어서션을 넣었다
  - ✅ **범위 밖 발견: 하네스 주석이 결과는 맞고 이유는 틀렸다.** `queue-reject.js`가 "`QUEUE_ADMIT_BATCH_SIZE=0` — `peekWaiting`이 `count<=0`을 막아준다"고 적고 있었는데 **둘 다 아니다** — ① `QueueProperties`가 `<= 0`을 기본값 50으로 보정하므로 설정으로 입장을 멈출 수 없고 ② 애초에 그 스크립트가 대기열에 줄을 서지 않아 `waiting`이 비어 있다. 실제 그물은 조건 3(403 비율)이었고 010의 거절 경로 측정은 유효하다 (교훈 4)

  - **`cacheComponents` 도입 검토** — Next 16의 통합 플래그(PPR + `use cache` + dynamicIO). 030_2의 공개/세션 진입점 분리가 선행 조건을 만들어 뒀고, `lib/api/client.ts`에 `revalidate`/`cacheLife`가 아직 안 켜져 있다. 전 페이지 Suspense 감사가 필요하다. **구 `후속 Task 후보`의 같은 항목을 흡수**했다

- **Task 043: [공통] 간섭 재현 — 분기 게이트** (`feature/workload-interference`)
  - **이 Phase의 마지막 Task이고 로드맵 전체의 분기점이다.** 결과가 Phase 14를 열거나 닫고, 그 판정이 Task 034(배포)의 재개 조건이다. 원래 Phase 12의 첫 Task였는데 위 "순서" 절의 두 이유로 옮겼다
  - **지금 측정은 워크로드를 따로 쟀다.** `browse` 10,150 req/s, `seatmap` 846 req/s, 예매 포화 309 req/s — **12배 차이인데 섞어서 잰 적이 없다.** 같은 Tomcat 스레드풀과 Hikari 커넥션풀(기본 10)을 공유하는 상태다
  - **Task 036이 이 Task의 전제를 약화시켰다.** 좌석맵이 768 → 995 req/s가 되면서 `browse` 10,150과의 격차가 13배 → 10배로 줄었고, 더 중요하게는 **좌석맵의 CPU 주인이 postgres(390%)에서 BE·nginx로 옮겨갔다**(postgres 144.6% / BE 279.9% / nginx 97.9%). 아래 040이 보강한 "두 워크로드가 서로 다른 자원에서 부딪힌다"가 그만큼 덜 성립한다 — **섞어서 재기 전에 좌석맵을 캐시 켠 상태로 둘지부터 정해야 하고, 둘 다 재는 쪽이 맞다**(캐시는 기본값이 off라 두 조건이 다 실재한다)
  - **Task 040이 이 Task의 전제를 하나 보강했다 — 두 워크로드가 CPU를 먹는 컨테이너가 서로 다르다.** 좌석맵 포화는 **postgres 400%** / BE 271%이고, 예매 포화는 **BE 700%** / postgres 51%다(t033 `cpu-probe.txt`). 섞으면 둘이 다른 자원에서 부딪히므로 **"처리량이 아니라 자원별로 본다"는 이 Task의 설계가 더 맞다**. 커넥션·스레드만 보지 말고 컨테이너별 CPU도 같이 남긴다
  - **측정 대상은 처리량이 아니라 서버 측 자원 경합이다.** 처리량으로 재면 006이 경고한 함정에 빠진다 — 부하 생성기가 같은 호스트에 있어서 섞으면 **생성기 부하도 2배가 되고**, 떨어진 처리량이 서버 간섭인지 생성기 굶주림인지 구분할 수 없다("부하를 더 올리면 p95가 서버 지연인지 생성기 굶주림인지 구분할 수 없다"). **Phase 14를 열거나 닫는 판단을 그런 측정에 맡길 수 없다**
  - 그래서 보는 것은 **Hikari 커넥션 획득 대기 시간·`pending` 수, Tomcat 스레드 점유, 요청별 커넥션 보유 시간**이다. 서버 내부 지표라 생성기 한계와 덜 엉킨다. **Task 033이 이미 이 기법으로 거절 경로의 요청당 커넥션 1.0114 → 0.0173개를 잡아냈다** — 하네스(`load-test/results/t033-backend-metrics/`)와 수집 방식이 그대로 있다. **이 설계 덕분에 043만은 Task 038(전용 부하 노드) 없이도 판정이 성립한다** — 그래서 분기점을 로컬에서 닫을 수 있다
  - 간섭의 직접 증거는 **섞었을 때 `browse` 요청이 커넥션을 얻기까지 기다리는 시간이 늘어나는 것**이다. 처리량 숫자는 보조 지표로만 기록하고 상한으로 읽지 않는다
  - 시나리오 조합은 기존 k6 하네스(`load-test/k6/browse.js`, `seatmap.js`)를 같은 런에서 돌리면 되므로 **새 인프라가 0이다**
  - 간섭이 확인되면 **단순한 해법부터** — Tomcat 스레드풀 분리, Hikari 풀 분리(읽기/쓰기), Resilience4j bulkhead. 여기서 해결되면 Phase 14는 열지 않는다. 주의: Task 033이 **커넥션 풀 상향은 이미 반증했다**(10/20/30 모두 365 req/s, 140/s에서는 올린 쪽이 더 느렸다) — 풀을 키우는 것과 풀을 나누는 것은 다른 조치다
  - **두 결과 모두 산출물이다.** 간섭이 작으면 "이 규모에서는 모놀리스로 충분하다"를 수치로 남기고 Phase 14를 기각한다. 간섭이 재현되면 Phase 14가 **측정에 등을 밀려서** 열린다 — 면접에서 "왜 쪼갰나"에 답할 수 있는 상태로 들어가는 것이고, 그게 "MSA를 해봤다"보다 강하다

### Phase 12: 모놀리스 + 카프카 (성능)

**쪼개지 않는다.** 서비스 분리는 Phase 14로 미루고, 지금 구조에서 카프카가 **실제로 성능을 올리는 자리**만 공략한다.

전제를 먼저 분명히 한다 — **카프카는 지금 병목을 직접 줄이지 않는다.** 처리량 벽은 365 req/s이고 원인이 CPU이며(포화 11.4 of 16 논리 스레드 = 물리 8코어 포화), 그 CPU의 68%가 좌석맵 조립이다. 큐를 넣어도 총 CPU 시간은 그대로다. 피크 평탄화도 Redis 대기열이 이미 한다. **그래서 "트래픽이 많을 것 같아서"는 이 Phase의 근거가 아니다.**

성립하는 근거는 하나다. 세 문서가 각자 남긴 한계가 한 줄로 이어진다.

| 문서 | 남긴 것 |
|---|---|
| 029 | 좌석맵 Redis 캐싱 **기각** — 적중률 99.97%에서도 느렸다(6.63 → 7.22ms). 이유는 337,885B의 왕복·역직렬화 |
| 010 | **"Caffeine 로컬 캐시에는 029의 기각 근거가 적용되지 않는다"** — 직렬화도 네트워크도 없다 |
| 008 | **"로컬 캐시의 2대 불일치를 실측하지 않았다"** — BE가 2대라 로컬 캐시는 서로 다른 값을 든다 |

**경로가 둘이다. 아래가 경로 A(읽기 캐시)이고, 그것이 Task 036에서 기각되면 Task 045_1(쓰기 버퍼링)이 경로 B다.** A를 먼저 두는 이유는 성능 근거가 직접적이기 때문이고, B를 적어 두는 이유는 **A가 036 하나에 매달린 단일 실패점**이기 때문이다.

**조립 68%를 없앨 수 있는 유일한 수단이 로컬 캐시이고, 그게 다중 인스턴스 일관성 때문에 막혀 있다.** 그 일관성을 푸는 것이 무효화 전파이고, 거기서 카프카가 근거를 얻는다. 순서는 이 레포의 방식을 지킨다 — **단순한 것 먼저, 한계를 재현한 뒤 교체한다.**

**순서**: 044 → 045 → (045_1은 조건부). **Task 043(간섭 재현)은 Phase 11 맨 끝으로 옮겼다** — 이 Phase와 Phase 11이 043의 전제를 바꾸기 때문이고, 근거는 Phase 11의 "순서" 절에 적었다. 그래서 이 Phase는 **읽기 캐시 무효화 하나만** 다룬다.

- **Task 044: [BE] 로컬 캐시 도입과 2대 불일치 재현** (`feature/local-cache-inconsistency`)
  > [!warning] 선행 Task 036이 끝났고, **이 Task의 전제가 깨졌다**
  > 036은 로컬 캐시를 **채택**했다(포화 +29.5%, postgres CPU -62.9%). 전제의 앞쪽("이득이 있는가")은 성립했는데 뒤쪽이 막혔다 — **그 캐시에는 무효화가 없다.** 담는 것이 좌표·구역·행·번호·등급 id뿐이고 그 필드를 런타임에 바꾸는 코드 경로가 0건이라 evict가 필요 없고, 상태는 매 요청 DB에서 읽어 합친다. 그러면 이 Task가 재현하려는 **"새로고침할 때마다 좌석 상태가 번갈아 바뀌는 화면"이 만들어지지 않고**, 045가 전파할 무효화 메시지도 없다.
  >
  > 불일치를 만드는 유일한 길은 **상태까지 캐시하는 것**인데, 그건 008부터 이 레포가 일관되게 거부해 온 선택이다(매진이 TTL만큼 늦게 보인다. `CacheNames`가 `status`와 `remainingQuantity`를 의도적으로 제외한 이유). **즉 경로 A는 "근거를 만들려고 나쁜 설계를 고르는" 자리에 와 있고, 그건 이 로드맵이 11편에 걸쳐 거부해 온 방향이다.**
  >
  > 남은 선택지는 둘이다 — ① 경로 A를 **기각**하고 Phase 13(실패와 보상, 근거가 가장 확실하다)을 앞으로 당긴다 ② 좌석 상태를 캐시해야 하는 다른 근거(예: 036 8절의 "상태 델타만 조회하기"가 막혔을 때)를 먼저 만든다. **기각이 기본값이다.** 자세한 것은 `docs/improvements/014-seatmap-assembly-cost.md` 4.5절.
  - 이득이 확인되면 **BE 2대에서 불일치를 재현한다.** 008이 미실측으로 남긴 바로 그것이다. 좌석이 팔렸는데 한쪽 인스턴스만 그걸 알고, nginx 라운드로빈이라 **새로고침할 때마다 좌석 상태가 번갈아 바뀌는** 화면을 만든다
  - 재현 방법은 Task 026이 세션 불일치를 재현한 하네스를 그대로 쓴다(BE 2대 + nginx, 같은 쿠키로 반복 요청)
  - **좌석 상태는 캐시 대상이 아니라는 기존 규칙과 충돌한다** — `CacheNames`가 `status`와 `remainingQuantity`를 의도적으로 제외했다. 로컬 캐시에 좌표·등급만 넣고 상태를 실시간으로 합치는 구조로 간다
  - **여기 적혀 있던 "그 분해가 이 Task의 절반이다"는 이미 끝난 일이다.** 029가 쿼리를 배치·상태로 쪼개 배치만 캐시하는 구조를 실제로 만들어서 쟀고(008 4.1절), 분해 결과가 남아 있다 — **분리만 하고 캐시를 끄면 6.63 → 8.62ms(+30%) 순손실**이고(왕복 1 → 2, `schedule_seats` 2,000행을 두 번 읽는다), 거기에 Caffeine을 켜면 4.98ms다. 036이 그 구조를 되살려 쓰므로 **이 Task에 남는 것은 2대 불일치 재현 하나다**
    > [!warning] 확인 필요
    > **이 Task의 전제가 036 설계에서 흔들렸다.** 캐시에 담는 것이 좌표·구역·행·번호·등급 id뿐이고, 그 필드를 런타임에 바꾸는 경로가 코드에 **0건**이다(좌석 상태 UPDATE 3개와 만료 배치는 전부 `status`·`reservation_id`·`updated_at`만 SET하고, `Seat`·`ScheduleSeat` 엔티티에 해당 필드 변경 메서드가 없다). 그러면 evict 자체가 필요 없어서 **BE 2대가 서로 다른 값을 들 수가 없다** — 008이 든 기각 근거 ②도, 이 Task가 재현하려는 불일치도, 045의 무효화 전파 근거도 같이 약해진다. 036이 측정과 함께 이걸 확정하고, 결과를 `014` 문서에 남긴다. **불일치를 만들려면 상태까지 캐시해야 하는데 그건 이 레포가 008부터 거부해 온 선택이다**

- **Task 045: [BE] 무효화 전파 — Redis Pub/Sub → 카프카** (`feature/cache-invalidation-kafka`)
  - **Redis Pub/Sub으로 먼저 한다.** 이미 Redis가 있어서 추가 인프라가 0이고, 무효화 메시지는 수십 바이트라 029의 기각 근거(큰 값)가 적용되지 않는다
  - **그다음 한계를 재현한다.** Pub/Sub은 at-most-once다 — 구독자가 죽어 있는 동안 발행된 무효화는 **영구히 사라지고, 그 인스턴스의 캐시는 되돌아올 방법이 없다.** 재배포·GC 정지·네트워크 끊김으로 재현한다. 세션 축출 실험(010 7.2)처럼 **조건을 만들어서 재현하는** 방식이다
  - **그 재현이 카프카의 근거다.** 컨슈머가 오프셋을 들고 있어서 재시작하면 놓친 무효화를 따라잡는다. 비교 항목: 전파 지연(p95), 유실률, 인스턴스 재시작 후 수렴 시간, 그리고 **운영 비용**(브로커 1대가 먹는 메모리·CPU와 그게 365 req/s 벽에 주는 영향)
  - **기각 조건을 미리 적어둔다**: Pub/Sub 유실이 재현되지 않거나, 유실이 나도 캐시 TTL로 자연 수렴하는 시간이 허용 범위면 카프카는 기각한다. 그때는 "왜 안 썼나"가 산출물이 된다
  - 카프카 구성은 **KRaft 단일 브로커**(ZooKeeper 없음), 토픽 1개, 파티션 수와 키 전략의 근거를 기록한다 — 무효화는 좌석 단위 순서가 필요하므로 `scheduleId`를 키로 쓴다
  - 로컬 리소스 한계 때문에 측정 시 FE를 끈다. 브로커가 추가되면 Task 038(전용 부하 노드)의 한계가 더 커진다는 것을 수치와 함께 적는다

- **Task 045_1: [BE] 좌석 선점 쓰기 버퍼링 (경로 B, 조건부)** (`feature/seat-hold-buffering`)
  - **위 경로가 Task 036 하나에 매달려 있어서 두 번째 경로를 열어 둔다.** 036에서 로컬 캐시가 이득이 없으면 044·045가 근거를 잃고 **Phase 12의 성능 근거가 0이 된다.** 그 경우에 이 Task로 간다
  - 근거는 다른 곳에서 온다. 010의 결론이다 — **"대기열은 유입을 차단하는 장치가 아니라 계량하는 장치다. 배치를 키우면 그만큼 그대로 흘러들어간다."** `admit-batch-size`를 키우면 좌석 API가 받는 부하가 그대로 올라가고, **활성 인원 절대 상한이 없다**(037). 즉 대기열 뒤에 최종 방어선이 없다
  - 좌석 선점 요청을 카프카 토픽에 넣고 컨슈머가 순차 처리하면 **DB 쓰기 속도를 컨슈머 수로 고정**할 수 있다. 대기열이 못 막는 구간을 토픽이 막는다. 파티션 키는 `scheduleId`이고(회차 단위 순서만 필요하다) 파티션 수가 곧 쓰기 병렬도가 된다
  - **대가가 크고 그걸 먼저 기록한다**: ① 선점이 동기 응답에서 "접수됨"으로 바뀌어 **FE가 결과를 폴링해야 한다** — Task 032가 대기열에 만든 `setTimeout` 체인을 재사용할 수 있다 ② 대기열과 역할이 겹친다 — 둘 다 유입 조절이라 **어느 층이 실제 상한인지 흐려진다** ③ v0.2.0이 조건부 UPDATE를 고른 근거("모든 쓰기 경로가 규약을 지켜야 하는 방식은 아무것도 강제하지 않는다")에 **정면으로 걸린다** — 토픽을 안 거치고 DB를 쓰는 경로가 생기면 상한이 무너진다
  - **그래서 기각이 기본값이다.** 036이 성립하면 이 Task는 열지 않는다. 열더라도 ③을 어떻게 막을지(선점 SQL을 컨슈머만 호출하도록 강제하는 수단)를 먼저 정하지 않으면 시작하지 않는다

### Phase 13: 실패와 보상 (카프카 근거 완성)

Phase 12가 **읽기** 쪽에서 카프카를 정당화한다면, 이 Phase는 **쓰기와 외부 연동** 쪽이다. 지금 이 영역에 근거가 전혀 없는 이유는 단순하다 — **실패하는 외부 의존이 없다.** `MockPaymentGateway`는 절대 실패하지 않고, 알림 구현은 0건이며, `@Async`·`ApplicationEventPublisher`도 0건이다.

- **Task 046: [BE] 실패 주입 PG와 보상 실패 재현** (`feature/payment-failure-injection`)
  - `MockPaymentGateway`에 실패율·지연을 설정으로 주입할 수 있게 바꾼다. 실제 PG 연동이 아니라 **실패를 만들 수 있는 Mock**이다 — 외부 계정 없이 재현이 되고, 실제 PG로 가는 길도 막지 않는다
  - 002가 남긴 한계를 **재현 가능한 버그로 만든다**: "환불 호출이 실패하면 로그만 남긴다. 그 트랜잭션은 곧 롤백되므로 실패 사실을 DB에 남길 수 없다." → **돈은 빠져나갔고 예약은 없는 상태**를 재현한다
  - 같이 드러날 두 번째 문제: **PG 호출이 `@Transactional` 안에 있다**(`ReservationService.pay()`). 지연을 주입하면 커넥션 점유가 수치로 보인다. 측정 지표는 Task 033이 쓴 것과 같다 — 요청당 Hikari 커넥션 수(거절 경로에서 1.0114 → 0.0173개를 잡아낸 그 방법)
  - 해법도 033과 같은 기법이다 — **승인 호출을 트랜잭션 밖으로 빼고 짧은 트랜잭션으로 상태를 재확인 후 확정**한다. 주석에 이미 적혀 있는 설계다

- **Task 047: [BE] 아웃박스 패턴과 정산 배치** (`feature/outbox-pattern`)
  - 002가 적은 해법을 그대로 구현한다 — **아웃박스 테이블 + 정산 배치 + 멱등키.** 카프카가 아니다
  - **카프카를 써도 아웃박스는 필요하다**는 것을 기록한다. DB 커밋과 메시지 발행의 원자성 문제가 그대로 남기 때문이다. 즉 아웃박스는 카프카의 대안이 아니라 선행이다 — 이 순서를 뒤집으면 "카프카를 넣었는데 메시지가 유실된다"를 만난다
  - 배치는 폴링이다. **폴링 주기와 처리량의 한계를 측정한다** — 주기를 줄이면 DB 부하가 늘고, 늘리면 보상 지연이 커진다. 그 곡선이 다음 Task의 근거가 된다
  - `@SchedulerLock`을 반드시 붙인다(BE 2대). 그리고 **보상 작업은 멱등이 아니다** — 기존 만료 배치가 멱등이라 중복 실행이 안전했지만, PG 환불은 두 번 부르면 사고다. `tikkit-back/CLAUDE.md`가 경고한 "다음에 추가될 배치"가 이것이다

- **Task 048: [BE] 알림과 DLQ** (`feature/notification-dlq`)
  - 알림(이메일 또는 푸시)을 붙인다. **비멱등 외부 호출이 처음 생기는 지점**이다
  - **먼저 `@Async` + 재시도로 한다.** 그 한계를 재현한다 — 애플리케이션이 재시작하면 큐에 있던 작업이 사라지고, 재시도 횟수를 넘긴 실패를 보관할 곳이 없다
  - 그 재현이 **DLQ와 영속 큐의 근거**다. 여기서 Phase 12의 카프카를 재사용할지, 아니면 아웃박스 테이블로 충분한지 비교한다 — **브로커가 이미 있다는 사실이 판단을 흐리지 않게** 두 선택지를 같은 조건에서 잰다
  - 알림은 예매 응답 경로에서 빠져야 한다. 동기로 두면 메일 서버 지연이 예매 p95에 그대로 더해지는 것을 먼저 수치로 보여준다

### Phase 14: 서비스 분리 (MSA)

**Task 043(간섭 재현, Phase 11 맨 끝)의 결과가 이 Phase를 열거나 닫는다.** 간섭이 작거나 스레드풀·커넥션풀 분리로 해결되면 여기는 열지 않고, 그 기각 근거를 `docs/improvements/`에 남긴다. **기각도 이 Phase의 완료 조건이다** — 산출물이 "MSA를 구현했다"가 아니라 "쪼갤 근거가 있는지 판정했다"이기 때문이다. 그래서 Task 034(배포)의 재개 조건도 '구현 완료'가 아니라 '판정 완료'로 걸어 뒀다.

**열린다면 Task 038(전용 부하 노드)이 필수 선행이다.** 컨테이너가 12~13개로 늘어나는데 부하 생성기가 같은 호스트에 있으면 분리 전후 수치의 원인을 가를 수 없다(038 항목 참조). 038 없이 열면 "쪼갰더니 느려졌다"가 서버 탓인지 생성기 탓인지 모르는 상태로 끝나고, **그건 이 레포가 11편에 걸쳐 피해 온 종류의 결론이다.**

분리 경계는 **측정과 결합도 둘 다**가 지목하는 곳으로 정한다. 현재 도메인 간 참조는 이렇다.

```
member      → (없음)        완전 독립
venue       → (없음)        완전 독립
performance → venue
queue       → performance
payment     → reservation
reservation → member, payment, performance, queue, venue      허브
```

여기서 두 가지가 드러난다. **`reservation`이 5개 도메인에 의존하는 허브**라서 떼면 분산 트랜잭션이 바로 생긴다. 그리고 **도메인 경계와 성능 경계가 다르다** — `browse`(10,150 req/s)와 `seatmap`(846 req/s)이 둘 다 `performance`(32개 소스, 최대 모듈) 안에 있다. 처리량으로 쪼개려면 도메인을 갈라야 하고, 도메인으로 쪼개면 12배 차이가 한 서비스에 남는다. **"어디서 쪼개나"가 이 Phase의 질문이다.**

- **Task 049: [공통] 경계 도출과 최소 분리** — 간섭 측정 + 결합도로 경계를 정하고 **하나만** 뗀다. 후보는 좌석 조회(성능 경계) 또는 `member`·`venue`(의존 0건이라 가장 싸다). HTTP 동기 호출로 먼저 쪼갠다 — 이벤트부터 시작하면 동기 호출의 문제를 재현할 기회를 잃는다
- **Task 050: [공통] 연쇄 장애 재현과 이벤트 전환** — 떼어낸 서비스를 죽여서 **예매가 같이 죽는 것**을 재현한다. 그 재현이 이벤트 기반(카프카)과 서킷 브레이커의 근거다. 둘 중 무엇이 맞는지도 이 측정이 가른다 — 조회 의존은 서킷 브레이커, 상태 전파는 이벤트다
- **Task 051: [공통] 분산 추적** — 서비스가 둘이 되면 "느린 요청이 어디서 느렸나"를 알 수 없게 되는 것을 먼저 겪는다. Task 025가 Prometheus를 넣었으니 Tempo 또는 Jaeger + OpenTelemetry로 잇는다. **p95가 버킷 경계를 읽던 004_3의 함정**과 같은 종류의 오독이 추적에도 있다는 것을 확인한다
- **Task 052: [BE] 데이터 일관성** — 허브인 `reservation`을 떼면 Saga 또는 2PC가 필요해진다. **여기까지 오면 "모놀리스가 옳았다"가 결론일 수도 있다.** v0.2.0이 조건부 UPDATE를 고른 근거가 "DB 제약은 경로와 무관하게 성립한다"였는데, 서비스를 쪼개는 것은 그 보장을 스스로 포기하는 일이다. 그 교환을 수치와 함께 기록하는 것이 이 Task의 목적이고, **되돌리는 결정도 산출물이다**

### Phase 12~14를 묶는 규칙

이 세 Phase는 기술을 도입하는 것이 목적이 아니라 **도입 근거를 만드는 것**이 목적이다. 그래서 모든 Task가 같은 모양을 지킨다.

1. **단순한 해법을 먼저 구현한다** — Redis Pub/Sub, `@Async`, 아웃박스 배치, HTTP 동기 호출
2. **그 해법이 깨지는 조건을 재현한다** — 구독자 사망, 애플리케이션 재시작, 폴링 지연, 연쇄 장애
3. **재현된 뒤에 교체하고 before/after를 잰다**
4. **기각 조건을 미리 적어둔다** — 깨지지 않으면 도입하지 않고, 그 사실을 기록한다

이 순서를 지키면 "왜 카프카인가"에 수치로 답할 수 있다. 뒤집으면 **브로커가 이미 있다는 사실이 모든 판단을 흐린다** — 029가 좌석맵 캐싱을 기각할 수 있었던 이유는 Redis를 이미 쓰고 있었음에도 **측정을 먼저 했기** 때문이다.

#### 카프카 근거는 셋이고 서로 독립이다

Phase 12가 Task 036 하나에 매달려 있어서, 그것만 보면 "036이 기각되면 카프카가 사라진다"로 읽힌다. 실제로는 근거가 셋이고 **의존하는 전제가 전부 다르다.**

| 근거 | 어디 | 전제 | 확실성 |
|---|---|---|---|
| 경로 A — 로컬 캐시 무효화 전파 | Task 044·045 | 036에서 Caffeine이 **포화 구간** 이득일 것 + 그 캐시에 무효화가 필요할 것 | **막혔다.** 앞쪽은 성립(+29.5%)했는데 **뒤쪽이 깨졌다** — 불변 필드만 캐시해서 evict가 없다(014 4.5절) |
| 경로 B — 좌석 선점 쓰기 버퍼링 | Task 045_1 | 대기열 뒤에 최종 방어선이 없다는 것(037) | 낮다. **기각이 기본값**으로 적어 뒀다 |
| 실패와 보상 | Phase 13 (046~048) | 환불 실패 시 돈은 나가고 예약은 없다 — **002가 이미 남긴 실재 버그** | **높다.** 재현이 보장된다 |

**경로 A는 036에서 막혔다.** 전제가 둘이었고 앞쪽만 성립했다 — 포화 구간 이득은 확인됐지만(+29.5%, postgres CPU -62.9%) **그 캐시에 무효화가 필요 없다.** 불변 필드만 담아서 BE 2대가 다른 값을 들 수가 없고, 그러면 044의 재현 대상도 045의 전파 메시지도 없다. 불일치를 만들려면 상태를 캐시해야 하는데 그건 008부터 거부해 온 설계다. **기각이 기본값이고, 그러면 Phase 13을 앞으로 당긴다**(아래 문단이 이미 그 분기를 적어 뒀다). 자세한 것은 014 4.5절.

**셋 중 가장 확실한 것이 Phase 13이다.** `MockPaymentGateway`가 절대 실패하지 않아서 아직 재현이 없을 뿐이고, 실패를 주입하면 002의 한계가 그대로 버그가 된다. 즉 **Phase 12가 통째로 기각되어도 카프카 근거는 남는다.** 순서를 12 → 13으로 두는 이유는 성능 근거를 먼저 세우는 쪽이 이야기가 깔끔하기 때문이고, **036이 기각되면 13을 앞으로 당긴다**(그 시점에 12에 남는 근거는 경로 B 하나이고 그것도 기각이 기본값이다).

셋 다 기각되면 **카프카를 쓰지 않는 것이 결론**이고 그것도 산출물이다. 003이 분산 락을, 029가 좌석맵 캐싱을 기각한 것과 같은 모양이다.

#### 배포 게이트 (Task 034)

**Task 043의 판정이 끝나면 배포한다.** Phase 14가 열려서 완료되든, 043이 간섭을 재현하지 못해 Phase 14가 기각되든 **둘 다 '판정 완료'**다.

재개 조건을 "MSA 구현 완료"로 걸지 않는 이유는 **Phase 14가 열리지 않을 수 있도록 설계돼 있어서**다. 구현을 조건으로 걸면 043이 기각일 때 둘 중 하나가 된다 — 배포가 영구히 오지 않거나, 근거 없이 Phase 14를 강행하거나. **후자는 이 로드맵이 11편에 걸쳐 거부해 온 바로 그것이고, 마지막 Phase에서 그걸 깨면 앞의 기각 기록 전부가 설득력을 잃는다.**

> [!warning] 확인 필요
> 043에서 간섭이 재현될지는 아직 모른다. `browse` 10,150 req/s와 `seatmap` 846 req/s가 같은 스레드풀·커넥션풀(기본 10)을 공유하므로 **재현될 가능성이 낮지 않다고 보지만, 그건 예상이고 측정이 아니다.** 재현되지 않는 경우를 대비해 위 '배포 게이트'를 '판정 완료'로 정의한 것이다.

## 브랜드 디자인 토큰 (Task 003 적용)

퍼플을 `primary`, 강한 핑크를 별도 `--highlight` 토큰으로 분리한다. shadcn의 `--accent`는 hover 배경으로 쓰이므로 강한 핑크를 넣으면 과해져, 옅은 핑크 틴트로 둔다.

| 토큰 | Light | Dark |
|---|---|---|
| primary (보라) | oklch(0.52 0.24 295) | oklch(0.68 0.20 295) |
| accent (옅은 핑크 틴트) | oklch(0.95 0.03 350) | oklch(0.30 0.06 350) |
| highlight (강한 핑크) | oklch(0.58 0.22 355) | oklch(0.72 0.20 355) |
| destructive | oklch(0.52 0.245 27.3) | oklch(0.704 0.191 22.2) |

- Task 016에서 라이트 모드 highlight(0.60→0.58)·destructive(0.577→0.52)의 명도를 낮춰 텍스트 대비 4.5:1(WCAG AA)을 맞췄다. 알려진 한계: `--border`/`--input`은 배경 대비가 1.2~1.5:1이라 입력창 테두리의 비텍스트 대비 기준(3:1)에는 못 미친다. shadcn 기본값이고 전체 톤이 바뀌는 사항이라 이번에는 두지 않았다.
